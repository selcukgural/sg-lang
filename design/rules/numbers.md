| Topic | Decision | Reason |
|---|---|---|
| <a id="arithmetic-on-small-integers"></a>Arithmetic on small integers | An operation happens in the type of its operands: `byte + byte` is a `byte`, and overflow panics as everywhere else. A `byte` widens to `int`, `long` and `nint` on its own; the way back is `(byte)x` | Rust's rule. C# computes in `int`, which is one more rule to know. Cost: `int x = b + 1000` is an error and is written `(int)b + 1000`. Approved on 12 November with the interpreter's sixth slice, as are the other rows of that slice ([the record of 12 November](../decisions/2026-11-12.md#slice-6)) |
| <a id="minus-on-a-byte"></a>`-` on a `byte` | Compile error; the hint is `-(int)b` | The result could only be 0 (Rust). Caught at compile time instead of a panic |
| <a id="integer-overflow"></a>Integer overflow | Rust's way, decided on 12 November: `+`, `-`, `*` and unary `-` panic on overflow in a debug build and in tests, and wrap in a release build (two's complement, defined, never undefined behaviour). `tryAdd` returns `int?` and is checked in every build; `wrappingAdd` wraps in every build. Division by zero and `MIN / -1` panic in every build | Overflow cannot break memory safety, because an index is still bounds checked; it is a correctness error. Measured on 12 November: the check cost nothing in ordinary code and 40 to 60% in loops that are only arithmetic. The first decision (6 November) was to panic in release too, as Swift does; it was changed when the cost was measured. Whoever needs the check in release writes `tryAdd` |
| <a id="implicit-conversion"></a>Implicit conversion | `read T` stands in for `T` if `T` is `Copyable`. A `read T*` can be given to a `read T` parameter | Otherwise a dereference would be needed on every line |
| <a id="number-types"></a>Number types | Based on the C# types: `byte`, `short`, `int`, `long`, their unsigned counterparts, the pointer-sized `nint` and `nuint`, `float`, `double`. `int` is 32 bits on every platform. Indexes and lengths are `nint` | No new names for a C# reader. If `int` were the index, `List` would stop at 2 billion items |
| <a id="narrowing-conversion"></a>Narrowing conversion | Written `(int)x`. It follows the overflow rule (12 November): if the value does not fit it panics in a debug build and in tests, and is cut to size in a release build; `tryToInt` is checked in every build and `wrappingToInt` cuts in every build. *(Until 12 November: a panic in every build.)* `x.tryToInt()` returns `int?`, `x.wrappingToInt()` truncates on purpose. A conversion whose value is known at compile time and does not fit is a compile error: `(byte)300`. No warning on every conversion; hovering over it in the editor shows the possibility of a panic and the two methods, and the panic message shows the value and `tryToInt`. `(int)3.7` gives 3, `NaN` or out of range panics. A widening conversion (`int` → `long`) is implicit | C# truncates silently and a wrong number comes out. A warning on every line would also appear in correct code and would be ignored; `a + b` and `xs[i]` do not warn either. Cost: one comparison per conversion |
| <a id="float-double-and-nan"></a>`float`, `double` and `NaN` | The C# way. The `==` and `<` operators are as in the hardware: `NaN == NaN` is false. `equals` and `compare` give a total order: `NaN` is equal to itself and is the smallest, and `sort`, `max`, `contains` work. Both are `Equatable` and `Comparable`, not `Hashable`: `HashMap<double, V>` is a compile error | Rust splits equality and order into "partial" and "total", and `sort` does not compile on a list of fractional numbers; that means two more concepts. Cost: the rule "`a == b` means `a.equals(b)`" does not hold only for fractional numbers. The ban on keys can be relaxed later |
| <a id="the-bits-of-an-integer"></a>The bits of an integer | C23's `<stdbit.h>` as methods: `countOnes`, `countZeros`, `leadingZeros`, `trailingZeros`, `leadingOnes`, `trailingOnes`, `rotateLeft(n)`, `rotateRight(n)`, `reverseBytes`, `reverseBits`, `isPowerOfTwo`, `nextPowerOfTwo`, `log2`. A count, and `log2`, is an `int`. Counting, turning and rotating work on every integer type, a signed one by its bits; the powers of two only on the unsigned ones (hint `((uint)n).isPowerOfTwo()`); C's `long` has none. The count of a rotation is cut to the width of the type, with no panic. `nextPowerOfTwo` follows the rule of overflow; `log2` rounds down and panics on 0 in every build. In compiled code the builtins of the C compiler, with 0 guarded. Approved on 18 November 2026, before the hundred-and-seventh slice (choices 1177 to 1183) | Rust's names and rules (`ilog2` panics on 0; C#'s `Log2(0)` is 0, the same as `Log2(1)`). A count is an `int` as in C#'s `BitOperations`, not Rust's `u32`: a length in SG is signed, and an `int` and a `uint` do not mix, so a `uint` count would need a cast in `32 - n.leadingZeros()` and as an index. Each is one instruction or a few, as C writes them |
| <a id="bit-operators"></a>Bit operators | `&`, `\|`, `^`, `~`, `<<`, `>>` and `&=`, `\|=`, `^=`, `<<=`, `>>=`, on integers only; two `bool`s have `&&`, `\|\|` and `!=`, and the error says which. `&`, `^` and `\|` bind tighter than a comparison, so `flags & mask == 0` tests the masked value; among themselves the order is C's (`\|`, `^`, `&`, shifts, `+ -`, `* / %` from loosest to tightest), and a bound of a range takes everything tighter than a comparison. `a & b` follows the rule of arithmetic (`byte & byte` is a `byte`), `~x` has the type of `x`. In compiled code they are the operators of C, cut back to the type. Approved on 13 November with the interpreter's "thirty-second slice" | In C and C# `flags & mask == 0` means `flags & (mask == 0)`, a leftover its authors called a mistake; Rust, Go, Swift and Zig read it as here. With C#'s order the line would be a compile error here, so the choice was between an error on a line that can mean one thing and the line working. Go's fewer levels would change what `1 << n + 1` means for a reader from C or C#. Cost: none at run time |
| <a id="shifts"></a>Shifts | A shift has the type of its left side and the count is any integer: `b >> 4` on a `byte` is a `byte`, and the expected type reaches the left side alone (`long wide = 1 << 40` shifts a `long`). The count follows the overflow rule: below zero, or not below the bits of the type, it is a compile error where it is known, a panic in the interpreter, in tests and in a debug build ("shift by 32 is out of range: int has 32 bits"), and cut to the bits of the type in a release build. The bits that `<<` pushes out are gone in every build. `>>` carries the sign on `int`, `long` and `nint` and brings in zeros on `byte`; there is no `>>>`. `x << (n & 31)` means the same in every build; there are no `wrapping...` or `try...` methods for shifts. Approved on 13 November | Rust's rule. The cut is what the shift of the machine does by itself, so a release build pays nothing. In C such a count is undefined and `1 << 40` is an `int` shifted too far; C# always cuts and never tells; Go tests in every build. Measured with `bits`: the sieve half takes the time of C |
| <a id="writing-a-number"></a>Writing a number | Decimal, hex (`0xde`), binary (`0b1010`), with `_` between digits (`1_000_000`, `0xdead_beef`). The prefix is a small letter, the hex digits may be either; no octal *(26 November 2026, slice 191, choice 1977: octal came in as `0o755`, the row [The permissions of a file](input-output.md#the-permissions-of-a-file); `010` stays ten)*. Such a number takes the type it is used as, like any other, and one that does not fit is an error that shows it as written with its value (`int mask = 0xffff_ffff`). Approved on 13 November | Nothing at run time, a dozen lines in the lexer. In C# `0xffff_ffff` quietly becomes a `uint`; Rust refuses it as here. C's octal (`010` is 8) is a trap and is left out |
| <a id="a-number-as-a-condition"></a>A number as a condition | `if flags & 2 {` is "expected `bool`, found `int`" with the hint "a number is not a condition; compare it: `flags & 2 != 0`". Approved on 13 November | The habit from C; the error was already there, the hint says what to write |
| <a id="the-other-integer-types"></a>The other integer types | `sbyte`, `short`, `ushort`, `uint`, `ulong` and `nuint` come together, next to `byte`, `int`, `long` and `nint`. Decided on 13 November | The names of the ["Number types"](#number-types) row; one line each in compiled code, so the four that are rarer cost little more than the two that hashes and rotations need |
| <a id="mixing-integer-types"></a>Mixing integer types | A type widens to another on its own only when the other holds every one of its values, on every machine (`nint` and `nuint` count as at least 32 bits). A signed type never becomes an unsigned one on its own. Two types where neither holds the other (`int` and `uint`, `long` and `ulong`) do not mix: a compile error whose hint is the cast. Decided on 13 November | Rust and Go widen nothing on their own; C# turns `int + uint` into a `long`; C turns the `int` into an `unsigned` without a word, so `-1 < 1u` is false. Core principle: caught at compile time, with the fix in the hint. Cost: none at run time |
| <a id="a-number-next-to-another-type"></a>A number next to another type | A number written in the program takes the type of the other side, on either side: `1 + count` and `count - 1` with a `uint count` are `uint`s. A number past every `long` on the left is typed from the right side (`0xffff_ffff_ffff_ffff == top`). Approved on 13 November | Without it `1 + count` would need a cast, since `int` and `uint` do not mix. Cost: none at run time |
| <a id="a-number-is-never-unsigned-on-its-own"></a>A number is never unsigned on its own | With no type where it goes, a number is an `int`, or a `long` if it does not fit in an `int`; one past every `long` is an error whose hint writes the `ulong` type. Approved on 13 November | C# quietly makes `0xffff_ffff` a `uint` and a larger one a `ulong`; Rust refuses as here |
| <a id="negative-and-unsigned"></a>Negative and unsigned | `-x` on an unsigned type is an error with the hint `-(long)x`, as on `byte`. A constant that cannot fit is a compile error with the note "a `uint` is never negative" (`(uint)-1`, `ushort port = -1`); a cast whose value is known only at run time follows the overflow rule. Approved on 13 November | Rust refuses `-x` the same way; C# makes `-uint` a `long`; C wraps |
| <a id="shift-shift-on-unsigned-types"></a>`>>` on unsigned types | `>>` brings in zeros on every unsigned type and carries the sign on the signed ones, so a rotation is `value << by \| value >> (32 - by)` on a `uint`. There is no `>>>`. Approved on 13 November | The type decides, as in C#, Rust and Go |
| <a id="unsigned-types-in-compiled-code"></a>Unsigned types in compiled code | `int8_t` to `uint64_t`; `nint` and `nuint` are `int64_t` and `uint64_t`. A failing operation hands its numbers to the panic as `__int128`, so a `ulong` is written in full, and a cast tests its value the same way. The interpreter keeps every integer as its value in 128 bits. Approved on 13 November | `__int128` is a clang and gcc extension like the overflow builtins already used, and costs nothing measurable. Measured with `hash` (XXH64 on `ulong`): the time of C, once the eight bytes it reads are cut out of the data first |
| <a id="writing-a-fractional-number"></a>Writing a fractional number | Digits on both sides of the point or an exponent: `1.5`, `1e9`, `6.674_30e-11`; a small `e`, `_` between digits, no suffix (`1.5f` is an error). It takes the type it is used as, `double` where nothing says otherwise. A number that would become infinity or 0 in its type is an error (`1e400`); a whole number where a fractional one goes becomes one if the type holds it exactly. Approved on 13 November | The rule of the integers: the type is where the number goes. C# needs `f` for a `float`; Rust infers as here |
| <a id="fractional-and-integer-types"></a>Fractional and integer types | A number becomes fractional on its own only when the type holds every value of it exactly: `float` to `double`, the integers up to 16 bits to both, `int` and `uint` to `double`; never `long`, `ulong`, `nint` or `nuint` (hint `(double)n`), never `double` to `float`, never a fractional number to an integer. Approved on 13 November, after looking at the cost | The mixing rule of the integers carried on. Cost: `sum / xs.length()` needs `(double)`, a length being a `nint`. C# converts a `long` to a `double` without a word and loses digits past 2^53; Rust and Go convert nothing on their own. A value that is sometimes whole and sometimes not is an enum written out |
| <a id="fractional-arithmetic"></a>Fractional arithmetic | The hardware's: `+ - * / %` and `-x` never panic, a division by zero gives `Infinity` or `NaN`, `%` keeps the sign of the left side, a `float` is computed as a `float`. Each operation is rounded on its own; nothing is fused into a multiply-add, in the interpreter and in compiled code (`-ffp-contract=off`). No bit operators. Approved on 13 November | Compiled code and the interpreter give the same digits; clang on arm64 fuses by default. A fused multiply-add on request (`x.fma(y, z)`) can come later |
| <a id="equality-with-fractional-parts"></a>Equality with fractional parts | `-0.0` equals `0.0` for `equals` and `compare` too. `==` on a struct, a list or an array compares its fractional parts with `equals`, so a value that holds `NaN` equals itself. `sort`, `indexOf`, `contains` use the total order. A fractional number cannot be a `match` pattern. Approved on 13 November | C#'s records and default comparer; every `Equatable` value equals itself. Cost: `p == q` is not always `p.x == q.x` |
| <a id="fractional-to-integer"></a>Fractional to integer | `(int)x` drops the fraction. A value that does not fit, `NaN` included, follows the overflow rule: a panic in the interpreter, tests and a debug build; in a release build the nearest value the type holds, 0 for `NaN`. A constant that cannot fit is a compile error. `(double)n`, `(float)n`, `(float)d` round and never fail. Approved on 13 November | Rust's `as` for the release build; in C the same cast is undefined behaviour |
| <a id="printing-a-fractional-number"></a>Printing a fractional number | The fewest digits that read back as the same number (as a `float` for a `float`), laid out as JavaScript does: `0.1`, `2`, `1e+21`, `1e-7`, `NaN`, `Infinity`, `-0`. Of those digits the nearest, a tie between two to the even digit (*changed on 15 November 2026, in the sixty-eighth slice, choice 496:* until then the number was rounded to 1, 2, ... digits until it read back, which next to a power of two can give one digit more; compiled code finds the digits with Dragonbox, the interpreter with Rust's shortest digits, and they agree by the rule). Methods: `abs`, `sqrt`, `floor`, `ceil`, `round` (half away from zero), `truncate`, `isNaN`, `isInfinite`. Approved on 13 November | The digits are those of C# and JavaScript; C# changes to an exponent from 10^15, Rust never. The constants and the math methods came in the next slice (see ["Constants of the number types"](#constants-of-the-number-types), ["Math methods"](#math-methods)) |
| <a id="fractional-numbers-in-compiled-code"></a>Fractional numbers in compiled code | C's `float` and `double`, `<math.h>` and `-lm`; one helper per integer type for a cast from a fractional number. Measured with `nbody`: the time of C. Approved on 13 November | Nothing on a fractional number is checked, so the overflow-checked build takes the same time |
| <a id="reading-a-number-out-of-text"></a>Reading a number out of text | `T.parse(read string text)` on every number type gives `Result<T, NumberError>`, called on the type: `int.parse(text)`, `double.parse(text)`. A whole number is a sign and digits and nothing else: no spaces, no `_`, no `0x`; a `-` on an unsigned type is an error. A fractional number may also have a point (`.5` and `5.` too) and an exponent (`1e3`, `1E-3`), and `NaN`, `Infinity`, `-Infinity` as `print` writes them. The value is the nearest number of the type; a fractional one past the largest is `Infinity`, as in Rust, C# and C. Approved on 13 November | What `print` writes, `parse` reads back. Data writes `.5` and `1E5`, so the reader is looser than a number written in the program; spaces are trimmed by the program, not ignored silently |
| <a id="the-error-of-parse"></a>The error of `parse` | The built-in `enum NumberError : Copyable, Formattable, Equatable { Invalid(nint position), OutOfRange }`: `Invalid` is the byte where the text stops being a number (its length when it ends too early, so an empty text is `Invalid(0)`), `OutOfRange` a whole number the integer type does not hold. Every byte is looked at before the size. Seen from every module, cannot be defined again; `try` puts it into the caller's error type. Approved on 13 November | Two cases to handle, and a position to show. Rust has five kinds and Go two, neither with a position |
| <a id="constants-of-the-number-types"></a>Constants of the number types | `MinValue` and `MaxValue` on every integer type (`nint.MaxValue` is the machine's); on `float` and `double` also `NaN`, `Infinity`, `Pi`, `E`, and `MinValue` is the most negative finite number. A constant is a value of its type, not a number written out: `uint u = int.MaxValue` needs `(uint)`. `Epsilon` is left out, and the error says why. Approved on 13 November | C#'s names. C# lets a constant that fits go to any type, but `nint.MaxValue` depends on the machine; one rule for all. `Epsilon` is the smallest number above zero in C# and the gap after 1 in C and Rust |
| <a id="conversions-that-do-not-panic"></a>Conversions that do not panic | `x.tryToInt()` gives `null` if the value does not fit, checked in every build; `x.wrappingToInt()` keeps the bits that fit, in every build; the same for every integer type, named after it (`tryToUlong`, `wrappingToByte`). On a fractional number only `tryTo...`, toward zero. One that cannot fail (`b.tryToInt()` with a `byte b`) is an error with a hint. Approved on 13 November | The pair of `tryAdd` and `wrappingAdd`, for a conversion: `tryTo` where a value that does not fit is an error, `wrappingTo` where cutting is what is meant (a hash, the low byte) |
| <a id="panics-name-the-way-out"></a>Panics name the way out | The panic of a cast names `tryToX()` and `wrappingToX()`; the panic of `+`, `-`, `*` names `tryAdd` and `wrappingAdd` (and the others), of `/` `tryDivide`. Compiled code writes the same lines. Approved on 13 November. An index past the end of a list, an array or a slice names `.get(i)`, which gives `null` (19 November, choice 1401). The text of a `panic`, the code of an `assert` and the values it compared, and a key that is not in the map are the program's own and are shown as written, where the tool's own messages choose `a` or `an` before code (21 November, choice 1596) | The row ["Narrowing conversion"](#narrowing-conversion) asked for it. `-x` and the shifts have no such method yet |
| <a id="math-methods"></a>Math methods | On `float` and `double`: `exp`, `log` (natural), `log2`, `log10`, `sin`, `cos`, `tan`, `asin`, `acos`, `atan`, `y.atan2(x)`, `x.pow(y)`, `a.fusedMultiplyAdd(b, c)` (rounded once); two numbers meet as with `+`. From the C library in the interpreter and in compiled code, so on one machine they agree to the last digit. On an integer the hint is `((double)x).sqrt()`. Approved on 13 November | Methods, as `sqrt` already is, not `Math.Sin(x)`. Across machines `sin` and the others may differ in the last digit, as in every language that uses the C library |
| <a id="min-and-max"></a>`min` and `max` | On integers the two meet as with `+`. On fractional numbers `NaN` if either side is one, and `-0` is less than `0` (C#, IEEE 754-2019 `minimum`). Approved on 13 November | C's `fmin` and Rust's `f64::min` give an answer that depends on the order and on the machine |
| <a id="reading-fractional-numbers-in-compiled-code"></a>Reading fractional numbers in compiled code | Clinger's fast path (digits that fit in 53 bits, a power of ten up to 10^22: one correctly rounded operation), otherwise `strtod`; correctly rounded like the interpreter, compared on 8000 random texts. Measured with `numbers`: reading takes the time of `strtoll` and `strtod`. Approved on 13 November | Rust takes the same fast path. Building the text with `toString` is slower than C; printing a `double` is on the list of slow places |
| <a id="parsehex"></a>`parseHex` | `T.parseHex(text)` on every integer type gives `Result<T, NumberError>`: small and capital digits, no `0x`, the sign rule of `parse`, and the value must fit the type (`"80000000"` on an `int` is `OutOfRange`). An error on a fractional type, hint `parse`. Approved on 14 November 2026 | Rust's `from_str_radix` agrees; C#'s `HexNumber` takes the digits as bits. `parse(text, 16)` would be a parameter and a check more for a base that is almost always 16, and `0x` read by `parse` would change what `"0x10"` gives today |
| <a id="numbers-out-of-bytes"></a>Numbers out of bytes | `T.fromLittleEndian(bytes)` and `T.fromBigEndian(bytes)` on `short`, `ushort`, `int`, `uint`, `long` and `ulong`: a function of the type, as `parse` is, that takes a `read byte[]` and gives the number the bytes write, the lowest byte first or the highest first; a signed type reads the highest bit as the sign. Approved on 14 November 2026 | Rust `u64::from_le_bytes`, Go `binary.LittleEndian.Uint64`, C# `BinaryPrimitives.ReadUInt64LittleEndian`. The name says the order in whole words and leaves out "bytes", which the argument already is. What a file format needs (a GIF keeps its sizes in two bytes, the lowest first) |
| <a id="exactly-as-many-bytes"></a>Exactly as many bytes | The window holds exactly as many bytes as the type takes (2, 4 or 8). A width the program shows (an array, `xs[..k]`, `xs[a..b]` with constants, `xs[at..at + k]` where `at` is a variable or a field of one) and that is another is a compile error whose hint is the window of the right width; a width that depends on data panics with both numbers. Approved on 14 November 2026 | Rust (`[u8; 8]`) and Zig (`*const [8]u8`) want exactly so many; Go and C# read the first ones and leave the rest. A window of another width is nearly always a wrong position or a wrong type. Cost: the width is written (`data[at..at + 8]`), which also shows the reader what is read |
| <a id="numbers-into-bytes"></a>Numbers into bytes | `n.toLittleEndian()` and `n.toBigEndian()` give the bytes of the number as a `byte[N]` where the value is; nothing is allocated. `out.addAll(read n.toBigEndian())` puts them into a list. Approved on 14 November 2026 | Rust `to_le_bytes`. Rust's `to_le` gives a number with its bytes turned around; SG has no such method, so the shorter name is free for the bytes |
| <a id="what-has-neither"></a>What has neither | `byte` and `sbyte` (one byte has no order), `nint` and `nuint` (an address has the size the machine gives it, a number kept in bytes has a size of its own) and the fractional types have neither function nor method; each is an error with a hint (`data[i]`, the `long` form and a cast). The names other languages use (`from_le_bytes`, `toBytes`) get the hint of the name here; a call whose value is not used is an error, as for every built-in method that only gives a value. Approved on 14 November 2026 | A fractional number out of bytes is not here yet |
| <a id="bytes-and-numbers-in-compiled-code"></a>Bytes and numbers in compiled code | One C function for each type and order: the count is compared with the width, then `memcpy` into a `uint64_t` (or narrower) and a byte swap where the machine keeps its bytes the other way. Where the window was cut with a constant width just before, the C compiler removes the test; writing is one store into the array. Approved on 14 November 2026 | Measured: XXH64 reads with it in 1.03 times the time of C, and its overflow-checked build went from 3.6 to 1.23 times C, since the overflow tests of `at + 8` no longer stand between eight reads |
