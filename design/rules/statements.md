# Statements, variables and names

How a program is laid out: lines, blocks, loops, assignments, the order things run in, and values and names that are not used. Each row is a decision with its reason, in the order it was made; the choices
of each slice are in [the records by day](../decisions/README.md), and the other topics in
[the decisions by topic](README.md).

| Topic | Decision | Reason |
|---|---|---|
| <a id="main"></a>`main` | `void main()`, `Result<void, E> main()`; `main(List<string> args)` for the command line (13 November) | Every function starts with its return type, no exceptions |
| <a id="return-in-an-expression"></a>`return` in an expression | Written only on the right side of `??` and as an arm of a `match`, a `match` that gives a value too (the arm `_ => return 0` of `var percent = match code { ... }`); not in an arm of `?:` (1915, 25 November; the arm of a `match`, 2085, 27 November) | The two places it reads well: an arm of a `match` stands on a line of its own, and the right of `??` is the end of one. Anywhere else it hides an exit in the middle of a line. An arm of `?:` is one value among others on the same line |
| <a id="order-of-evaluation"></a>Order of evaluation | The parts of an expression are computed from left to right: the arguments of a call (the receiver first), the two sides of an operator, the fields of a literal, the values of a formatted text. The values of a formatted text (`$"..."`) are all computed before any of them is written: a `format` method runs when every value of the line is there (`$"{a} {say(3)}"` calls `say(3)` first, then `a`'s `format`; decided on 13 November, Rust's `write!` does the same, and it lets `f.write` put a struct straight into the text with no allocation). Compiled code keeps to it although C does not promise it: where the order can be seen (two parts that can stop the program or call a function, or one that lends with `ref` what another reads) the earlier parts are computed into variables first. Decided on 12 November. The receiver of a built-in method (`text.contains(read make())`, `map.add(k, v)`, `tx.send(v)`) is found, and lent, before an argument whose value is kept until the statement ends, as for a call (1348, 19 November). An assignment is a statement with an order of its own: its right side is computed first, then the place is found and written (`xs[place()] = value()` calls `value` first), for `+=` and the others too; a borrow the right side reads last ends before the write (`b = Box { n = r.n + 1 }` where `r` borrows `b`), and what the place uses must still hold after the right side. Decided on 14 November, in the forty-sixth slice | The interpreter always did this; a program must not depend on the C compiler it was built with. Nothing is paid where the order cannot be seen. The order of an assignment is Rust's (C# and Java find the place first): the place is found right before it is written, so its address cannot be stale when the right side grows a list, and the right side can be made from the value it replaces |
| <a id="leaving-in-the-middle-of-a-line-in-compiled-code"></a>Leaving in the middle of a line, in compiled code | A `match` gives its value inside a larger expression: it is written before the statement and the parts before it are computed first, so the order stays left to right. A value that owns something and has no name (an argument, a field of a struct being built, a value of an enum value) is kept under a name when something after it can leave the function (`try`, `?? return`, a `match`), and the way out frees it. Every compiled program is looked at for leaks by the tests, and the leak check itself is tried on a program that leaks on purpose. Still refused, as limits of the back end: leaving after an item of a list being built or after a side of an operator that owns something, in an argument of a method call, inside `$"..."`, on the right of `&&` and `\|\|`, inside `assert`. Decided on 13 November | Nothing is paid where nothing can leave; one store for each kept value where something can. A value left behind is not seen in the output or by the sanitizers, so it is looked for by name |
| <a id="loops-with-a-name"></a>Loops with a name | `outer: for ...`, `outer: while ...`, and inside, `break outer` and `continue outer`. A name not used is an error, as is the name of a loop around it again; loops side by side may share one; names of loops are apart from those of variables. Leaving goes as `break` does: what the bodies left own is let go, through `lock`, `as`, `unsafe` and an arm of a `match`, and `while true` left only by `break outer` is a loop that ends. In compiled code a `goto`. Approved on 18 November 2026, before the hundred-and-sixth slice (choices 1148 to 1150) | C2y's named loops, Go's and Java's notation; Rust writes `'outer:`, C# has only `goto`. Without it, leaving two loops takes a flag and a test in each round |
| <a id="counting-down"></a>Counting down | `for i in (a..b).reversed()`: the numbers of `a..b`, the last first; none when `a` is not below `b`. The ends are found once, the left first. In compiled code the end is taken down by one before each round, so an unsigned counter stops at 0 without wrapping. A range in brackets is written only so, at the head of a `for`. Approved on 18 November 2026, before the hundred-and-sixth slice (choice 1155) | Rust's `(a..b).rev()`, Swift's `reversed()`. Counting down by hand with `while` and a `uint` is a loop that never ends |
| <a id="the-order-of-an-assignment"></a>The order of an assignment | An assignment computes its right side first, then finds the place and writes it, for `=` and for `+=` and the others: `xs[place()] = value()` calls `value` first (see ["Order of evaluation"](#order-of-evaluation)). Decided during the forty-sixth slice and approved with it on 14 November 2026 | Rust's order; C# and Java find the place first. The place is found right before it is written, so its address cannot be stale when the right side grows a list, and the right side can be made from the value it replaces. Compiled code had taken the place first, so the two programs printed in different orders and an item could be written through a moved address |
| <a id="assignments-in-compiled-code"></a>Assignments in compiled code | When the place is more than a variable, the right side is computed into a C variable first, and the address of the item is taken after it. Approved on 14 November 2026 | Nothing is paid: the C compiler removes the variable, and the measured programs that write items compile to the same instructions, up to the names of registers |
| <a id="a-new-text-that-is-not-used"></a>A new text that is not used | A call of `replaceAll` or `repeat` whose result is not used is a compile error (`line.replaceAll('\t', " ")` alone changes nothing); the hint assigns the new text back when the text is a variable or a field. The other methods that give a new value (`trim`, `clone`, `toString`) are left as they were for now. Approved on 14 November 2026; the forty-eighth slice took the rule to every built-in method that only gives a value (["The value of a built-in method"](#the-value-of-a-built-in-method)) | Rust warns (`#[must_use]`), Zig refuses every value thrown away; SG has no warnings. No cost at run time |
| <a id="the-value-of-a-built-in-method"></a>The value of a built-in method | Every built-in method that only gives a value is a compile error when the value is not used: `line.trim()`, `name.clone()`, `count.toString()`, `distance.abs()`, `xs.contains(3)`, `xs.length()`, `total.tryAdd(1)` and `string.join(", ", read names)` alone do nothing. It takes the methods that give a new value and the ones that answer a question alike, so it is one rule with no list to learn. `_ = xs.contains(3)` throws a value away on purpose. Approved on 14 November 2026 | Zig refuses every value thrown away; Rust marks most of these `#[must_use]` and warns. No cost at run time: the checker alone |
| <a id="methods-that-change-and-give"></a>Methods that change and give | *Replaced on 16 November 2026 by ["Every value of a call"](#every-value-of-a-call) below.* A built-in method that changes its value and gives one too may stand alone: `xs.removeLast()`, the `add` and `remove` of a `HashSet`, the `remove` and `getOrAdd` of a `HashMap`, `next` on an iterator. The change is what they are called for. Approved on 14 November 2026 | As in Rust, where `Vec::pop` and `HashSet::insert` may stand alone |
| <a id="functions-of-your-own"></a>Functions of your own | *Replaced on 16 November 2026 by ["Every value of a call"](#every-value-of-a-call) below.* A function or a method you write may stand alone even when it gives a value: it can print, change through `ref` or stop, and the checker does not know which ones do nothing else. A `Result` stays an error everywhere. Approved on 14 November 2026 | Zig asks for `_ =` here too; SG keeps the error for what it knows does nothing |
| <a id="the-words-of-an-unused-value"></a>The words of an unused value | A method that gives a new value of the type of the variable or field it is called on says "it leaves `x` as it was", and the hint assigns it back (`x = x.abs()`); `trim`, which gives a look at the same text, has `var text = line.trim()` as the hint; the others name what was not used ("the copy that `clone` makes", "the value that `contains` gives"). Approved on 14 November 2026 | The hint is the line to write |
| <a id="a-break-inside-an-expression"></a>A `break` inside an expression | The check for a `break` in a loop looks inside every expression (a `match` arm in `1 + match k { ... }`, the condition of an `if`, the range of an inner loop). Before, such a `break` was missed: `while true { ... }` counted as never ending, and a function ending with it was accepted without a `return` and gave whatever was in a register in compiled code. Approved on 14 November 2026 | A hole found during the forty-ninth slice, closed in it |
| <a id="end-of-line"></a>End of line | No semicolons, the end of a line ends the statement. A statement continues on the next line in these cases: inside `(` or `[`; if the line ends with an operator, a comma, a dot or an opening parenthesis; if the next line starts with `.` (a method chain). A line cannot start with an operator, and the hint says to move the operator to the end of the previous line | Go's rule + Python's parenthesis rule; the leading `.` is for the chain notation of C# and Rust. A leading operator creates ambiguity (`- x`), a leading dot does not. Approved on 12 November together with the interpreter |
| <a id="place-of-and-else"></a>Place of `{` and `else` | `{` at the end of the line, `else` on the same line as `}`: `if x {`, `} else {`. Writing them on a new line is a compile error, and the hint shows the right place | The Go way: a single form. C#'s usual layout (`{` on a new line) was deliberately not taken, there would be two ways to write the same thing |
| <a id="statement"></a>Statement | Only a call, an assignment and a declaration are written as a statement; `a + 2` alone is a compile error. A name at the start of a statement, followed by `*` and `?`, followed by a second name, is a declaration: `int x = 1`, `Node*? list = null` | The C# rule (CS0201). This way the distinction between `Node* n` and `a * b` is resolved with lookahead: `a * b` cannot be a statement anyway |
| <a id="struct-construction-in-a-condition"></a>Struct construction in a condition | In the head of an `if`, `while` and `for`, `{` starts the block; struct construction there needs parentheses: `if p == (Point { x = 1 }) {`. Everywhere else without parentheses | Rust's rule. `if x == Node { ... } {` cannot be told apart otherwise. Cost: two parentheses in a rare case |
| <a id="name-clashes"></a>Name clashes | A method and a field of the same struct cannot share a name. A function cannot have the name of a type | A name on a struct should mean one thing. `Stack(...)` always means `Stack.create(...)`. Approved on 12 November |
| <a id="name-f"></a>`Name.f()` | A variable called `Name` wins over a type called `Name` | The nearer name wins, as everywhere else. Approved on 12 November |
| <a id="for-over-what-try-opens-compiled"></a>`for` over what `try` opens, compiled | The collection is computed once before the first round, so the `try` leaves the function there as at the start of any statement. Approved on 15 November 2026 (choice 584) | |
| <a id="a-variable-nothing-reads-as-built"></a>A variable nothing reads, as built | One never used and one only written are errors at the name, the second with its first write; a write through a borrow, `shared`, `weak`, raw memory or a slice is a use, through a `T*` it is not. A parameter is not looked at, nor a `var` of a `Disposable` type, of a struct with one in its fields, or a `shared` owner of one (changed in the slice: decided for a `Disposable` type alone). The names of `for`, of patterns and of `as` and `lock` blocks are held to it (the last two added in the slice), the hint the pattern written again with `_`; a write to a copy of a struct has the borrow as its hint. Approved on 15 November 2026 (choices 588 to 592) | |
| <a id="a-name-that-hides-another"></a>A name that hides another | A local variable, the name of a `for`, of a `match` arm or of an `is` (also one seen after its `if` or `while`) may not take the name of a local variable or a parameter of a block around it that is still open: `var x = 1` and, in a block inside, `var x = 2` is a compile error, as in C# (CS0136), not a second variable as in Rust; so is a local of the function's body with the name of a parameter. The error points at both and says to give the new variable another name. Blocks side by side may use one name (two `for i`, the arms of one `match`), and so may the code after a block has ended, since a name's scope starts where it is declared: that much is looser than C#, whose scope is the whole block. `_` is not a name. A field is never hidden, since it is reached only through `this`; the names of functions, types and modules are not part of the rule. It is a check of the checker alone. *Decided on 17 November 2026, during the ninety-first slice; built in the ninety-second, its details decided before it (choices 886 to 894) and approved on 17 November 2026* | "Caught when compiled": a name that means two things in one function is a mistake waiting to happen, and Rust's shadowing is mostly for changing a type, which SG writes with a new name. The rule found three in the repository's own code, one a parameter of the language's own module |
| <a id="the-rule-built-and-followed-in-c"></a>The rule, built and followed in C | The checker notes what each name stands for, and `unread.rs` tells reads from writes after every other check, so it never hides another error; a use found another way counts for every variable of that name before it, so a read is never missed. Compiled code no longer marks these names used (`for _` and parameters keep it), and the C compiler's warnings check the rule again. Approved on 15 November 2026 (choices 593 to 596) | |
| <a id="every-value-of-a-call"></a>Every value of a call | *Decided on 16 November 2026, in the seventy-seventh slice (choices 614 to 616), and approved.* A call that gives a value is a compile error when the value is not used: a function or a method of your own, one of the language's own module, a built-in method and a function of C alike, and the value after `try` and `await` too. `xs.removeLast()`, `seen.add(x)`, `try cmd.status()` and `noisy(4)` alone are errors; `_ = xs.removeLast()` drops a value on purpose, where the reader sees it. It replaces ["Methods that change and give"](#methods-that-change-and-give) and ["Functions of your own"](#functions-of-your-own): there is no list of calls that may stand alone | Zig refuses every value thrown away the same way; Rust warns only on what is marked `#[must_use]`. No cost at run time |
| <a id="question-colon"></a>`?:` | `c ? a : b` is `a` where `c` holds and `b` otherwise; only the arm chosen runs, and `if` stays a statement. The condition is a `bool`. The arms have one type, as the arms of a `match`; an arm that is only a number or `null` takes the type of the other one, `null` making it a `T?`, and a borrow of a `Copyable` value gives the value, as with `??`. As in an `if`, the first arm sees the names of an `is` in the condition and what it narrows (`p is not null ? p.x : 0`, `r is Ok(v) ? v : 0`), the second the names of an `is not`. It binds more loosely than any other operator, `??` too (`a ?? b ? c : d` is `(a ?? b) ? c : d`), and groups to the right (`a ? 1 : b ? 2 : 3`). It is not a statement, an arm that gives nothing is an error, and an arm cannot `return`. Inside `{ }` of `$"..."` it is written in parentheses. Choices 1910-1916, approved on 25 November 2026 with the hundred-and-eighty-third slice | C#'s operator, with C#'s order and grouping, and its rule for `$"{(c ? a : b)}"`, where a `:` starts the format. A value picked by a condition otherwise took a `match` on `true` and `false` or a variable assigned in an `if`. Rust's `if` that gives a value was the other way; `?:` was asked for, and it leaves `if` as it is. The names and the narrowing follow the `if`, so that `p is not null ? p.x : 0` reads as it would there. A `return` in an arm would hide an exit in the middle of a line; `??` already holds the one place it reads well. Cost at run time: none, it is an `if` |
| <a id="question-colon-as-built"></a>`?:`, as built | The checker checks it as `if c { a } else { b }`: the scope of the condition is the first arm's, the moves of the arms are joined, and an arm that never gives a value (`panic(...)`) does not reach what comes after. A value that borrows carries the borrows of the names of the condition, as a `match` carries those of its subject: after `var t = r is Ok(s) ? s : "none"`, `r` stays lent while `t` is used. Compiled, it is written as the `if` it is, before the statement, and gives its value through a name, as a `match` inside an expression does; in a declaration, an assignment, a `return` or the last line of an arm of a `match` it writes straight into the place, and a chain becomes `if ... else if ...`. A line ending in `?` or `:` goes on on the next one; one that starts with either is an error whose hint moves it. Built on 25 November 2026, in the hundred-and-eighty-third slice | The C compiler makes the same code of the `if` as of C's `?:`. Writing it as a statement keeps the order of evaluation and lets an arm hold what needs lines of its own (a `try`, a text made for the value) |
