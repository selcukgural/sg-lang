| Topic | Decision | Reason |
|---|---|---|
| <a id="array"></a>Array | Slice (pointer + length), bounds check panics | |
| <a id="type-of-an-index"></a>Type of an index | An index and the ends of a range take any integer that widens to `nint` (`byte`, `int`, `nint`). A `long` is converted with `(nint)` | The widening rule as it is; no special case for indexes |
| <a id="backwards-range"></a>Backwards range | `text[3..1]` panics, it is not an empty text | Rust. A range that ends before it starts is a mistake in the data, not a request for nothing |
| <a id="a-range-is-written-bare"></a>A range is written bare | `text[a..b]` is a `read string` on its own. `read text[a..b]` is a compile error whose hint is the bare form. `read items[0]` stays: it lends one element | One way to write it; the range already says "a window". Decided on 12 November |
| <a id="built-in-collections"></a>Built-in collections | `List<T>`, `HashMap<K, V>` and `HashSet<T>` are known to the compiler, like `Result<T, E>`; there are no generics of your own for now. A key of a map and an item of a set is `Equatable` and `Hashable`: an integer, a `bool`, a `string`, or a type of your own written with both. `List<int>(` and `List<int> {` start a value, so `a < b > (c)` is read as a type (C#'s rule), and in a condition the braces need parentheses | Go's old way; the generics question stays open |
| <a id="reading-an-item"></a>Reading an item | `xs[i]` lends an item that cannot be copied: `names[0]` is a `read string`; an item is never moved out through an index (the hints are `.clone()`, `read`, `replace`). A copyable item is the value itself | Follows from `at` returning `read T`. In Rust `v[0]` cannot move a `String` either, and `&v[0]` is written; here the `read` comes on its own |
| <a id="list-and-set-methods"></a>List and set methods | `removeLast()` gives a `T?`, `null` for an empty list. `xs.get(i)` gives a `read T?`, and `xs.get(i) ?? 0` is the value when it can be copied. `xs.indexOf(v)` gives a `nint?`. `set.remove(v)` gives a `bool`. `for x in ref set` is a compile error | Rust's `pop`, `get` and `position`. An item of a set changed in place would sit under the wrong value |
| <a id="looking-a-key-up"></a>Looking a key up | A method that only looks a key up takes text as `read string`: `ages.get(read name)`, a literal as it is; a number or a `bool` by value. `add` takes the key itself | The existing rule for passing a `string` where a `read string` is expected; without `read` the call would read as a move. Rust writes `map.get(&name)` |
| <a id="equality-of-collections"></a>Equality of collections | A collection is `Equatable` if what it holds is: a `List` with the same items in the same order, a `HashSet` with the same items, a `HashMap` with the same keys and equal values (order does not count for the last two). A struct that holds one is `Equatable` field by field. A collection is not `Hashable` and not `Comparable`. Decided on 12 November | The same pattern as `Copyable` on a generic type and as the text of a collection; no new concept. Rust does the same for `==`; C# compares identity (the trap we ruled out), Go refuses. Not a key and no `<`: rarely needed, easy to add later, and an order is written, not made up |
| <a id="text-of-a-collection"></a>Text of a collection | A collection is written as text if its items are: `[1, 2, 3]`, `{"ada": 36}`, `{1, 2, 3}`; text inside is in quotes. A struct that holds one can be `Formattable` without its own `format` | One rule less, and it is what is wanted while looking for a mistake. Go prints a slice too; Rust needs `{:?}`, C# prints the type name |
| <a id="a-collection-inside-its-own-for"></a>A collection inside its own `for` | The compile error of the ["`for` and ownership"](ownership.md#for-and-ownership) row covers: a changing method, `xs[i] = v`, `xs = ...`, `ref xs`, moving `xs`, and a `ref this` method on what holds it. Looking, and changing other fields, is allowed. Pointing a `read` variable elsewhere is not a change | The same as Rust. The hint: go over the positions, or keep the changes until the loop ends |
| <a id="collection-initialisation"></a>Collection initialisation | `List<int> { 1, 2 }`, `HashMap<string, int> { {"x", 10} }`. Each item is an `add` call, and `reserve(n)` is called first. `HashMap()` and `add` are valid too | As in C#, works without macros, and user collections benefit as well |
| <a id="index"></a>Index | `xs[i]` is short for the call `xs.at(i)` when reading and `xs.refAt(i)` when writing | The `T(args)` pattern. No general operator definition is needed, and user collections benefit as well |
| <a id="length"></a>`length` | A method everywhere: `xs.length()`, `text.length()` | Since a `public` field can be written from outside, `xs.length = 100` would corrupt the list |
| <a id="hashmap-getoradd"></a>`HashMap.getOrAdd` | `map.getOrAdd(key, initial)` returns `ref V` and copies the key only if it is missing | One hash, one `clone`. `counts[k] += 1` panics if the key is missing. `counts.getOrAdd(k, 0) += 1` is not taken, since the left side of an assignment is a variable, a field or an item; the hint writes it through a name, `var slot = counts.getOrAdd(k, 0)`, then `slot += 1` (19 November, 1402) |
| <a id="hashmap-add-and-map-key-value"></a>`HashMap.add` and `map[key] = value` | `map.add(key, value)` panics if the key is already there, also inside `HashMap<K, V> { ... }`. `map[key] = value` writes only under a key that is there and panics otherwise, like `map[key]` and `map[key] += 1`. "Put or overwrite" has no notation of its own: it is written with `contains` or `getOrAdd`. Decided on 12 November | Core principle: neither a silent overwrite nor a key that appears silently. C#'s `Add` throws too, but its `map[key] = value` inserts; Rust's `insert` overwrites and returns the old value |
| <a id="hashset-add"></a>`HashSet.add` | `set.add(value)` gives a `bool`: `true` if the item was added, `false` if it was already there. It does not panic. Decided on 12 November | C# and Rust agree. Unlike a key in a map, adding what is already in a set is ordinary use (`if !seen.add(id) { continue }`) |
| <a id="order-of-a-hashmap"></a>Order of a `HashMap` | The language promises no order, and neither the interpreter nor compiled code gives one: a `HashMap` and a `HashSet` are hash tables, gone over in whatever order the table has, as in Rust. Changed on 12 November (until then the interpreter went over the entries in the order of their keys, for the golden tests). Since the twenty-fourth slice both build the same table (entries one after the other, a removed one replaced by the last), so a program prints the same in both; what falls out is the order of adding until something is removed, and it is not promised | A sorted structure would make every lookup slower to give an order nobody was promised. A program that needs an order sorts the keys |
| <a id="list-in-compiled-code"></a>`List` in compiled code | A `List<T>` is a pointer to its items, a length and a capacity; an empty list has no block, a full one gets room for twice as many. `xs[i]` is the item where it is, and the index is checked in every build. A `for` over a list that is handed over gives each item to its round, and leaving early frees the items not reached; over `read xs` / `ref xs` the name points at the item. `xs.get(i)` is a look at the item or `null`. Limits of the back end for now: `get` cannot stand on the right of `??` (on the right of `&&` and `||` it can since the twenty-fifth slice); `indexOf`, `contains` and `sort` are compiled for integers, `bool` and text (`sort` is the C library's `qsort`, which does not keep equal items in order; that cannot be seen for these types). Decided on 12 November | Rust's `Vec<T>` is the same three words. The index check is what keeps memory safe; in `for i in 0..xs.length()` the C compiler removes it. The list benchmark runs in 1.02 times the time of C |
| <a id="a-list-made-at-its-size"></a>A list made at its size | `List<T>.repeat(item, count)` gives `count` copies of a `Copyable` item in one block, and `List<T>.withCapacity(count)` an empty list with room for `count` items; fewer than 0 is a panic in both, and memory that cannot be had a panic that says so. In compiled code an item whose bytes are all zero is given by `calloc`, which hands fresh pages over without writing them; another is written into each place. `xs.repeat`, `xs.reserve` and their kin on a list are errors that point at the type. Approved on 21 November 2026, in the hundred-and-fiftieth slice (choices 1648, 1652), found by measuring `std`: the compressor built its tables of 64 KB by adding 4 KB at a time, and the zip reader its list of entries by doubling | Rust's `vec![x; n]` (zeroed by `calloc` too) and `Vec::with_capacity(n)`; Go's `make([]T, n, c)`. A buffer of a size known when the program runs had no way to be made but item by item |
| <a id="hashmap-and-hashset-in-compiled-code"></a>`HashMap` and `HashSet` in compiled code | Both are hash tables: the entries lie one after the other in one block, and a block of 32-bit slots says which entry a hash points at (open addressing, at most three quarters full); a removed entry is replaced by the last one. `map[key]` is the value where it is and a missing key stops the program; `get` is a look or `null`; `getOrAdd` copies the key only when it adds it; `remove` gives the value back. A `for` over a table that is handed over gives each entry to its round, and leaving early frees the rest. Keys are numbers, `bool`, text and `: Hashable` structs and enums. The hash has a secret key drawn from the system when the program starts (SipHash-1-3), so keys chosen by someone else cannot all be made to collide; this stays the default although it is not a memory-safety check, and a plain hash can be offered by name later. A table holds at most about two thousand million entries. Limit of the back end for now: `getOrAdd` with a key that owns memory other than text. Decided on 13 November | The default is the one that cannot go wrong. Rust's `HashMap` has the same keyed hash and pays the same: the table benchmark runs in 1.20 times the time of C, 0.99 with C's plain hash. Rust mixes the order of a table on purpose; this one, like C#'s `Dictionary`, does not |
| <a id="collection-names"></a>Collection names | `HashMap<K, V>`, `HashSet<T>` (the Rust names; C# says `HashSet` too). `List<T>` stays. The old spelling was `Map`, changed on 11 November | The target audience comes from Rust. The name says that order is not guaranteed, and when an ordered version arrives the difference can be read from the name. `Vec` says nothing to a C# reader, `List` is clear to both sides |
| <a id="slice-type"></a>Slice type | `read T[]` is a readable window, `ref T[]` a writable one: pointer + length. A bare `T[]` is not a type, compile error; the hint is `List<T>` for an owner and `read T[]` for a window. What `read string` is for text, `read byte[]` is for raw data. Conversion to a slice: `read xs` and `ref xs` give a slice where a slice is expected (`parse(read buffer)`), for `List<T>` and `T[N]`; passing it without writing `read` is a compile error, and the hint is `read xs`. `xs[..]` stays valid as range notation | Rust's `&[T]` and `&mut [T]` types, in our notation. No new name is needed, `read` and `ref` are enough. In C# `T[]` is an owning array on the heap, here it is not: the same name, a different meaning, and the error hint says so. Conversion to a slice is the same rule as `string` → `read string`, and in Rust `&buf` works this way too. The first decision was `xs[..]` only; it made people memorise a separate notation for lists, and it changed on 11 November |
| <a id="range"></a>Range | In the `a..b` notation the ends can be left out: `data[..end]` from the start, `data[start..]` to the end, `data[..]` the whole. The same on `string`, `List<T>` and slices | The same as Rust and C#. `data[0..end]` and `line[i..line.length()]` were noise, and no new concept is needed |
| <a id="fixed-size-array"></a>Fixed-size array | `T[N]`, where `N` is an integer constant: `int[8] values`. It is a value and stays where it is (on the stack or inside the struct), no heap. `length()` is known at compile time. `xs[i]` is bounds checked; if the index is known at compile time and out of bounds it is a compile error, and if it depends on data it panics. Construction: `int[3] { 1, 2, 3 }` writes the items (a compile error if the count does not match), `byte[16](../255)` puts the same value in every item (`T` must be `Copyable`), and `byte[16]` alone fills with zero; a zero value exists only for numbers, `bool` (`false`) and `T?` (`null`), and for any other type it is a compile error. There is no uninitialised memory. If `T` is `Copyable` the array is `Copyable` too, otherwise it is moved (the struct rule). Conversion to a slice is in the ["Slice type"](#slice-type) row | Rust's `[T; N]` type, in our notation. C# has no natural counterpart (`stackalloc` only in locals, `fixed` only in `unsafe`). Without this every buffer goes to the heap through `List`, and C-level performance does not hold. For construction Rust writes `[1, 2, 3]` and `[255; 16]` and has no short form for zero; in C# `new byte[16]` is always zero, and the short form comes from there. Cost: `T[]` (a slice, needs `read`/`ref`) and `T[N]` (a value) look alike; a large array passed by value is copied silently; the cost of zeroing |
| <a id="a-range-that-is-written-through"></a>A range that is written through | `xs[a..b]` on a list, an array or a slice is a `read T[]`: it only looks, as a range of text does. `ref xs[a..b]` is a `ref T[]` and needs what `ref xs` needs. `read xs[a..b]` is a compile error whose hint is the bare range. A `for` over a slice lends its items; a list cannot be changed inside a `for` over a range of it | Rust writes `&mut xs[a..b]`. One rule for every range: bare means "look", and the one word that asks for more is `ref`. Approved on 13 November 2026 |
| <a id="arrays-and-slices-details"></a>Arrays and slices, details | `T[0]` is a compile error. `byte[16]` alone builds an array when `byte` names a type and no variable has that name; in a condition `int[3] { ... }` needs parentheses, like a struct literal. An array and a slice have the methods of a list that only look (`length`, `get`, `indexOf`, `contains`), and `sort` and `reverse` since the forty-second slice (["`sort` and `reverse` on a slice"](#sort-and-reverse-on-a-slice)); `==` compares the items in order when they are `Equatable`; `print` writes `[1, 2, 3]`. Only an index on an array is checked at compile time; the ends of a range and an index on a slice panic. Put off: an array of arrays, `read T[]?`, an array as a key | An array without items has no use and no natural form in C. The rest follows what `List` already does, so nothing new has to be learned. Approved on 13 November 2026 |
| <a id="arrays-and-slices-in-compiled-code"></a>Arrays and slices in compiled code | An array `T[N]` is a C array inside a struct: it lies where its variable or its field lies, nothing is allocated for it, and passing, returning or assigning it copies its items; `length()` is a constant. A slice is a pointer and a count, one C type for `read T[]` and `ref T[]`. `text.asBytes()` and `string.fromUtf8` copy nothing. A range checks its two ends once, and an index into the window is checked against the window's own count, in every build. An array whose items own something is freed item by item, and moving it empties every item. The success of a `Result` can be a `read string`, a slice or a `read` of a struct, an enum or a collection; a `read T?` as the success is not compiled yet, nor is a `for` that is handed an array behind a pointer | What C does by hand, with the checks the checker cannot do before the program runs. Measured: a buffer on the stack and slices onto it take the time of the same program in C (`buffer`, 0.99); there the C compiler could remove every check, and where a length is not known a check is one comparison that is never taken. Approved on 13 November 2026 |
| <a id="a-range-with-an-end-outside"></a>A range with an end outside | A range with an end that lies outside the items panics with "range 4..3 is out of range: the length is 3", for text and for items, in the interpreter and in compiled code. "ends before it starts" is left for a range whose two ends are both inside (`xs[2..1]`) | `xs[4..]` on three items used to say "ends before it starts", which sends the reader to the wrong end. Approved on 13 November 2026 |
| <a id="an-index-stays-a-nint"></a>An index stays a `nint` | `uint`, `nuint` and `ulong` are not `nint`s on their own, so an index of those types needs `(nint)`. Approved on 13 November | Follows from ["Mixing integer types"](numbers.md#mixing-integer-types): a `uint` does not fit in a 32-bit `nint`. Rust indexes with `usize` only |
| <a id="addall"></a>`addAll` | `list.addAll(items)` copies the items of a `read T[]` to the end of the list: `read ys` for a list or an array, a range (`ys[2..]`), `text.asBytes()`. The items must be `Copyable`; on a `List<string>` it is an error whose hint is `add(item.clone())`. Other languages' names (`extend`, `addRange`, `extendFromSlice`, ...) are errors whose hint is `addAll`. Approved on 14 November 2026 | The design's name, already in the HTTP example (05); Java and Kotlin call it the same. A copy of `Copyable` items is a copy of their bytes, so the call is one `memcpy`; for text it would be an allocation per item that the call does not show. Moving every item of one list into another is a method of its own, not here yet |
| <a id="a-list-is-not-added-to-itself"></a>A list is not added to itself | `xs.addAll(read xs)` and `xs.addAll(xs[1..])` are compile errors; the hint is `xs.add(xs[i])`. Approved on 14 November 2026 | The rule of a text written into itself: the list may move to a larger block while it grows, and the items would be read from the old one. Rust refuses the same and has `extend_from_within`, which can come when a program needs it |
| <a id="sort-and-reverse-on-a-slice"></a>`sort` and `reverse` on a slice | An array and a `ref T[]` have `sort` and `reverse`; the items change places where they are, in the list or the array the slice looks at. Through a `read T[]` it is an error whose hint is `ref xs`. The sort is the list's: stable, and in compiled code it takes a block of the slice's size from the heap while it sorts. Approved on 14 November 2026 *(18 November 2026, choice 1337: the interpreter sorts with the merge sort of compiled code, step for step, so a `compare` that gives no single order leaves the same items in the same places in both, and panics in neither; 24 November 2026, slice 166: both merge the runs the items already make, a run strictly in the reverse order turned round and a short one made 32 long, still step for step)* | They change the order and not the number of items, which a window can do and `add` or `clear` cannot. A sort that does not allocate can come when a measurement asks for it |
| <a id="a-range-in-front-of-sort"></a>A range in front of `sort` | `xs[2..5].sort()` and `xs[..3].reverse()` lend the range as `ref`, with what `ref xs[2..5]` needs (written, not `readonly`, not borrowed, not gone over by a `for`). A bare range anywhere else only looks. Approved on 14 November 2026 | A variable in front of a method is lent as the method needs with nothing written (`xs.sort()`), and the range follows that rule; `(ref xs[2..5]).sort()` would need brackets. Rust writes `xs[2..5].sort()` too |
| <a id="addall-and-slice-sorting-in-compiled-code"></a>`addAll` and slice sorting in compiled code | `addAll` tests for room once, grows the block to twice its room or to what is needed, and copies with `memcpy`; `sort` on a slice is the list's merge sort on the slice's pointer and count, `reverse` swaps from both ends. Measured with `blocks`: a gigabyte gathered in pieces of 1 to 255 bytes takes the time of `memcpy` in C (1.00); one `add` per byte takes ten times as long. Approved on 14 November 2026 | What C does by hand |
| <a id="copyfrom"></a>`copyFrom` | `dst.copyFrom(src)` copies the items of a `read T[]` over as many: `dst` is a list, an array, a `ref T[]` or a range in front of it (`buf[0..n].copyFrom(...)`, lent as `ref` as in front of `sort`), the items `Copyable`. Lengths that differ are a panic (`` `copyFrom` is given 2 item(s) to copy over 3 ``). The two may be windows of one place (`buf[0..n].copyFrom(buf[k..k + n])`): the items given are read before any is written over, as C's `memmove`, the one exception to "a `ref` borrow is the only one", since `Copyable` items hold nothing a write could free (1609). `copyFromSlice` and `copy_from_slice` are errors whose hint is `copyFrom`. Compiled as a test of the lengths and one `memmove`. The loops of `std` that copied item by item (deflate's window and input, inflate's output, the slots of the Pike machine, SHA-256's block, the groups of an IPv6 address) are calls of it. Approved on 20 and 21 November 2026 (1597, 1609) | Rust's `copy_from_slice` panics on lengths that differ and `copy_within` copies inside one slice; Zig's `@memcpy` checks the lengths and refuses overlap, `@memmove` allows it; Go's `copy` copies the shorter length and allows overlap. One method that allows overlap keeps the language one name smaller than Rust and Zig, and a count that differs is a mistake Go would hide |
| <a id="an-index-written-a-c"></a>An index written `a + c` | In a checked build, an index of a list, an array, a slice or a text, or an end of a range, written `a + c` (or `c + a`) with `c` a constant and the sum signed, is tested for overflow with the place: the sum wraps, one that overflowed is negative and the check of the place refuses it, and only then is the overflow told, with the message, the numbers and the line the test of the sum gave. The program stops where and as it did; nothing a program can see changes, and a release build is as before. Approved on 14 November 2026 | One comparison where there were two; XXH64's checked build went from 0.154 s to 0.129 s, the time of its release build |
| <a id="what-keeps-its-test"></a>What keeps its test | `xs[i - 1]` (a difference that overflows wraps to a large positive number, refused only while no length nears 2^63: a fact about machines, not a promise of the language), `a + b` with two variables, an unsigned index (it wraps to a small number), `i * 2`, and a sum that is not the place itself (handed to a function, compared). Approved on 14 November 2026 | Measured: those cost nothing in `hash`. The checked `buffer` and `vector` pay for the tests of a sum kept in a loop (`sum += b`), which are real; the "Slower than C" list keeps them |
| <a id="the-start-of-a-range"></a>The start of a range | The overflow of the start is found after the end is computed, so the start is tested with the range only where the end can neither stop the program nor do anything else: a constant, a variable, a field, or such a value plus a constant (`xs[at + 1..at + 3]`: both sums with the range, the start's overflow told first). `xs[at + 1..loud(2)]` keeps the test of its start. Approved on 14 November 2026 | Keeps the order of evaluation: nothing prints before the overflow is told |
| <a id="index-sums-in-compiled-code"></a>Index sums in compiled code | Each such place has a `static const sg_sum` (the constant, the type, the line of the sum) and calls the helper it called with one pointer more (`sg_ats_...`, `sg_cuts_...`, `sg_slices`); the pointer is read only on the way out, where `a` is the wrapped sum less `c` in the type of the sum. Approved on 14 November 2026 | Fifteen tests, each its own process, compare the interpreter and compiled code, also under the sanitizers |
| <a id="a-sum-kept-in-a-loop"></a>A sum kept in a loop | In a checked build, before a loop that adds to a sum starts, compiled code works out from the sum's value how many rounds cannot overflow it (the room to each end of its type divided by the most a round adds or takes). | <a id="searching-items-in-order"></a>Searching items in order | *Decided on 18 November 2026, before the hundred-and-eleventh slice (choices 1249 to 1254).* On a list, an array, a slice and a range in front of them (whose places are counted from its start), of `Comparable` items, as `sort` asks: `xs.binarySearch(v)` gives a `nint?`, the place or `null`, as `indexOf` does, and of equal items always the first, so on items in order it gives what `indexOf` gives; `xs.lowerBound(v)` gives the first place whose item is not less than `v`, `xs.upperBound(v)` the first whose item is greater, both a `nint`.
