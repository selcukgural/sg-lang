| Topic | Decision | Reason |
|---|---|---|
| <a id="match"></a>`match` | `match x { Circle(r) => ... }`, as an expression or a statement. A missing variant is a compile error. Short names in patterns | When a new variant is added, every place that needs a look gives an error |
| <a id="patterns"></a>Patterns | `_` catches everything, `var other` also takes the value, an unknown bare name is an error. The condition is `when` *(28 November 2026, choice 2210: `when` is a word only after the pattern of an arm and after what a `lock` holds, and `not` only right after `is`; elsewhere both are names, `var when = DateTime.fromUnixSeconds(0)`, as `alias` is (1919). `or` stays a keyword)* | A mistyped name should not silently become "catch everything" |
| <a id="match-and-ownership"></a>`match` and ownership | `match x` behaves like `var y = x`: it moves if `x` is an owner, `match read x` and `match ref x` borrow, and if `x` is already a borrow it gives the same kind of borrow | No new rule |
| <a id="testing-a-single-variant"></a>Testing a single variant | `if s is Circle(r) { }`, the same word as `is null` | The counterpart of Rust's `if let` |
| <a id="is-and-ownership"></a>`is` and ownership | `x is Circle(r)` only looks: it never moves `x`. The names are `read` borrows, or `ref` borrows when `x` is a `ref` borrow or the test is written `ref x is Circle(r)`. To take the values out, `match` | `is null` already only looks, and a test that uses its subject up would surprise. Rust's `if let` moves; we differ on purpose |
| <a id="pattern-shape"></a>Pattern shape | A pattern names or skips every value: `Rect(w, _)`. A bare `Rect` for a variant that carries data is a compile error | One way to write it; adding a field to a variant shows every pattern that needs a look |
| <a id="unreachable-arm"></a>Unreachable arm | An arm that can never run (its variant is handled above, or an arm above takes every value) is a compile error | Rust warns; there are no warnings here |
| <a id="arm-of-a-statement-match"></a>Arm of a statement `match` | Follows the statement rule: a call, an assignment (`Circle(r) => r += 1`), `return`/`break`/`continue`, or a block. `Circle(r) => r * 2` is "the value is not used". `Empty => {}` does nothing | No new rule |
| <a id="separators-in-enum-and-match"></a>Separators in `enum` and `match` | Variants and arms are separated by line ends, never commas | The line-end rule; one way to write it |
| <a id="match-is-and-t"></a>`match`, `is` and `T*` | Both look through `T*`, like field access. `var other` gets the value as it was given (the `T*` itself) | No new rule |
| <a id="match-on-a-number"></a>`match` on a number | Patterns are numbers and characters, `_` and `var name`. `_` or `var name` is required, even when all 256 values of a `byte` are listed. The same number twice, or a number that does not fit the type, is a compile error. Changed in the forty-fourth slice (14 November 2026): the check counts, so arms that take every value (ranges `0..=127` and `128..=255` on a `byte`, or all 256 numbers) need no `_`, an `_` below them can never run, and a `match` that misses values names them | The check does not count values: one simple rule. An arm that can never run is an error, as for enums. With ranges that rule would have required an `_` that can never run; the search that counts already ran for patterns inside patterns |
| <a id="when-only-looks"></a>`when` only looks | The condition of a `match` arm (`when`) cannot move a value; it reads, or lends with `read`. If it could move a value and then not hold, the arms below would run without it. Decided on 12 November | Rust has the same rule. No cost at run time, one rule, and compiled code can then fill in the names of an arm before its condition is known |
| <a id="patterns-inside-patterns"></a>Patterns inside patterns | Inside the parentheses of a variant goes a pattern where a name goes: a variant with its own parentheses (`Add(Number(0), right)`), a variant that carries nothing (`Paint(Red)`), a number, a character, a text (`Word("let")`), `_` or a name, at any depth, in `match` and in `is`, through a `T*` too. An arm with a pattern inside does not settle its variant: the arms below still run for its other values. Ownership is the rule of `match`: on an owned value the names take what they name, what no name takes is dropped and a box that was looked into is given back; on a borrowed value the names borrow, and through a `read` field they are `read`. No pattern inside a value that may be `null` (that came in the forty-fourth slice: ["`null` as a pattern"](#null-as-a-pattern)). Approved on 14 November 2026 | They cost nothing at run time: an arm tests what a person would test by hand. This takes up "nested patterns" from the things left for after the first version. C#, Rust and Swift have them |
| <a id="a-name-alone-inside-the-parentheses"></a>A name alone inside the parentheses | It is the variant when the enum of that value has a variant of that name, otherwise a name that takes the value. A name that starts with a capital letter and is not a variant there is an error (`Paint(Rd)`: hint `Red`). `var` is not written inside the parentheses. Approved on 14 November 2026 | A mistyped variant must not quietly take every value (the row ["Patterns"](#patterns)). Variants begin with a capital letter and names with a small one; the rule leans on that only here. Rust has the same question and answers it with a warning |
| <a id="what-a-match-misses"></a>What a `match` misses | With patterns inside, a `match` that does not take every value is a compile error that names one it misses (`does not handle Add(Name(_), _)`), and an arm the arms above take together is an error too. Without patterns inside the messages stay as they were. An arm with `when` takes nothing for this. Approved on 14 November 2026 | The row ["`match`"](#match): a new variant shows every place that needs a look; with patterns inside the value that is missing is named, not only the variant. The search is Maranget's, the one Rust uses, and runs in the checker only |
| <a id="match-on-text"></a>`match` on text | On a `string`, a `read string` and a `ref string`: the arms are texts as they are written, `_` and `var name`; `_` or `var name` is required and the same text twice is an error, as on a number. `$"..."` is not a pattern. A `match` on an owned `string` moves it, as every `match` does (`match read text` keeps it). Approved on 14 November 2026 | A lexer or a command line sorts words this way; a chain of `==` says the same at more length. No new rule for ownership |
| <a id="patterns-and-enum-methods-in-compiled-code"></a>Patterns and enum methods in compiled code | An arm with patterns inside is one condition: the tests of the tags and the values joined by `&&` in the order they are written, so a value is read only after the tag of its variant was tested; each arm tests from the top. A text arm is a test of the length and then of the bytes. A method of an enum is a C function like a struct's, and the helpers that write, compare and order an enum call its own methods. Measured with `keywords`: a million words sorted forty times by a `match` with twelve texts take 1.03 times a chain of `memcmp` in C. Approved on 14 November 2026 | What C does by hand. A decision tree, or a switch on the length of a text, can come if a measurement asks for it |
| <a id="ranges-in-patterns"></a>Ranges in patterns | `'a'..='z'`, `0..=9`, `-5..=-1`: from the first value to the last, both taken, on an integer and on a `char`, also inside the parentheses of a variant. `..` in a pattern is an error whose hint is `..=`; `..=` outside a pattern is an error whose hint is `a..b + 1`. The ends are numbers or characters as they are written, the first not greater than the last, each fitting the type; no constant (`int.MaxValue`, refused with "a range in a pattern ends with a number or a character" and a note, 28 November 2026) and no open end (`5..=`). Decided before the forty-fourth slice and approved with it on 14 November 2026 | `..` stops before its end everywhere else (`for i in 0..n`, `text[a..b]`), so `'a'..'z'` would quietly leave out `z`. Rust wrote patterns this way until 1.80 |
| <a id="or-in-patterns"></a>`or` in patterns | `Add(l, _) or Mul(l, _)`, `'+' or '-'`, `Word("if" or "else")`, in an arm and inside the parentheses, in `match` and in `is`. Every pattern of an `or` names the same values with the same types; a pattern that the arms above and the patterns before it take is an error (inside the parentheses that is not looked for yet). A line may end with `or`. `or` is a keyword; `|` or `||` between patterns is an error whose hint is `or`, and `or` between two conditions an error whose hint is the line with `||`. Approved on 14 November 2026 *(28 November 2026, as built, choice 2211: the `when` of an arm whose pattern is an `or` runs once, with the names of the first pattern that fits, and the patterns after it are not tried when it fails, so `Two(x, 1..=9) or Two(1..=9, x) when x > 5` on `Two(2, 7)` goes to the next arm; a pattern that the patterns before it take stays an error with a `when`, since the condition never sees its names)* | C#'s word: SG writes its patterns as C# does (`is not null`), and `|` is an operator on numbers in SG, so a pattern and a value look different (`x is A or B \|\| ready`). First written `|` as in Rust, changed during the slice |
| <a id="null-as-a-pattern"></a>`null` as a pattern | On a `T?`, as a field or as the value of the `match`, `null` takes `null` and any other pattern takes a value that is there and tests it as on a `T` (`Node(null, Leaf(label))`, `match shape { null => ... Circle(r) => ... }`). `null` on a type without `?` is an error. A `match` on a `T?` takes `null` with an arm or with `_`. Approved on 14 November 2026 | Takes away "no pattern inside a value that may be `null`" of the row ["Patterns inside patterns"](#patterns-inside-patterns). C# and Swift test `null` in a pattern too |
| <a id="a-name-below-null"></a>A name below `null` | In a `match` on a `T?`, a name in an arm under an arm `null` without `when` has the type `T` (`match s { null => 0  var text => text.length() }`); above it, or without such an arm, the name is a `T?`. Approved on 14 November 2026. The same one level down (2132, 28 November 2026): below an arm without `when` such as `Go(null, _)` or `Ok(null)`, with `null` in one place of a variant and `_` or names in every other, a name in that place of the same variant is a `T`; `Go(null, 1)` narrows nothing | The same narrowing `if s is not null` gives, and nothing to unwrap by hand |
| <a id="true-and-false-as-patterns"></a>`true` and `false` as patterns | `match done { true => ... false => ... }`, `Flag(true)`; both arms make the `match` whole without `_`. Approved on 14 November 2026 | A `bool` is a type of two values like an enum of two variants |
| <a id="what-the-search-names"></a>What the search names | The search of ["What a `match` misses"](#what-a-match-misses) knows `or`, ranges, `null`, `true` and `false`, and runs for every `match` on a number, a character, a `bool` and a `T?`. The values of a number type are cut where the arms' ranges begin and end, so the search stays small however wide the type. A `match` on a number or a character that misses values says which (`no arm takes 128..=255`; the ends of the wide types by name: `int.MinValue..=-1`). Approved on 14 November 2026 | The value that is missing is named, as for an enum. The row ["`match` on a number"](#match-on-a-number) changed with it: arms that take every value need no `_` |
| <a id="the-rest-of-the-patterns-in-compiled-code"></a>The rest of the patterns in compiled code | A range is `c >= lo && c <= hi`, without the half whose end is the first or the last value of the type; an `or` is `\|\|`; on a `T?` the flag (or the null pointer) is tested before the value. An `or` that names nothing drops an owned value as `_` would; an `or` with names is opened into one pattern for each way to match, the names are declared once, and the way that matched sets them and drops what it leaves. Measured with `classes`: ten million bytes sorted twenty times into the classes of a lexer take 0.87 times a chain of `if`s in C. Approved on 14 November 2026 | What C does by hand. Many `or`s inside one pattern open into their product; no limit is set, as none was needed yet |
| <a id="the-names-of-is-along"></a>The names of `is` along `&&` | An `is` on the left of `&&` names values for its right side and for the block of the `if` or `while` whose condition the chain is: `if int.parse(read text) is Ok(value) && value > 0 { ... }`, `while tokenAt(i) is Word(w) && w.length() > 0 { ... }`. A chain anywhere else (`return s is Circle(r) && r > 10`, a `var`, a `when`, an `assert`, inside `!( ... )`) gives its names to its own right side and ends them with itself. `else` and the code after the `if` do not see them, nor does `\|\|`; `(a && b) && c` is `a && b && c`. Decided before the forty-fifth slice and approved with it on 14 November 2026 | C#'s rule (`if (o is int n && n > 0)`); Rust 2024 chains `if let` with `&&` the same way. Until then the names existed only when the `is` was the whole condition |
| <a id="narrowing-along-and"></a>Narrowing along `&&` and `\|\|` | On the left of `&&`, `x is not null` makes `x` a `T` on the right and in the block; on the left of `\|\|`, `x is null` makes it a `T` on the right. An `if` whose condition is a `\|\|` chain of `is null` tests narrows them in `else`, and after the `if` when the block always leaves (`if a is null \|\| b is null { return }`); a `&&` chain of `is not null` tests narrows them after the `if` when `else` always leaves. Only the parts of the chain itself count, not `!(x is null)` or a test inside the other operator. Approved on 14 November 2026 | The `&&` half was decided before the slice; the `\|\|` half is its mirror image, added during it. C# narrows the same way |
| <a id="no-names-where-nothing-sees-them"></a>No names where nothing sees them | An `is` that names values and is joined by `\|\|` is an error whose note says that the block also runs when the test does not hold; an `is` with names under `!` or as a whole value (`var round = s is Circle(r)`) is an error whose hint is `_` or `match`. A name of an `is` used in `else`, after the `if` or after the chain is an error that points at the `is` that named it and says where its names are seen. Approved on 14 November 2026 | Before, the error said only that the names exist when `is` is the whole condition, and a name used too late got a guess at a near name |
| <a id="chains-in-compiled-code"></a>Chains in compiled code | A chain whose `is` names values declares the names before the statement and sets them inside the condition where the test holds: `(s.tag == 0 && (r = &s.u.v0.m_radius, 1)) && *r > 10`; an `or` with names sets them by the way that matched. A value made by a call at the start of the chain stays until the block is done; an `is` with names on a value made by a call after the first `&&` is refused with "not in the C back end yet" (the interpreter runs it). Narrowing writes nothing new. Approved on 14 November 2026 | One pointer set in the condition, the C a person writes with the same names; not measured on its own |
| <a id="narrowing-under"></a>Narrowing under `!` | A condition is read as a whole: each says which variables are not `null` where it holds and which where it does not. `!` swaps the two, so `if !(x is null)` narrows like `x is not null`; where `a && b` holds both sides held, where it fails only what both sides say when they fail is known, and `\|\|` is the other way round (`!(a is null \|\| b is null)` narrows both, `!(a is null && b is null)` neither). The same reading serves a part of a chain, `else` and the code after an `if` whose branch leaves. Approved on 14 November 2026 | C# reads a condition the same way. Until then `!(x is null)` and a test inside the other operator narrowed nothing. No cost at run time |
| <a id="narrowing-after-a-while"></a>Narrowing after a `while` | A loop ends when its condition fails, so after `while x is null { ... }` the variable is a `T`, and after `while a is null \|\| b is null { ... }` both are; `while x is null && tries < 3` narrows nothing. A `break` that leaves the loop, wherever it stands, turns it off; one of an inner loop does not. A variable left a `T?` by a `break` gets the usual error; a note that names the `break` is not here yet. Approved on 14 November 2026 | C# does the same; Rust has no `null` to narrow |
| <a id="a-variable-the-condition-empties"></a>A variable the condition empties | What a whole condition says (in `else`, after the `if`, after a `while`) leaves out the variables the condition empties with `take` or assigns in a `match` arm: `if b is null \|\| b.take() is null { return }` does not narrow `b`. Along the chain itself `take` already ended the narrowing. Approved on 14 November 2026 | There since the forty-fifth slice: `b` was read as a value after `take` emptied it |
| <a id="the-names-of-is-not"></a>The names of `is not` | The names of `x is not Circle(r)`, and of `!(x is Circle(r))`, are seen where the test fails: on the right of `\|\|`, in `else`, in the second arm of a `?:` (`s is not Rect(w, _) ? 0 : w`), after an `if` whose block leaves (`return`, `break`, `continue`, `panic`, `exit`), and after a `while` that only its test ends: `if int.parse(read text) is not Ok(value) { return -1 }` and then `value`. A `while` with a `break` sees them nowhere, and the error points at the `break`. Approved on 14 November 2026 | C# 9 (`if (o is not int n) return;`); Rust writes it `let ... else`, which moves the value out where `is` only looks. Until then `is not` with names was an error |
| <a id="names-after-an-if-whose-else-leaves"></a>Names after an `if` whose `else` leaves | `if s is Circle(r) { ... } else { return 0 }` and then `r`: the code after the `if` sees what the way that reaches it is sure of, as narrowing already did. Approved on 14 November 2026 | The mirror image of ["The names of `is not`"](#the-names-of-is-not) |
| <a id="names-along"></a>Names along `\|\|` | On the left of `\|\|` an `is not` names values for its right side (`if r is not Ok(n) \|\| n < 0 { return }`); after the `if` the names of every `is not` of the chain are seen. An `is not` with names on the left of `&&` is an error. A `!` around a whole chain is not read for names. Approved on 14 November 2026 | C# also reads `!(a && b)`; left for later |
| <a id="where-the-names-after-a-statement-live"></a>Where the names after a statement live | In the scope that holds the `if` or `while`, to its end, as a `var`; a name already declared in that scope is an error that points at both. They stay borrows of the tested value. Approved on 14 November 2026 | In an inner block a name of a block around them is an error, as it is for a `var` (since 17 November 2026: ["A name that hides another"](statements.md#a-name-that-hides-another)) |
| <a id="a-value-with-no-name-after-an-if"></a>A value with no name after an `if` | The value with no name that such an `if` looks at (`if fetch() is not Text(body) { return }`) stays until the block around the `if` ends; in compiled code its drop moves there. After a `while`, a name that borrows from such a value is an error: the loop makes it again in every round. Approved on 14 November 2026 | What lets `int.parse(read text) is not Ok(value)` be written without a `var` first |
| <a id="names-in-compiled-code"></a>Names in compiled code | `x is not Circle(r)` is the test of `x is Circle(r)` that sets the names, under a `!`; the names are declared before the statement (before the loop for a `while`). A value made by a call after the first `&&` or `\|\|`, for an `is` with names, is compiled when it owns no memory: declared before the statement and made inside the condition. Approved on 14 November 2026 | One that owns memory is still refused ("not in the C back end yet") |
| <a id="take-and-narrowing"></a>`take` and narrowing | `take` on a variable known not to be null ends that knowledge: the variable is `T?` again | `take` puts `null` in its place. Approved on 12 November |
| <a id="assignment-and-narrowing"></a>Assignment and narrowing | An assignment of a value that is never `null` (a `T`) to a narrowed variable keeps the narrowing: after `if count is not null`, `count = 9` leaves it an `int`. A `T?` or `null` ends it. An assignment does not narrow a variable no test narrowed, and a loop that assigns the variable ends what was known before it, as before. 2130, 28 November 2026 (#36) | What C# and Kotlin do; the value assigned says as much as the test did. Before, any assignment ended the narrowing, and the error hinted to test what had just been tested |
