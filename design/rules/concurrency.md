| Topic | Decision | Reason |
|---|---|---|
| <a id="lock"></a>Lock | `locked T` (`Mutex`), access only inside a `lock x as c { }` block *(14 November: where it is written, what a `lock` block may not do and two locks together are in the rows ["Where `locked` is written"](#where-locked-is-written) and ["A `lock` block does not wait"](#a-lock-block-does-not-wait).)* | A two-step operation cannot be left halfway. Since a panic stops the process, there is no poisoning and no `.unwrap()` |
| <a id="thread-rule"></a>Thread rule | An argument to `spawn` cannot carry a borrow, an unlocked `checked` or a `Func`, including one stored in a struct field *(12 November: a `Func` is now only the address of a function and can be passed to `spawn`. 14 November: there is no `spawn`; the rule holds for the arguments of `Task.run` (["Starting a task"](#starting-a-task)), for what a task gives back, and for what a `locked` value holds; a `Task` itself does not go to another task.)* | Since the counter is always atomic, Rust's `Send` and `Sync` distinction comes down to this single rule. `Func` is forbidden because its type does not show what it holds |
| <a id="starting-a-task"></a>Starting a task | `Task.run(work, share counter)` starts a function in parallel and gives a `Task<R>`, `R` being what the function returns. The function and its arguments are given apart, and the arguments are checked against its parameters as in a call; a `Func` can be given too. There is no `spawn` keyword. Approved on 14 November 2026, before the fifty-seventh slice | C#'s way. C# writes `Task.Run(() => Work(counter))` with a lambda, which SG does not have; `Task.run(work(counter))` would read as if `work` ran first and gave its result to `Task.run`, which is the kind of surprise the language avoids |
| <a id="task-r"></a>`Task<R>` | The handle of a task. `t.wait()` waits for it and gives its result, so `try t.wait()` passes on its error; async code will write `await t` (["Async, the direction"](../directions/async.md)). A task may run on a thread of its own or in a pool of threads, and no program can tell which | One handle for threads now and async later, as in C#. The runtime can move from a thread per task to a pool without changing what any program means |
| <a id="every-task-is-waited-for"></a>Every task is waited for | A `Task` that is not waited for on every path is a compile error, as a `Closable` value that is not closed; `Task.run(...)` alone on a line is one too. No task is ever cancelled without being told, by dropping its handle or otherwise. Approved on 14 November 2026, before the fifty-seventh slice | Structured concurrency, as Swift's task groups and Kotlin's `coroutineScope`: no task is left without an owner, no error of one is lost, and no work is cut off when `main` returns. In Rust a future that is dropped stops at any `await` without a word, a source of bugs known as "cancellation safety" |
| <a id="a-task-stays-with-its-starter"></a>A task stays with its starter | A `Task` does not go to another task: it is not an argument of `Task.run`, not what a task gives back, and not held in a `locked` value. Approved on 14 November 2026, before the fifty-seventh slice | Only the task that started one can wait for it, so the waits make a tree and never a circle |
| <a id="a-lock-block-does-not-wait"></a>A `lock` block does not wait | Inside a `lock` block there is no other `lock`, no `wait`, later no `await`, and no call of a function that does one of these, followed through the calls; a call of a `Func` there is refused when it could be such a function. Two values are locked together with `lock a as x, b as y { }`, which takes them in one fixed order (by address); the same value twice is a panic. Approved on 14 November 2026, before the fifty-seventh slice | A task that holds a lock never waits, so it lets the lock go, and with the rule above no circle of waits can form: locks and waits cannot deadlock, and no task can take the same lock twice. C# refuses `await` inside `lock` (CS1996) but lets a lock be taken inside another; Rust allows both. The cost: a lock is not taken inside another, the two are taken together |
| <a id="where-locked-is-written"></a>Where `locked` is written | Like `checked`, only after `shared` or `weak`: `shared locked T`, `weak locked T`; `locked` alone is an error. What it holds follows the thread rule. Approved on 14 November 2026, before the fifty-seventh slice | The same rule as `checked` (["`shared checked` as written"](ownership.md#shared-checked-as-written)); a struct that needs a locked field makes the field `shared locked` |
| <a id="globals-as-decided"></a>Globals, as decided | The language has no variable that lives outside a function and can be assigned freely, and none that each thread has of its own (Rust's `static mut` and `thread_local!`, C's globals and `_Thread_local`), and does not get them. What lives for the whole program is a `static` (["Statics"](types.md#statics)): read only, `atomic` or `locked`, never assigned, and every task reaches it under the thread rule. Approved on 14 November 2026, before the fifty-seventh slice; rewritten with the statics on 17 November 2026 (choice 1088) | A global that any task may assign is a data race the compiler cannot see; one that each thread has of its own does not follow a task, which moves between the threads of a pool, so a task would find another task's value after an `await`. What two tasks share is then in the arguments of `Task.run` or in a static, both of which the thread rule sees, and the owners of a `checked` value stay inside one task, which the compiler can prove. This is what lets a task move between threads in a pool. In Rust a task that holds an `Rc` cannot move (`Send`), because nothing proves the `Rc` stayed inside it |
| <a id="a-panic-in-a-task"></a>A panic in a task | Stops the process, as every panic does (["Panic"](errors.md#panic)). The message says which task and which line; a second panic at the same time does not mix into it, and no other task writes after it. There is no lock poisoning. Approved on 14 November 2026, before the fifty-seventh slice | The other tasks could reach a half-changed state |
| <a id="print-from-several-tasks"></a>`print` from several tasks | Each `print` writes its line whole, so the lines of two tasks never mix; their order is not fixed. Approved on 14 November 2026, before the fifty-seventh slice | The order of two tasks is theirs; a line cut in half is a surprise |
| <a id="the-stack-of-a-task"></a>The stack of a task | 8 MB on every platform, as `main`'s. A system that refuses a new thread is a panic that says so. Approved on 14 November 2026, before the fifty-seventh slice | A thread other than the first has 512 KB on macOS and 8 MB on Linux, so the same recursion would run on one and crash on the other |
| <a id="tasks-in-the-interpreter"></a>Tasks in the interpreter | Each task runs on a thread of the interpreter, but one at a time: they change hands only where one waits (`wait`, a lock held by another; later `await` and channels). What a program prints is the same on every run. Approved on 14 November 2026, before the fifty-seventh slice | The tests are the same on every run, and nothing changes when async and channels come. Compiled code runs the tasks at the same time |
| <a id="a-task-runs-when-it-is-waited-for"></a>A task runs when it is waited for | In the interpreter a task runs when it is waited for, on a thread of its own while the one that waits is blocked, until it ends; `Task.run` only records the function and what it is given, so the starter goes on first. Approved on 14 November 2026 (choice 356) | Which task runs where tasks change hands is the one waited for, so the output is the same on every run and the waits make a tree |
| <a id="an-exit-with-an-error-waits-for-a-task"></a>An exit with an error waits for a task | An exit with an error (`try`, `return Error(...)`) lets a task that is not waited for go: it is waited for there and what it gives is dropped. Every other exit is a compile error (["Every task is waited for"](#every-task-is-waited-for)). Approved on 14 November 2026 (choice 357). *Changed on 22 November 2026, in the hundred-and-fifty-fifth slice (choices 1686, 1691-1695):* the tasks let go are cancelled first, then waited for, as Swift's task groups, Kotlin's `coroutineScope` and Trio's nurseries have it: every wait in them that can say so (the network, files and pipes, other programs, a name looked up, a delay or a channel given a token) ends at once with `Cancelled`, and so does every such wait they start afterwards; a task they await, alone or in `Task.whenAny` and `Task.whenAll`, is let go in turn. Each goes out by its own way of an error. A delay or a channel without a token, work that never waits and a task of `Task.run` held in a call that blocks run on and are waited for. `Task.whenAll` still waits for every task and gives what each gave; `Task.whenAny` with `try` stops at the first error and lets the rest go. A task that waits for what never comes (a listener for a connection no client will make, after the error of a client) held the program for ever before, and when such an error comes depends on the system: the ports a machine has for connections are 16,384 on macOS and about 28,000 on Linux. Each task carries a mark of 4 bytes, and a wait that is not cut takes no lock more | As a `StreamWriter` is let go there: the caller gets the error that made the function stop. Without it `try first.wait()` could not leave `second`, as the examples' two files do |
| <a id="where-a-task-is-kept"></a>Where a `Task` is kept | Only as it is, in a local variable, a parameter or a return value: not in a field, a variant, a collection, a `T?`, a `T*`, a `shared` value, and not behind `read` or `ref`. Approved on 14 November 2026 (choice 358) | Only there can the compiler see it waited for; a list of tasks comes with `Task.whenAll` |
| <a id="wait-takes-the-task"></a>`wait` takes the task | A task is waited for once, and a borrowed one cannot be. What it gives is used or dropped on purpose: `t.wait()` alone is an error when the function returns a value (hint `_ = t.wait()`); a `Task<void>` is waited for alone. Approved on 14 November 2026 (choice 359, changed the same day: first written to let a value go unused) | The rule of the built-in methods that only give a value (["The value of a built-in method"](statements.md#the-value-of-a-built-in-method)) |
| <a id="what-task-run-checks"></a>What `Task.run` checks | The first argument is the name of a function or a `Func` (`Task.run(work(1))` is an error whose hint is `Task.run(work, 1)`); the rest are checked as the arguments of a call, and the thread rule on the types of the function's parameters and on what it returns, naming the field where it is broken. Approved on 14 November 2026 (choice 360) | The type of the function says what crosses, also for a `Func` |
| <a id="the-thread-rule-as-written"></a>The thread rule, as written | A borrow, a slice, a type that carries a borrow, an iterator over a text, a `shared checked` or `weak checked` value and a `Task` do not go to another task, also inside fields, items, `T?`, `T*` and `shared` values. A `Func`, a `StreamReader`, a `StreamWriter` and a plain `shared T` go. Approved on 14 November 2026 (choice 361) | A plain `shared T` is only read and its count is atomic; a stream owns its file |
| <a id="what-a-locked-value-holds"></a>What a `locked` value holds | Follows the thread rule, checked once every type is known, naming the field; `shared checked locked`, `locked` alone, `new locked` and a `locked` around a `Task` are errors. Approved on 14 November 2026 (choice 362) | ["Where `locked` is written"](#where-locked-is-written) |
| <a id="nothing-reached-outside-lock"></a>Nothing reached outside `lock` | What a `locked` value holds is not reached outside a `lock` block, not even read: a field, a method, `for`, `match`, `print`, `==`, `read x` and `read x as` are errors whose hint is `lock`. `share`, `weak`, `same` and `.clone()` work. Approved on 14 November 2026 (choice 363) | They do not touch what it holds |
| <a id="the-lock-block-details"></a>The `lock` block, details | Each name is a `ref T` for the block. The same variable twice is a compile error, the same value through two variables a panic, two names alike an error; a `weak locked` value is locked through `share`, a `shared locked T?` after a test. Approved on 14 November 2026 (choice 364) | ["A `lock` block does not wait"](#a-lock-block-does-not-wait) |
| <a id="what-waits-found-on-the-whole-program"></a>What waits, found on the whole program | After the checker: a function waits when it takes a lock or waits for a task, or calls one that does. A `Func` called in a `lock` block is refused when any function whose address is taken, with as many parameters and the same return type, waits; the error shows the chain of calls. Starting a task in a `lock` block is allowed. Approved on 14 November 2026 (choice 365) | A little wider than "could be such a function", never narrower |
| <a id="a-panic-in-a-task-shown"></a>A panic in a task, shown | Under the message, the line of `Task.run` that started the task; in a test what a task writes with `printError` shows under the test's `FAIL` line. Approved on 14 November 2026 (choice 366). The task named is the innermost one, and a panic that shows a second place of its own (a `checked` conflict) keeps it (choice 372, 15 November) | ["A panic in a task"](#a-panic-in-a-task): which task and which line |
| <a id="a-lock-in-the-interpreter"></a>A lock in the interpreter | No lock is ever held by another task when one is taken, since tasks change hands only at `wait`, which a `lock` block cannot reach; nothing is kept for a lock, and the same value twice is found by comparing the values. A system that refuses a thread is a panic. Approved on 14 November 2026 (choice 367) | Follows from ["Tasks in the interpreter"](#tasks-in-the-interpreter) |
| <a id="lock-and-locked-are-words"></a>`lock` and `locked` are words | They cannot be names, as `shared` and `checked` cannot; `spawn` is a name like any other. Approved on 14 November 2026 (choice 368) | There is no `spawn` |
| <a id="the-leak-report-of-locked"></a>The leak report of `locked` | It covers `locked` values, which are `shared` ones; its hint is `weak locked T?`. Approved on 14 November 2026 (choice 369) | ["`shared` cycle"](ownership.md#shared-cycle) |
| <a id="a-task-is-a-thread-of-the-system"></a>A task is a thread of the system | In compiled code a task is a thread of the system, started by `Task.run` at once, with a stack of 8 MB on every platform. `Task.run` takes one allocation, for the thread, the function, its arguments and what it will return; `wait` joins the thread, takes the value and frees the block. A system that refuses a thread is a panic that says so. Approved on 15 November 2026 (choice 371) | ["Starting a task"](#starting-a-task), ["The stack of a task"](#the-stack-of-a-task); the interpreter runs a task when it is waited for, so its output is the same on every run |
| <a id="a-panic-holds-the-output"></a>A panic holds the output | A panic holds the standard output and the standard error from its first line to the end of the process, so two panics do not mix and nothing is written after one; a line of `print` is one call of the system and comes out whole. Approved on 15 November 2026 (choice 373). A panic in a program whose output was closed early (`program \| head`) is still told and ends the program with 1: compiled code leaves `SIGPIPE` out from the panic's first line, as the interpreter has it (choice 1602, 20 November; it ended by the signal before the message) | ["A panic in a task"](#a-panic-in-a-task); the order of taking the two streams is always the same, so holding them cannot deadlock |
| <a id="a-locked-value-in-compiled-code"></a>A `locked` value in compiled code | A `shared locked` value has a mutex of the system in front of its counts (64 bytes on macOS, 48 on Linux, with the alignment). `lock` takes several values in the order of their addresses and gives them back on every way out of the block (its end, `return`, `break`, `continue`, `try`); one value named twice is the panic of the interpreter. Approved on 15 November 2026 (choice 374) | ["Lock"](#lock); the order of addresses is a second guard beside "a `lock` block does not wait" |
| <a id="standard-streams-from-several-tasks"></a>Standard streams from several tasks | `Stdout`, `Stderr` and `Stdin` are safe from several tasks: a write is put together in a block of the call's own and written with one call of the system, a read takes a lock of the input, and the failure of a stream is kept atomically. Approved on 15 November 2026 (choice 375) | No code of the program runs while a stream is held |
| <a id="memory-kept-by-each-thread"></a>Memory kept by each thread | In a program with tasks the block where printed values are written is one for each thread, given back when a task ends, and the list of `shared` values alive (the leak report of a debug build) is changed under a lock. Approved on 15 November 2026 (choices 376, 377) | The block of one program was a data race between two tasks that print a struct; the thread sanitizer found it |
| <a id="threads-only-where-there-are-tasks"></a>Threads only where there are tasks | A program pays for threads only when it has tasks or `locked` values: only then does its C hold locks, values of each thread and tests of a stream. A task started through a `Func` finds the name of its function by its address. Approved on 15 November 2026 (choices 378, 379) | A program with one thread runs as it did before tasks came |
| <a id="the-order-of-tasks-in-the-tests"></a>The order of tasks in the tests | Where tasks print in an order of their own, a `.unordered` file next to the program says so, and the compiled output is compared line by line in any order; the interpreter's output is compared as it is. Every program with tasks also runs under the thread sanitizer, which is first tried on a C program that races on purpose. Approved on 15 November 2026 (choice 380) | A check that cannot see a race does not pass |
| <a id="leaks-after-a-panic-in-the-tests"></a>Leaks after a panic in the tests | A compiled program that ends in a panic is not looked at for leaks: a panic does not unwind, so the system takes back what the program owned, and whether a leak tool still sees a pointer to it is up to the C compiler. Such a program still runs under the sanitizers and gives the interpreter's output; the test counts how many there were. The tests pass on Linux as on macOS (tried in a container, by hand; there is no CI). Approved on 15 November 2026 (choices 382, 383) | ["Copy and cleanup"](ownership.md#copy-and-cleanup): panic does not unwind; the same rule as a compiled test that fails |
| <a id="async-comes-in-parts"></a>Async comes in parts | First `async` functions, `await`, `Task.delay` and the rules of ["Async, the direction"](../directions/async.md) that need nothing more, in the checker and the interpreter; then cancellation with input and output that is async, where how a cancellation shows in a `Result` and the names of the functions are still open; then compiled code (state machines, a pool of threads, a loop that waits for input and output). Approved on 15 November 2026 (choice 384) | ["Async, the direction"](../directions/async.md) |
| <a id="an-async-function"></a>An async function | `async` is written in front of a function at the top level, and the type after it is what the body returns: `async int count()` gives a `Task<int>`, the same `Task<R>` as `Task.run`. `async void f()` gives a `Task<void>` that is awaited like any task, not C#'s `async void`. An `async` method, and `async` in front of anything but a function, are not here yet. `main` can be async. Approved on 15 November 2026 (choices 385, 396) | ["Async, the direction"](../directions/async.md) |
| <a id="an-async-call-starts-at-once"></a>An async call starts at once | A call without `await` starts the task at once, and it runs on the caller until it first waits, as in C#; a task of `Task.run` still runs when it is waited for in the interpreter. `await f(x)` runs `f` as part of the caller's task, with no task of its own. Approved on 15 November 2026 (choices 386, 387) | ["Starting"](../directions/async.md#starting), "`await f()` takes no allocation" |
| <a id="what-an-async-call-is-given"></a>What an async call is given | A call without `await` follows the thread rule, as `Task.run` does; `await f(read xs)` ends before the caller goes on, so it can borrow. What an async function returns follows the thread rule wherever it is called. Approved on 15 November 2026 (choice 388) | Rust's line: `tokio::spawn` needs owned values, an awaited future borrows |
| <a id="await-and-wait"></a>`await` and `wait` | `await t` takes the task as `wait` does and is written only in an async function (elsewhere the hint is `t.wait()`); its value is used or dropped with `_ =`. `wait` in an async function is an error whose hint is `await t`; code that is not async waits for an async task with `wait`. Approved on 15 November 2026 (choices 389, 390) | ["Waiting the wrong way"](../directions/async.md#waiting-the-wrong-way) |
| <a id="nothing-holds-the-thread-in-async-code"></a>Nothing holds the thread in async code | In an async function `wait`, the functions of `File`, reading `Stdin`, a file stream, and a call of a function that does one of them (found on the whole program, the chain in the message) are errors whose hint is `await Task.run(work, x)`. Writing to `Stdout`, `Stderr` and `print` are not counted. Approved on 15 November 2026 (choice 391) | C# writes to its console from async code; the promise is about waits that can take long |
