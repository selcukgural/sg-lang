| <a id="file-api"></a>File API | C# names: `File.openText` gives a `StreamReader`, `File.createText` gives a `StreamWriter`. `reader.readLine(ref line)` reuses the buffer and returns `Result<bool, IoError>`. `reader.lines()` gives an owned `string` per line and ends after the first error. `int.parse` returns a `Result` | `Iterator.next` cannot lend from its own buffer, since `next` would change that buffer on the following call. And there is no loop that gives the same error forever |
| <a id="close-error"></a>Close error | `writer.close()` takes `this`, writes the buffer and returns a `Result`. `Closable` is an empty marker (`StreamWriter : Closable`): if a local variable of such a type is dropped at a normal exit without being closed or moved elsewhere, it is a compile error, and the hint is `try writer.close()`. An error exit through `try` is exempt, `dispose` runs there; so is `return Error(...)` *(13 November, choice 211)*, while `exit` is a normal exit that is checked *(choice 212)*. To give up on purpose, `_ = writer.close()`. If the value is moved into a struct field, a list or a `shared`, the compiler stops tracking it and there is no restriction | A forgotten `close` silently loses the write error. In C# the same idea is an analyser warning (CA2000), in Rust there is no check. It is an error because the language has no concept of a warning and the check is exact. The heavy version that tracked everywhere was removed on 11 November, and this version that looks only at locals was added the same day. Cost: one marker and one rule; a value moved into a field and dropped without being closed is not seen, and the responsibility lies with whoever writes the struct |
| <a id="print-error"></a>`print` error | `print` does not return an error. If it cannot write, the program stops with a message, exit code 1. On a closed pipe (`program \| head`) it exits silently, like Unix tools: by `SIGPIPE` on Linux and macOS, interpreted and compiled, as C's and Go's programs end; with 0 on Windows, which has no such signal (18 November; the interpreter ended with 0 before). Whoever wants to handle the error writes `Stdout.writeLine(...)`, which returns a `Result` (named `Console.out` until 13 November; `Stdin`, `Stdout` and `Stderr` are the names of C, Go, Rust and Zig, and the input is often a pipe, not a console) | If it returned an error, every line would need a `try`. Rust panics too, but it also prints a message on a closed pipe, and we differ there. Cost: the only exception to the rule that panic is "only for programmer errors" |
| <a id="where-print-writes-as-built"></a>Where `print` writes, as built | On Linux and macOS a standard stream closed when the program started (`program >&-`) is opened on `/dev/null` first, as Rust's runtime does, so the first file the program opens does not take its number and get what `print` writes (choice 1595). Compiled code gathers what `print` and `Stdout` write in a block of 64 KB of its own and gives it to C's `stdout` when it is full, when the program ends (by returning, `exit` or a panic), and before anything else writes where the output may go: `printError` and `Stderr`, another program started, a read of a terminal, a call of C and the return of an `export` function to C. A terminal gets each call's bytes at once. One lock of the program's own is taken for each call (one atomic operation when nobody else holds it), on every program, since a thread of C may call SG back. A line without widths is written piece by piece where it is printed, its values computed first, so a value that panics leaves no part of the line written; a line with widths (`{x,8}`, `{n:X4}`) goes through the runtime's writer of formats. The interpreter gives C's streams on after each call of C, and on Windows puts them in binary mode as compiled code does, so the two write the same bytes in the same order. Approved on 20 November 2026 (choices 1543 to 1546). Where the block goes out with no `Result` to tell an error to (`print`, before `printError`, another program, a read of a terminal or a call of C, and the end of the program, C's `stdout` given on too), an error ends compiled code as the ["`print` error"](#print-error) row says, with the interpreter's message and 1; a closed pipe by `SIGPIPE`, also when the program was started with it ignored, and an output never open (`>&-`) drops what is written, as Rust's does (choice 1547, the same day; compiled code ended with 0 on a full disk before) | Found by the trial `grep`: 136,000 printed lines took SG 11 ms over the search, Rust 4 ms; the format read at run time and a call of C's `fwrite` with its lock for each line were the difference. Now 4 ms |
| <a id="files-read-and-written-whole"></a>Files read and written whole | `File.readText(path)` gives a `Result<string, IoError>`, `File.readBytes(path)` a `Result<List<byte>, IoError>`; `File.writeText`, `File.writeBytes` (make or empty the file) and `File.appendText` (add at the end, make a missing file) a `Result<void, IoError>`. A path is a `read string`; one with a zero byte in it is `NotFound`, never cut off. `readText` checks the text: a bad byte is `InvalidText(position)` from the start of the file. Approved on 13 November 2026 | The names follow the design's `File.readText`; a path is text, as in C# and Go. A file read piece by piece needs `Closable` and comes later |
| <a id="ioerror"></a>`IoError` | Built in: `NotFound`, `PermissionDenied`, `IsDirectory`, `NoSpace`, `InvalidText(long position)`, `Other(int code)`; `Copyable`, `Formattable`, `Equatable`. The system's codes map the same on Linux and macOS. It does not carry the path. Approved on 13 November 2026. Since 15 November also `Cancelled(Cancelled cancelled)`, for async input and output whose token was cancelled (["A cancellation in a `Result`"](../directions/async.md#a-cancellation-in-a-result)), and the network's `ConnectionRefused`, `ConnectionReset`, `AddressInUse` and `HostNotFound` (["The network, as written"](../directions/async.md#the-network-as-written)), and `LineTooLong` (["The longest line over a connection"](../directions/async.md#the-longest-line-over-a-connection)); since the seventy-fourth slice `AlreadyExists`, `NotDirectory` and `DirectoryNotEmpty`, and a file on the way of a path (`ENOTDIR`) is `NotDirectory`, where it was `NotFound` (choice 569); since the seventy-seventh slice `InvalidInput`, for what cannot be handed to the system, as an argument of a program with a zero byte in it (604); since the eightieth slice `MessageTooLong`, a datagram too long to send as one message or for the buffer it is received into (655), and `ENOTCONN` is `ConnectionReset` (660). Since the 159th slice `TooLong`, `fill` on a reader whose block holds its limit already (1736). Since the 160th slice `AddressNotAvailable`, an address that is not the machine's or no local port left to connect from (1764). `NotAFile`, a pipe, a device or a socket `File.openRegular` did not open (1873). Since the 197th slice `NotATerminal`, no terminal where one was asked for (2033). Written as a sentence in lower case since 20 November (choice 1537): `not found`, `invalid text at byte 812`, `system error 5`, so that a tool's message reads `grep: nope: not found` | The four a program tells apart, and the code for the rest. With the path it would own a text and stop being `Copyable`; the caller has the path for its own error (Rust leaves it out too; Go and C# keep it) |
| <a id="the-command-line"></a>The command line | `main(List<string> args)` gets the words after the program's name, without the name (C#'s way); `void main()` stays. In compiled code nothing is copied. A word that is not UTF-8 stopped the program before `main` until 26 November 2026; now it comes as a name of the system does ([Names of the system, as built](#names-of-the-system-as-built)). `sg file.sg a b` runs a program with `a b`. Approved on 13 November 2026 | The list is the program's own. `args[0]` is the first word, not the program |
| <a id="names-of-the-system-as-built"></a>Names of the system, as built | A name of the system is any bytes on Linux and macOS and any units of UTF-16 on Windows; a `string` is always UTF-8. Such a name comes into the program as a `string` whatever it holds: a byte that is not part of UTF-8, and each byte of a character from U+10FF80 to U+10FFFF, is written as the character U+10FF00 + the byte; given to the system, each such character is its byte again, so the name goes back as it came (choice 1950). On Windows a name is carried as WTF-8, so a half of a pair alone is three such bytes and goes back alone. It holds for every name, in the interpreter and compiled: the words of `main`, the names and values of the environment, the names `Directory.list` gives, `Directory.current`, the temporary folder, every path given to a call of files, folders and programs, and the program and words a started program gets (1951); not for what a file, the input or the network holds, nor for `string.fromUtf8`, which stay `InvalidText`. `Path.systemBytes(name)` gives the bytes the system is given and `Path.fromSystemBytes(bytes)` the text of bytes, and never fails (1952). `print` writes such a character as UTF-8, as any other (1953). A text not made from a name that holds one becomes its byte when it goes to the system; only bytes from 0x80 come out, never `/`, `\`, `.`, `:` or a zero byte (1954). A word of the command line no longer stops a program, `Directory.list`, `Directory.current` and `Environment.get` no longer give `InvalidText`, and `VariableError` has only `Missing` (1955). On Windows a byte that no WTF-8 has, which only a text not made from a name gives, is U+FFFD (1959). Decided on 26 November 2026, slice 189 | `find`, `tar` or `rsync` see and open every file; Python takes the same way (PEP 383) with halves of pairs, which a `string` of SG cannot hold, so the characters are taken from the end of the last plane of private use, which no name of a file uses |
| <a id="reading-the-input"></a>Reading the input | `Stdin.readLine(ref line)` puts the next line into `line` without its `\n` or `\r\n` and gives `Result<bool, IoError>`, `false` at the end; `Stdin.readText()` gives the rest. A line that is not UTF-8 is `InvalidText` from the start of the input, is used up and leaves `line` empty. On a terminal what was printed goes out first. `Stdout` and `Stderr` are kept for the writers. Approved on 13 November 2026 | One text for every line, as `reader.readLine` (row ["File API"](#file-api)); no loop meets the same error forever. `Stdin` is the name of C, Go, Rust and Zig, the input is often a pipe and not a console, and it will be a reader of the type `File.openText` gives |
| <a id="printerror-and-exit"></a>`printError` and `exit` | `printError(x)` writes as `print` does, to the standard error, after what was printed; it gives nothing. `exit(code)` ends the program with a `byte` code after the output goes out, frees nothing and gives no value (`x ?? exit(2)`); in a test it fails the test. Approved on 13 November 2026. A line of `printError` is one write of the system, however long, so lines that several programs append to one file do not mix; a standard error whose reader is gone ends the program by `SIGPIPE` on Linux and macOS, as `print` and C's and Go's programs do, also when the program was started with the signal ignored, and on Windows the line is lost (choice 1601, 20 November; the interpreter went on before, compiled code ended) | There is no one to tell that the standard error failed, and a program whose messages no one reads is ended as one whose output no one reads is. A `byte` makes `exit(256)`, which the system would turn into 0, a compile error. A compiled test runs in a process of its own, where `exit(0)` would pass it |
| <a id="files-and-input-in-compiled-code"></a>Files and input in compiled code | The calls of the system (`open`, `read`, `write`), not `FILE*`; the input in blocks of 64 KB that the program keeps, a line found with `memchr`. Checking UTF-8 passes sixteen bytes at a time while they are ASCII, and from sixteen that hold a byte past ASCII goes straight to it by counting zero bits (choice 1550, 20 November 2026). Measured with `lines`: reading two million lines takes 1.08 times `getline`, which does not check them. Approved on 13 November 2026 | The difference is the guarantee: without the check SG reads faster than `getline` ("Slower than C") |
| <a id="files-read-piece-by-piece"></a>Files read piece by piece | `File.openText(path)` gives a `Result<StreamReader, IoError>`, `File.createText(path)` a `Result<StreamWriter, IoError>` (made or emptied). A reader has `readLine(ref line)`, `readText()` and `lines()`; while `lines()` is used the reader cannot be used beside it. A reader has no `close`. A writer has `write(x)` and `writeLine(x)` (what `print` takes), `flush()` and `close()`, each with a `Result<void, IoError>`; writing needs the writer as `ref`. A folder is `IsDirectory` when it is opened. Approved on 13 November 2026 | The rows ["File API"](#file-api) and ["Close error"](#close-error) made real. A writer that appends piece by piece, and bytes read piece by piece, come later *(14 November: the rows ["A writer that appends"](#a-writer-that-appends) and ["Bytes piece by piece"](#bytes-piece-by-piece))* |
| <a id="the-writer-s-buffer-and-its-first-error"></a>The writer's buffer and its first error | 64 KB, the same in the interpreter and in compiled code: a write that fills it writes it out. The first error is kept, and every later `write`, `flush` and `close` gives it again. A writer that ends without `close` writes its buffer and loses the error; a panic and `exit` write nothing. Approved on 13 November 2026 | A program that reads its own file back sees the same bytes in both. A kept error makes `close` report a full disk even when the writes before it were dropped with `_ =`, as C's `ferror` does |
| <a id="closing-a-writer-checked"></a>Closing a writer, checked | The `Closable` check of the row ["Close error"](#close-error) covers a local variable, a parameter taken by value, a name of a pattern and the item of a `for`, at the end of its block, `return`, `break`, `continue`, `exit`, and before the variable gets another writer. Closed on one path only is an error of its own. `return Error(...)` is let go like `try`. Approved on 13 November 2026 | The caller gets the error that made the function stop; without the exemption every `return Error` would need writers closed by hand. `exit` runs nothing after it, so a writer open there would lose its buffer |
| <a id="stdin-stdout-and-stderr-are-streams"></a>`Stdin`, `Stdout` and `Stderr` are streams | `Stdin` is a `StreamReader`, `Stdout` and `Stderr` are `StreamWriter`s, which every function and test has as `ref` parameters the program gives: `count(ref Stdin)`. They are never moved, given another value or closed, and no variable may have their names. `Stdout` writes where `print` writes, in order; `Stderr` where `printError` does. `print` and `printError` stay. Approved on 13 November 2026 | One function serves a file and the program's own streams. Go has `os.Stdin` as a variable, Rust `io::stdin()`, C# `Console.In` |
| <a id="streams-in-compiled-code"></a>Streams in compiled code | A reader is a block of 64 KB with its file (`Stdin` the same struct over the input); a writer is a text that serves as its block, written with `write` of the system. `Stdout` and `Stderr` go through C's `stdout` and `stderr`, so they keep their order with `print`. Measured with `copy`: a log of 125 MB copied line by line takes 0.93 times `getline` and `fprintf`. Approved on 13 November 2026 | The reading is faster than `getline` even with the UTF-8 check |
| <a id="a-writer-that-appends"></a>A writer that appends | `File.openAppend(path)` gives a `Result<StreamWriter, IoError>` that writes after what the file holds; a missing file is made, a folder is `IsDirectory`. It is a `StreamWriter` like any other, with the `Closable` check. The file is opened to append, so every block lands at the end even when another program writes to it too. Approved on 14 November 2026 | C#'s `File.AppendText(path)` is this stream, but `File.appendText(path, text)` is the whole write here, and one name cannot mean both without overloading |
| <a id="bytes-piece-by-piece"></a>Bytes piece by piece | `reader.readBytes(ref buffer)` puts bytes at the start of a `ref byte[]` and gives how many (`Result<nint, IoError>`); it fills the buffer unless the end comes first, so fewer means the end, and the next call gives 0. `writer.writeBytes(bytes)` writes a `read byte[]` as it is, through the writer's buffer, in order with `write`. Both go through the `StreamReader` and `StreamWriter` of text, so `Stdin`, `Stdout` and `Stderr` read and write bytes too; bytes and lines from one reader share its block, and an `InvalidText` position counts the bytes read as bytes. No type and no opening function of their own. Approved on 14 November 2026 | One meaning for a short count; Rust's `read` and Go's `Read` may give fewer at any time, and a program that needs the buffer full loops. Cost: on a pipe or a terminal the call waits until the buffer is full or the input ends (see "Open questions"). A second reader type or `File.openBytes` would be two ways to do one thing |
| <a id="bytes-in-compiled-code"></a>Bytes in compiled code | `readBytes` takes what the block holds first, and a rest of 64 KB or more is read straight into the buffer; `writeBytes` of 64 KB or more writes the block and then the bytes straight. Measured with `bytes`: a log of 125 MB copied in pieces of 4 KB takes 0.94 times `fread` and `fwrite`. Approved on 14 November 2026 | Large reads and writes are not copied twice |
| <a id="receive-and-send"></a>`receive` and `send` | A `TcpStream` receives what has come (how many, 0 at the end) and sends all its bytes; `read` is a word of the language, and these are C#'s names for a socket. A listener is reached through `read`, so several tasks can take connections from one `shared` listener; a stream through `ref`. A socket has no buffer and no `close`: it closes where it ends. Approved on 15 November 2026 (choices 466-470) | Apart from a reader's `readBytes`, which fills the buffer |
| <a id="the-network-in-the-interpreter"></a>The network in the interpreter | A socket does not block; a task whose socket is not ready gives the turn away, and when none can run the scheduler waits for the sockets with `poll` until the first timer is due, then the clock goes on to the time that has gone by. A task of `Task.run` that has not run starts when a task is about to wait for the network or the input. Approved on 15 November 2026 (choices 473, 474) | Otherwise a server started with `Task.run` never runs while `main` waits for it; programs without the network keep the order they had |
| <a id="the-network-in-compiled-code"></a>The network in compiled code | One thread waits for the sockets with epoll or kqueue (since the eighty-first slice, a thread of the pool with nothing to do); a cancel takes the socket off, and the loop wakes the task once it is done with the events it holds. A listener is waited for through a copy of its socket (*changed on 16 November 2026, in the eighty-second slice:* a socket goes on the loop once, the first time a task waits for it, edge-triggered, and a wait is no call of the system; several tasks wait for one socket in its slot, with no copy, and a cancel takes the task out of the slot and wakes it at once). A socket blocks until an async call first uses it, so a call without async is one call of the system. Names are looked up on a thread that a cancel leaves. Approved on 15 November 2026 (choices 471, 472, 475-477) | The threaded echo takes the time of C |
| <a id="the-network-the-async-way-measured"></a>The network the async way, measured | An echo server with eight clients takes 1.86 times C with blocking threads, 0.99 without async; two threads are woken for each wait where C wakes one, in "Slower than C". Approved on 15 November 2026 (choices 478, 479). *Measured again on 16 November 2026, in the eighty-first slice (choices 673, 674):* 1.21 times C on macOS, 17 times on Linux in a container (28 before), where Tokio takes 5.5 times C; with work in each message, the time of C. *Measured again in the eighty-second slice (choice 688):* 1.03 times C on macOS, still 17.7 times on Linux, where the time is in the one queue of the pool; datagrams 1.16 times on Linux (1.54 before). *Measured again in the eighty-third slice (choice 700):* 0.89 times C on macOS and 7.4 times on Linux (Tokio 5.5); datagrams 1.06 and 0.57 times C. *Measured again in the 157th slice (choices 1708-1714):* 1.06 times C on macOS and 7.5 times on Linux, datagrams 1.07 and 1.05 times C: with a loop on each thread the two ends of a connection lie on two threads | |
| <a id="the-reader-of-a-connection-as-built"></a>The reader of a connection, as built | `conn.reader()` is a `StreamReader` that carries a borrow of the connection: lent where a reader is lent, refused in a field, a return or a task. `send` goes through `read`, `receive` through `ref`, so a `receive` while the reader is used again is a compile error; neither `send` nor `reader()` through a `shared` connection. A line or a text longer than the limit (64 KB, or `conn.reader(limit)`) is `LineTooLong`, and every read after it; `readSome` is on every reader. Approved on 15 November 2026 (choices 480-485) | What has come stays in the block until a read can take all it needs, so a cancel loses nothing |
| <a id="the-reader-of-a-connection-in-the-interpreter-and-in-c"></a>The reader of a connection, in the interpreter and in C | The interpreter keeps what has come in a block of its own and gives the turn away while the socket is not ready. In C, `sg_reader` has the connection, the size of its block, the limit and the mark of a line too long; an async read its block cannot answer waits on the loop of the network. Approved on 15 November 2026 (choices 486, 487) | |
| <a id="lines-over-a-connection-measured"></a>Lines over a connection, measured | Two million lines over the loopback read with `readLineAsync` take 1.46 times `getline` in C, which does not check that they are text; 0.89 without the check, which is in "Slower than C". Approved on 15 November 2026 (choices 488, 490) | |
| <a id="signals-as-built"></a>Signals, as built | `Signals.listen(read List<Signal> { Signal.Interrupt, Signal.Terminate })` gives a `SignalListener` (`Disposable`, given to a task if need be); while it lives, those signals do not end the program, and once the last listener of a kind ends, the kind does what it did before. `listener.next()` waits for the next and gives it; `await listener.nextAsync(read token)` does not hold the thread, a cancel ends the wait and a later signal stays. Several of one kind before a call are one, kinds come in their order, every listener gets each. `Signal` is `Interrupt`, `Terminate`, `Hangup`, `Quit`, `User1`, `User2`, `WindowChange`, without numbers. `Signals.raise(s)` is C's `raise`, what was printed written out first; `process.signal(s)` sends one to a program started with `Command`.
