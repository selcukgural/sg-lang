| Topic | Decision | Reason |
|---|---|---|
| <a id="a-character-is-a-byte"></a>A character is a `byte` | `'+'` is a `byte` where an integer goes: `int x = '+'` is 43 through the ordinary widening, `text[i] == ':'` compares bytes. *(Changed on 13 November with the `char` row: where nothing decides, it is a `char`, and `print('+')` writes `+`.)* | Follows from the `char` row and the widening rule, no new rule |
| <a id="quotes-and-escapes"></a>Quotes and escapes | `\'` is an escape in both kinds of quotes; neither quote has to be escaped inside the other (`'"'`, `"'"`) | C#'s rule |
| <a id="print-and-null"></a>`print` and `null` | `print` of a `T?` or a `Result` is a compile error; the hint is `??`, `is null` or `try`. Inside a generated text `null` is written | A silent `null` in the output is more likely a forgotten test. Rust does not print an `Option` either; C# prints an empty line |
| <a id="characters-and-slices"></a>Characters and slices | `'+'` is a character constant (a `char`, or a `byte` where an integer goes), `string` is UTF-8 and byte indexed, a slice is `text[a..b]` (C#). `read string` is pointer + length. Unicode operations are in the library. The single-character type is in the ["`char`"](#char) row | The language core stays small, indexing is O(1) |
| <a id="string-constant"></a>String constant | The type of `"x"` is `read string`. Where a `string` is expected it becomes a `string` without allocating: capacity 0, data inside the program. It is not freed, and the first write or growth copies first. Only for constants, a `read string` variable needs `.clone()`. If a function with no borrow parameter returns `read string`, the source can only be a constant, and nothing needs to be written | No `.clone()` noise, and no hidden heap allocation either. To keep a constant in a struct field, `string` is enough, no separate source name is needed. *As built: the type of `"x"` is `string`, with all the rest of this row; a constant goes where a `read string?` goes as it is too (choice 1403).* |
| <a id="text-formatting"></a>Text formatting | `$"{a}: {b}"`, C# notation. It is a language feature, checked at compile time, and does not allocate. The result is a value that borrows its arguments and implements `Formattable`. For a `string`, `.toString()` is written. `{{` writes a curly brace. A width and a letter may follow the value (see "A width and a letter in `$"..."`", 14 November) | It has to be in the language because there are no macros. The only difference from C#: so that heap allocation stays visible, a `string` is not created by itself, and where a `string` is expected the hint is `.toString()` |
| <a id="string-guarantee"></a>`string` guarantee | Always valid UTF-8. A bad byte on reading gives `IoError.InvalidText(long position)`, the only way from bytes to text is `string.fromUtf8`, which returns a `Result`, and raw data is read as a `byte` slice. String constants are checked at compile time. A slice through the middle of a character panics. `text[i]` is read only, a byte cannot be written | Core principle: bad data should not silently become `�` (C#), and Unicode operations should not meet garbage |
| <a id="char"></a>`char` | 32 bits, holds every Unicode character (`Rune` in C#). `'+'` fits the expected type like a number constant: `byte` where an integer is expected, `char` everywhere else: `var c = '+'` gives a `char` (changed on 13 November; it was a `byte`, which made `print('+')` write 43). A constant that does not fit in one byte (`'é'`) is a compile error where a `byte` is expected, and the hint is `char`. To walk through text character by character, `text.chars()` | C#'s 16-bit `char` splits an emoji into two parts, and that mistake should not be carried over. Cost: the same name, a different size from C# |
| <a id="text-and-bytes"></a>Text and bytes | `text.asBytes()` views text as `read byte[]`, for free. `string.fromUtf8(bytes)` views bytes as text: it checks the UTF-8, does not copy, and returns `Result<read string, TextError>` | The Rust names (`as_bytes`, `str::from_utf8`). C# has no path without a copy. The `string` guarantee is kept: there is no unchecked conversion. The copying `string.fromBytes` was removed on 11 November, and whoever wants a copy writes `.clone()`: one way, and the copy is visible in the code |
| <a id="texterror"></a>`TextError` | A built-in struct, `TextError : Copyable, Formattable, Equatable`, with one field: `public readonly nint position`, the place of the first byte that is not valid UTF-8. Seen from every module with nothing written; the name is reserved | Rust's `Utf8Error::valid_up_to`. The design had named the type and nothing more; a position is what a caller can act on. Approved on 13 November 2026 |
| <a id="raw-text"></a>Raw text | C#'s: `"""a "quoted" word"""` on one line; on lines, the opening quotes end their line and the closing ones stand on a line of their own, whose indentation is taken off every line (a line indented less is an error, one with nothing on it may be). No escapes; a line break is `\n`; more quotes hold three. `$"""` puts values in as `$"..."` does, `{{` for a brace; C#'s `$$"""` is not taken. Approved on 18 November 2026, before the hundred-and-sixth slice (choices 1153, 1154) | Tests, JSON, help texts and Windows paths are written as they are read. Rust's `r#"..."#` keeps the indentation; Go's backquote and Zig's `\\` lines are the same idea |
| <a id="char-is-not-a-number"></a>`char` is not a number | No arithmetic on a `char`, no comparison with an integer, no widening: `int x = c` is an error whose hint is `(int)c`. A cast goes between `char` and the integer types only. `(char)n` panics in every build when no character has the code (hint `n.tryToChar()`, which gives `null`), and is a compile error when the code is known; `(byte)c` follows the integer rule. `char` is `Copyable`, `Equatable`, `Hashable`, `Comparable` and `Formattable`, and `match` takes characters. Inside a collection it is written `'a'`. Approved on 13 November 2026 | Rust's way; C# adds a `char` like a number. A bad code written into a text would break the `string` guarantee, so that check stays in release, like the bounds check |
| <a id="backslash-u"></a>`\u{...}` | A character by its code, in a text and in a character constant: `'\u{e9}'`, `"\u{1F600}"`, one to six hex digits. Approved on 13 November 2026 | Rust's and Swift's form, and what `print` writes for a control character inside a collection. C#'s `\uXXXX` cannot reach past 0xFFFF in one escape |
| <a id="ascii-tests-of-a-character"></a>ASCII tests of a character | `isAscii`, `isAsciiDigit`, `isAsciiLetter`, `isAsciiAlphanumeric`, `isAsciiUpper`, `isAsciiLower`, `isAsciiWhitespace`, `toAsciiUpper`, `toAsciiLower` on `char` and on `byte`; `isWhitespace` (Unicode's White_Space) and `utf8Length` on `char`. `isDigit` is not there, and gets `isAsciiDigit` as a hint. Approved on 13 November 2026; the methods that need Unicode tables came on 16 November (["Unicode tests of a character"](#unicode-tests-of-a-character)) | One answer everywhere; C#'s `char.IsDigit` says yes to the digits of many scripts and `ToUpper` depends on the culture |
| <a id="going-over-a-text"></a>Going over a text | `text.chars()`, `text.split(sep)` (a `char` or a `read string`, never empty), `text.splitWhitespace()`, `text.lines()`. The parts are `read string`s that look at the text; `split` keeps the empty parts, `splitWhitespace` skips them, `lines` leaves out the `\r` before `\n`. What they give is an iterator: `for` goes over it and uses it up, `it.next()` gives the next part or `null`. It is not copied, and its type cannot be written yet (it carries a borrow of the text). Approved on 13 November 2026 | Rust's meanings. Nothing is copied, and the iterator waits for generics to get a type that can be written |
| <a id="a-part-of-a-text-and-its-text"></a>A part of a text and its text | A part borrows the text, not the iterator: after `var name = parts.next()` the iterator goes on. While a `for` goes over a text the text cannot be changed or moved; `split` keeps its separator too. An iterator over a text with no name is an error. Approved on 13 November 2026 | The rule of a `from source` method, and of a `for` over a collection |
| <a id="trimming-and-looking-in-a-text"></a>Trimming and looking in a text | `trim`, `trimStart`, `trimEnd` give a `read string` without Unicode's White_Space at the ends. `indexOf`, `lastIndexOf` (a `nint?` in bytes), `contains`, `startsWith`, `endsWith` take a `char` or a `read string` (the two positions a `byte` too). `equalsIgnoreAsciiCase` folds the ASCII letters only; the design's `equalsIgnoreCase` is renamed. Approved on 13 November 2026 | Positions in bytes, because `text[a..b]` takes bytes. Ignoring the case of any text needs Unicode tables |
| <a id="try-on-a-read-t"></a>`try` on a `read T?` | Gives a `read T`, as `??` does: `var level = try parts.next()`, in a function that returns a `T?` or a `read T?`. Approved on 13 November 2026 | Nothing is taken out; the borrow is passed on. It was an error before |
| <a id="text-in-compiled-code"></a>Text in compiled code | A `char` is a `uint32_t`; an iterator a small struct whose `next` the C compiler inlines; a part a pointer and a length into the text. Measured with `fields`: splitting, trimming and reading a million lines takes 1.08 times C written with `memchr` and `strtoll`. Approved on 13 November 2026. A text of more than one byte is looked for (`indexOf`, `contains`, `split`, `replaceAll`, and a regular expression's plain text) by its two rarest bytes, ranked by a table of how common each byte is in text and code, compared at sixteen starts at a time with the processor's vector instructions where the C compiler has them, the text itself only where both are found; one byte by `memchr` (choice 1549, 20 November 2026) | What C does by hand, with the UTF-8 read where a character matters |
| <a id="building-a-text"></a>Building a text | A `string` is its own builder: `text.write(x)` adds at its end whatever `print` takes, as `f.write` does, and a `$"..."` is written straight into the block. No builder type beside it. It needs the text where it may change (not through `read`, not a `readonly` field), and the borrow rules hold as for any `ref this` method. Approved on 13 November 2026 | A `string` already is a pointer, a length and a capacity, so the finished text needs no copy. Rust's `String` is its own builder; C# and Go keep a separate one |
| <a id="writing-a-text-into-itself"></a>Writing a text into itself | `s.write(s)`, `s.write(s[..3])`, `s.write(s.trim())` and a value that borrows from `s` are errors whose hint is `.clone()`; a number, a `bool` or a `char` computed from `s` is fine, since the values of a line are computed first. Approved on 13 November 2026 | The text may move to a larger block while it grows, and what is written would be read from the old one. Rust's rule |
| <a id="clear-and-withcapacity"></a>`clear` and `withCapacity` | `text.clear()` empties the text and keeps its block; `string.withCapacity(n)` takes room for `n` bytes at the start (0 takes none, a negative `n` panics in every build). Without it the block starts at 32 bytes and doubles. A constant is copied on the first write. Approved on 13 November 2026 | A line built again in every round of a loop takes memory once; a text whose size is known grows once |
| <a id="plus-equals-on-text"></a>`+=` on text | Stays an error, with the hint `text.write(...)`; `StringBuilder`, `append` and `push` get the same hint, `a + b` keeps `$"{a}{b}"`. Approved on 13 November 2026 | One way to add to a text |
| <a id="building-text-in-compiled-code"></a>Building text in compiled code | `write` is the code of `f.write`; the formatted pieces are written straight into the block where it has room. Measured with `numbers` and `fields`: building a million lines takes the time of `sprintf` into one buffer in C. Approved on 13 November 2026 | The cost a text built from many small ones had ("Slower than C") is gone |
| <a id="a-width-and-a-letter-in"></a>A width and a letter in `$"..."` | After the value, as in C#: `{value,width:letter}` (`{n,5}`, `{name,-10}`, `{b:X2}`, `{price,8:F2}`). Part of the program, checked at compile time. Inside `{ }` a `:` outside the value's own brackets starts the letter, and a `,` outside them starts the width when a number follows it; otherwise the `,` stays part of a type (`HashMap<string, int>`). Takes up "a format specifier inside `$"..."`", which had been left for after the first version. Approved on 14 November 2026 | `$"..."` is already C#'s. Rust writes `{:>8.2}`, C and Go `%8.2f`. Nothing is read while the program runs |
| <a id="the-letters"></a>The letters | `x` and `X` hex, `b` binary, `D` decimal, `F` digits after the point; only `x` and `X` differ by case. The number after the letter is the digits there are at least for `x`, `X`, `b` and `D` (zeros in front, the sign before them: `{-7:D3}` is `-007`) and the digits after the point for `F`, which must have one. At most 999. A letter that does not fit the value is a compile error with a hint (`{(double)n:F2}`, `{(int)c:X4}`); `N`, `E`, `G`, `C`, `P` and formats made of characters are left out. Approved on 14 November 2026 | `N` puts separators between groups of digits that change from one country to another, and C#'s default for `F` comes from the country settings; a program here writes the same text everywhere |
| <a id="a-negative-number-in-hex-and-binary"></a>A negative number in hex and binary | Written as the bits of its type: `{small:x}` with `sbyte small = -1` is `ff`, with an `int` `ffffffff`. No `0x` is put in front. Approved on 14 November 2026 | C# and Rust write the same |
| <a id="rounding-of-f"></a>Rounding of `F` | The exact value to the nearest, a tie to the even digit: `{2.5:F0}` is `2`, `{0.125:F2}` is `0.12`. `NaN` and the infinities as `print` writes them; `-0.0` and a small negative number keep their minus. Approved on 14 November 2026 | Rust, C's `printf` and .NET since 3.0 give the same digits |
| <a id="a-width-counts-characters"></a>A width counts characters | Not bytes: `{"Zürich",8}` has two spaces. Positive: spaces in front; negative: after. A longer value is not cut. Every value `print` takes, a struct with its own `format` and a list included. The fill is a space only, no centring, and the width is a number written in the text. No `padLeft`: `$"{name,10}".toString()` is that text. Approved on 14 November 2026 | C#'s alignment. A variable width would be a second way to build the format at run time |
| <a id="writing-a-number-in-compiled-code"></a>Writing a number in compiled code | Hex and decimal digits are `printf`'s conversions with the width in them (`%8.4llx`); binary digits by a small function; `F` by a function of the program that rounds exactly in 128 bits (`snprintf` past 18 digits or out of its range); a width on text is one `%*.*s` whose width in bytes counts the characters. Measured with `table`: two million lines take 0.89 times `printf`. Approved on 14 November 2026 *(18 November 2026, the hundred-and-sixteenth slice: the lines the code SG writes, `print`, `printError`, `panic`, `$"..."` and `f.write`, no longer go through C's `printf`: the runtime writes the few conversions that code uses itself, a text with its length, the byte 0 and more than 2 GB included, and a width counted in characters; `table` takes 0.52 times `printf`; choice 1336)* | The first version (1.30 times) wrote `F` with `snprintf` and copied it with `printf`, and put the spaces of a width in a conversion of their own |
| <a id="replaceall"></a>`replaceAll` | `text.replaceAll(old, new)` gives a new text with every place of `old` replaced by `new`; the text stays as it was. Not `replace(old, new)`: `x.replace(value)` already puts a new value in a place on every type, so the same name would change the text with one argument and not with two. `line.replace(a, b)` is an error whose hint is `replaceAll`. Decided before the forty-seventh slice and approved with it on 14 November 2026 | Go's `ReplaceAll`; C# and Rust say `Replace`/`replace`, where the name is free |
| <a id="replacing-what-is-looked-for"></a>Replacing: what is looked for | `old` and `new` are each a `char` or a `read string` (not a `byte`). The places are found from the left and do not overlap (`"aaa".replaceAll("aa", "b")` gives `"ba"`), and what was put in is not searched again. An empty `old` is refused as the separator of `split` is: a constant `""` is a compile error, an empty text at run time a panic. Approved on 14 November 2026 | Rust and Go put `new` between every two characters, C# and Zig stop; a loop over `chars()` says the first plainly |
| <a id="repeat"></a>`repeat` | `text.repeat(n)` gives the text `n` times over as a new text. `n` is a `nint`, as an index is. A negative constant is a compile error, a negative number at run time a panic, and a text too big for the memory a panic that says so. A `char` has no `repeat` (`c.toString().repeat(n)`). Approved on 14 November 2026 | Rust's and Go's `repeat`; the panic in place of an abort holds in both programs |
| <a id="replacing-and-repeating-in-compiled-code"></a>Replacing and repeating in compiled code | `replaceAll` finds each place with the search of `indexOf` (its two rarest bytes, then `memcmp`, choice 1549) and copies the pieces into a block that doubles when it is full; `repeat` allocates the whole size once and copies what it has written after itself. Approved on 14 November 2026 | Rewriting lines with them takes 0.94 times the same program in C |
| <a id="checking-utf-8-a-block-at-a-time"></a>Checking UTF-8 a block at a time | A reader checks the rest of its block at once and keeps how far it is known to be text; the lines inside that part cost nothing. A line starts after a `\n`, so what is found is what a check of each line finds; a line two blocks share is checked whole, and a read of bytes lets go of what is known. The check passes sixteen bytes at a time while they are ASCII, the same C on every machine. Reading two million lines takes 0.82 times `getline` in C (1.08 before), over a connection 1.14 (1.46). Approved on 15 November 2026 (choices 491-495) | A check of each short line cost about the same whatever the way of checking; vector instructions (NEON, 8.8 GB/s) are left in "Slower than C" |
| <a id="unicode-tests-of-a-character"></a>Unicode tests of a character | *Decided on 16 November 2026, before the seventy-ninth slice (choices 635 to 638).* On `char`, from the tables of Unicode 17.0: `isLetter` (general category L), `isNumeric` (N), `isAlphanumeric`, `isUpper` (Lu), `isLower` (Ll), `isControl` (Cc); `toUpper` and `toLower` give a `char` by the simple mapping (`'ß'.toUpper()` is `'ß'`). Not on `byte`, which keeps the ASCII methods. Out: normalization (in since the hundred-and-forty-seventh slice, choice 1599), grapheme clusters, sorting by a language, width, names in Unicode | C#, Go and Java take the categories; Rust's `is_alphabetic` is wider and its `to_uppercase` gives an iterator, whose type cannot be written here |
| <a id="the-case-of-a-text"></a>The case of a text | *Decided on 16 November 2026, before the seventy-ninth slice (choices 639 to 642).* `toUpper` and `toLower` give a new `string` by the full mappings, with `Σ` at the end of a word as `ς` (Rust's `to_uppercase` and `to_lowercase`). `equalsIgnoreCase` compares by the full folding without allocating, `foldCase` gives the folded text. No language is taken into account; the Turkish and Azeri mappings are left for later | One answer on every machine; C#'s `ToUpper` follows the culture of the machine |
| <a id="one-set-of-unicode-tables"></a>One set of Unicode tables | *Decided on 16 November 2026, before the seventy-ninth slice (choice 636).* The tables are made by a script from the Unicode Character Database (each file checked against its SHA-256) and kept in the repository; the data files are not. The interpreter and compiled code read the same tables, not Rust's own `char` methods. In compiled code they are only in a program that uses them | The two sides give the same answers whatever version of Unicode Rust knows |
| <a id="the-general-category-of-a-character"></a>The general category of a character | *Decided on 20 November 2026 (choices 1475, 1476), and built in the hundred-and-thirtieth slice.* The tables take the general category of every code point (five bits of its record). `c.category()` gives a `UnicodeCategory`: Unicode's 29 long names as SG writes a name (`UppercaseLetter` ... `Unassigned`; no `Surrogate`, which no `char` is), `abbreviation()` the short one (`Lu`). Written in `std/unicode.sg` over a lookup only `std` calls | C#'s `char.GetUnicodeCategory` gives the same; Rust's library has none, Go asks `unicode.Is(unicode.Lu, r)` |
| <a id="normal-forms-of-unicode"></a>Normal forms of Unicode | *Decided on 20 and 21 November 2026 (choices 1599, 1611 to 1615), and built in the hundred-and-forty-seventh slice.* `text.normalize(form)` gives a new `string` in a normal form of UAX #15 and `text.isNormalized(form)` says whether the text is in it; the form is a `NormalizationForm` of `std`, `C`, `D`, `KC` or `KD` (C#'s names), always written. The work is the compiler's own, as the case of a text is: the interpreter and compiled code read the same tables (the combining class, the quick checks and the full decompositions of each code point, found in three steps, and the pairs that compose; Hangul by its rule), in compiled code only in a program that normalizes, apart from the tables of case. The quick check looks at the text first, and a text in the form is copied as it is; the rest is normalized a piece at a time, a piece ending before each starter the check says Yes to. The output is always Unicode's: no Stream-Safe Text Format, and the marks of a run are put in order by a stable sort, in O(n log n) however long the run. Tested by every line of `NormalizationTest.txt`, interpreted and compiled, and every code point against Python's Unicode 17.0. Zip names are compared by the canonical caseless match (D145) | Rust has them in the `unicode-normalization` crate (`s.nfc()`, `is_nfc`), Go in `golang.org/x/text/unicode/norm`, which inserts U+034F after 30 marks and so changes the text; C# has `Normalize` and `IsNormalized` |
