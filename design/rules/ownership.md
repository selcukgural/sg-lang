| Topic | Decision | Reason |
|---|---|---|
| <a id="lifetime-notation"></a>Lifetime notation | No `'a`; `from a, b` at the end of the signature, with default rules | The name of the source variable is written instead of an abstract name. Details: [syntax](../02-syntax-draft.md) |
| <a id="from-and-where"></a>`from` and `where` | `from` states the source of the return value, `where` states a type constraint. If another parameter stores the borrow, `where r from name` *(12 November: `where` is deferred with generics; `from` stays.)* | `where return from` was crowded, and it is clear that the subject is `return` most of the time |
| <a id="read-only-borrow"></a>Read-only borrow | `read T` | It says directly what it does and is not confused with `for x in xs` |
| <a id="owning-pointer"></a>Owning pointer | `T*`, created with `new` | Short, and consistent with the `T*?` notation |
| <a id="move"></a>Move | Implicit, the compile error shows the line where the value was moved | `list = push(move list, 1)` was getting crowded |
| <a id="local-borrow"></a>Local borrow | `read T x` is not written. `var` infers the type, and the borrow is on the right-hand side: `var x = read items[0]` | `read` is a contract in a signature and in a field, and in a local it is information the compiler already has. `string x` asks for an owner; assigning a borrow is an error, a copy must be made |
| <a id="ref"></a>`ref` | Writable borrow (`&mut T`); also written at the call site | Familiar from C#. Can also be used in a return type and in a field |
| <a id="shared-ownership"></a>Shared ownership | `shared T`, a second owner with `share x`, creation with `new shared x` | One name for `Rc` and `Arc`: the counter is always atomic. A non-atomic version can be added later if needed, the reverse is hard. The cost is paid only on `share` and when an owner lets go, a borrow does not touch the counter |
| <a id="weak-reference"></a>Weak reference | `weak T`, `weak x`. The result of `share w` is `shared T?` | Not an owner, breaks cycles. `null` if the object is dead |
| <a id="interior-mutability"></a>Interior mutability | `checked T` (`RefCell`) borrows on access and panics on a conflict. Its duration is in the ["`checked` borrow duration"](#checked-borrow-duration) row | A run-time check like the array bounds check, visible in the type |
| <a id="question-and-borrows"></a>`?` and borrows | `ref T?` is a borrow of the original variable of type `T?`; "the borrow may be absent" is written `(ref T)?`. `read T?` has a single meaning, `shared T?` says the pointer may be absent | A C# reader expects `ref T?` to read this way. Since `read` cannot write, the two readings do not differ. `T*` cannot be empty; null cannot be assigned through `ref T*`, the caller's type would be lying |
| <a id="copy-and-cleanup"></a>Copy and cleanup | The `Copyable`, `Clonable`, `Disposable` interfaces. The compiler generates the body of the first two *Built on 15 November 2026, in the seventy-first slice, `Disposable` on a struct:* `void dispose(ref this)`, which the program never calls; it runs once where the last owner ends, before the fields end, and not after `exit` either | No macros. `dispose` does not run during a panic |
| <a id="source-name-parameter"></a>Source name parameter | `Match<from text, from pattern>`, also for a single source: `Parser<from source>`. If the type has a single source, `from` is not written on the field, and if it has more than one it is: `read string found from text`. In a method `from source`, outside `from lx.source` | It is told apart inside the same `<>` as a type parameter. `from this.lexer.input` was pulling a private field into the signature. With a single source there is no ambiguity, and repeating it on the field is noise |
| <a id="a-looked-at-argument"></a>A looked-at argument | An argument a method only looks at is lent when it cannot be copied: `old.compare(read next)`, `tags.contains(read tag)`; a `Copyable` one is passed as it is. The operators need no `read`: `old < next`. Decided on 12 November | The same rule as ["Looking a key up"](collections.md#looking-a-key-up); operands are never taken ("Looking is not taking") |
| <a id="new"></a>`new` | Required. It puts the value on the heap and gives a `T*`, it does not mean creating an object. `HashMap<K, V>()` takes no `new`, it is the value itself | A separate heap allocation should stay visible, and `var` should know which type is wanted. An implicit conversion can be added later, but cannot be removed |
| <a id="types-that-carry-a-borrow"></a>Types that carry a borrow | Every type that contains a borrow declares its source: `enum Token<from source>`. The rule of not writing `from` holds only when `read` or `ref` is visible in the return type. If the borrow is hidden in the name of the type, `from` is required: `Result<Expr*, E> parse(read string input) from input` | The dependency should be readable from the signature. It is not written on parameters and locals: on a parameter the borrow ends with the call, and on a local a compile error shows it if there is a problem |
| <a id="take-replace-swap"></a>`take`, `replace`, `swap` | In the standard library: `x.take()` only on `T?`, gives the value and puts `null` in its place. `x.replace(newValue)` gives the old value, on every type. `swap(ref a, ref b)`. A field is moved through a `ref` only with these: `var node = this.top` is a compile error, the hint is `this.top.take()` | Rust's `mem::take` needs a default value, and we do not have that concept |
| <a id="disposable-and-moving-a-field"></a>`Disposable` and moving a field | Moving a field out of a `Disposable` type is a compile error *Built on 15 November 2026, in the seventy-first slice:* inside its own methods and `dispose` too, and through a field of a field; `take` and `replace` are the way | `dispose` should not see a half object |
| <a id="for-and-ownership"></a>`for` and ownership | The `match` rule: `for x in xs` moves, `for x in read xs` and `for x in ref xs` borrow, and if `xs` is already a borrow it gives the same kind of borrow. Changing `xs` during the loop is a compile error *(12 November: `for` goes over a range, the built-in collections and the built-in iterators such as `text.lines()`; going over a type of your own is deferred with generics.)* | No new rule. The run-time `InvalidOperationException` of C# appears here at compile time |
| <a id="dispose-order"></a>`dispose` order | The reverse of declaration *Built on 15 November 2026, in the seventy-first slice:* a value's own `dispose` first, then its fields in the order they are declared, each with its own `dispose`; the items of a collection in their order, and those of a `for` handed the collection one by one, each at the end of its turn | What is declared later may have borrowed from what is declared earlier |
| <a id="checked-borrow-duration"></a>`checked` borrow duration | An access borrows for the duration of the expression. A borrow at the head of a `for` or `match` lasts for the whole statement. A local variable cannot hold a `checked` borrow, compile error. A block for several lines: `read x as n { }`, `ref x as n { }` *(14 November: narrowed by the row ["How long a `checked` borrow lasts"](#how-long-a-checked-borrow-lasts): a read or a write borrows nothing after it, and a value lent to a call is borrowed until the call returns.)* | With the "for the duration of the expression" rule it was impossible to loop over a `checked` list. The block has the same form as `lock x as c { }`, no new word is needed, and the duration of the borrow is visible in the code |
| <a id="checked-conflict"></a>`checked` conflict | A conflicting access on the same variable while a borrow is in progress is a compile error: `for x in read a.items { a.items.add(y) }`. A conflict that comes through another variable panics, and the message prints both lines | The `for` rule extended to `checked`: code that would panic every time it runs does not compile. Cost: location information per `checked` and one write on every borrow, the principle wins |
| <a id="weak-t-and-share"></a>`weak T?` and `share` | The result of `share` is a single `null`: `shared T?`, whether it is not linked or the object is dead. `x is null` answers "is it linked", `share x` answers "is it alive". If the difference matters, `if x is not null { var up = share x ?? panic("parent was deleted") }` | There is no `T??`. The difference is not needed in most places, and where it is, two separate questions are asked |
| <a id="copy-of-shared-t"></a>Copy of `shared T` | `Clonable`, and `.clone()` means `share`, it does not copy the content. `List<shared T>.clone()` shares the items | So that `for child in folder.children.clone()` can be written. For a single value the `share x` notation stays |
| <a id="how-long-a-borrow-lasts"></a>How long a borrow lasts | Until its last use, not until the end of the block: after the last line that uses `first`, what `first` borrowed from is free again. Decided on 12 November | Today's Rust (since 2018). The rule the user learns is one sentence either way; "until the end of the block" is simpler for the compiler but rejects much correct code and makes people open blocks only to end a borrow. No cost at run time in either |
| <a id="borrows-that-do-not-go-together"></a>Borrows that do not go together | While a variable holds a borrow and is used again later: with a `read` borrow the place cannot be changed, moved or lent as `ref`; with a `ref` borrow it cannot be touched at all. A variable gets a borrow from `read x` / `ref x`, a range of text, a lent item (`names[0]`), the names of a `match` or `is` pattern, a copy of another borrow, and a call that returns a borrow. Fields are told apart (`ref p.x` and `read p.y` go together), items of a collection are not. A use in the other branch of an `if` or `match` does not count as later; a use anywhere in a loop does, unless the variable is declared inside the loop. In one call the same place is not lent twice when one of the two is `ref`, and what a part of a call lends (the receiver, an argument, the value an index or a range looks into) lasts until the call runs: a later part may read it, and changing or moving it is an error, with no exception for plain data (decided on 19 November, 1340 and 1347). An item a `for` lends borrows the collection; after an `if`, a `match` or a loop a variable borrows what it borrowed on any way that reaches there, and a borrow a round leaves is held into the next round; writing through a `ref` variable is a use of it; what `lock` and `read ... as` open is lent for their block only; a `ref` reached through a `read` borrow only reads; a `Disposable` value that borrows uses the borrow where its block ends; what a `shared checked` value holds, looked at where it lies, is lent until its line ends (1340, 19 November). Made rules, not cases, after the second review (1592, 20 November): a `break` or `continue` ends the blocks between it and its loop, as their ends do; a `ref` given on as it is, or copied into a variable, lends again what it borrows, to be changed, and goes with no other borrow of it in the call; a `ref` field reached through a `read` borrow is not given on as a `ref`; giving away, as `ref` or by value, a value that holds a `ref`, calling its `ref this` method or its `dispose` changes what it borrows; a part of a value with no name carries what that value borrowed; the parts of every value computed from left to right (a struct, `with`, a variant, a list, `==`, `??`, `$"..."`) are lent until it is made, as those of a call; an argument that looks at a place another one lends as `ref` is an error; a borrow put where no variable of the function is, or behind a `ref` field, is held by what that place borrows; the names `for`, `is` and `match` give out of a `shared` value end with their statement; a value that holds a `Disposable` anywhere by value uses its borrows where it ends and where it is written over; a `while`'s condition is part of each round. A range lent as `ref` (`ref xs[0..2]`) lends its whole list or array to the call, as an item does: beside the place itself it is an error, as in Rust (1610, 21 November). Two windows or items of one place, one of them `ref`, go together when they share no item, held by two variables or given to one call: `var a = ref xs[..k]` beside `var b = ref xs[k..]`, `swap(ref xs[i], ref xs[j])`; that they share none is checked when the second is taken, a panic if they do, and where their ends are numbers when the program is compiled; a field of an item counts as the item (2011-2015, 26 November). The variable must be declared with its window and given no other. A field or an item that only carries a borrow (a `Word<from source>` in a list) is not behind one: lending it, or writing into it, is a borrow of its owner; a variable declared with a borrow (`var all = ref names`) lends what it borrowed, so beside its place in one call it is that place lent twice (195, 26 November). Pointing a `read` variable elsewhere frees what it held. Decided on 12 November | Rust's rule. A value read for an argument is not a borrow, so `xs.add(xs.length())` is fine |
| <a id="a-borrow-does-not-outlive-its-owner"></a>A borrow does not outlive its owner | A function that returns a borrow returns one that comes from a borrowed parameter: with one such parameter nothing is written, with more `from a, b` says which (leaving it out is a compile error that shows what to write; it may name fewer than are borrowed, and it may be written with one). `from` is checked in both directions: inside, every returned borrow comes from a named parameter; at the call, the result borrows only from the named arguments. Returning a borrow of a local or of a parameter taken by value is a compile error; with no borrowed parameter only a constant can be returned. A variable cannot keep a borrow of something declared in an inner block and be used after that block. A built-in method that returns a borrow lends from its receiver; a call through a `Func` value from every borrow it was given. Decided on 12 November | Rust's lifetime rules with the design's notation: the source is named, not a lifetime |
| <a id="var-and-a-borrowed-variable"></a>`var` and a borrowed variable | `var kept = a`, with `a` a `ref int` or `read int`, copies the number: a borrowed variable used as a value is the value behind it. A second borrow is written `ref a` / `read a`. What cannot be copied (`read string`) is copied as a borrow, and a call that returns a `ref` keeps it (`var slot = map.getOrAdd(key, 0)`). Decided on 12 November | It used to make a second borrow silently, and a swap written with it was wrong. C#'s `var` copies too |
| <a id="following-a-type-that-carries-a-borrow"></a>Following a type that carries a borrow | A value of a type with a source (`struct Word<from source>`) is followed like a `read` variable: it keeps what it borrowed from until its last use; so does a list or a map of such values and a struct built from them. `from source` in a method means what the value holds, not the value: after `var word = words.next()` the `words` is free. Lending a field that is itself a borrow (`this.input[a..b]`, `word.text`) lends what the field borrowed. A type that holds a type with a source names a source too, and a type that names one holds something that borrows. A function with no borrowed parameter that returns such a type writes no `from`. One source per type for now. A borrow from outside is not stored through `ref` (`this.input = other`): no notation for it for now; a value is built where its source is known. Decided on 12 November | What the ["Types that carry a borrow"](#types-that-carry-a-borrow) row left unsaid. `where r from name` went away with `where`, and nothing written so far needed it |
| <a id="owned-values-in-compiled-code"></a>Owned values in compiled code | The checker decides who owns a value and the back end follows it: an owned value is freed where its variable ends, on every way out of the block; a use that moves the value empties the place it leaves, so the later free finds nothing to do. No garbage collector and no reference count. A text constant is never allocated or freed. A `read string` is a pointer and a length, a `string` a pointer, a length and a capacity. An owned value without a name lives until the end of its statement. If memory runs out the program stops; there is no notation for handling it. An index and a range of text are checked in every build, the character boundary of a range too (its cost could not be measured). Decided on 12 November | Emptying the place on a move is the simplest correct form (a value moved in only one branch needs nothing more), and the C compiler removes most of the tests. Stopping when memory runs out is Rust's default too |
| <a id="a-slice-that-may-be-missing"></a>A slice that may be missing | *Decided and built on 23 November 2026, in the 161st slice (choice 1774).* `read T[]?` is a window that may be missing: a function gives one back (`read byte[]? header(read this, read string name) from this`, `return null`), takes one (`null` or a slice), and a struct that carries a borrow holds one; `is null`, `is not null`, which narrows it to the window, and `??` look into it, and a list of windows gives one from `get` and `removeLast`. Only `read`: a `ref T[]?` and a `T[]?` alone are compile errors. In C it is the window, of length -1 when it is missing, as a `read string?` is; nothing is copied | A lookup that lends gives what it found or nothing, as Rust's `Option<&[u8]>` and Zig's `?[]const u8`; without it each such function gave an empty slice or a position. No `ref T[]?` until a program needs one |
| <a id="a-field-from-another-and-formatted-text"></a>A field from another, and formatted text | *Built on 23 November 2026, in the 162nd slice.* In a method of `ref this`, one field is written from another (`this.out.addAll(read this.extra)`), as in a function; writing a field from itself (`this.out.addAll(read this.out)`) stays an error. `$"...".toString()` gives text of its own, which carries no borrow of what was formatted into it, so the borrows it read end where it is made | The checker had taken both for a field written into itself, or the text for a borrow, though no byte is shared |
| <a id="a-borrow-that-may-be-missing-in-compiled-code"></a>A borrow that may be missing, in compiled code | A `read T?` is a pointer to the `T`, null when there is nothing; for text it is the pointer and the length of a `read string`, and for a slice its window (1774), with the length -1 for nothing. A function that gives one back (`read Product? get(...) from this`), `list.get(i)` and `map.get(key)` give a pointer into what they were lent, and nothing is copied. Where a `T?` that is kept is lent (`read account.limit`), its flag is tested once, there. A `ref T?` stays a pointer to the flag and the value, because `null` can be written through it. Decided on 13 November | What would be written in C by hand, and no cost that grows with the size of the struct. The other form (a flag and a copy of the value's bytes that nobody drops) kept `read T?` and `ref T?` in one shape but copied a `T` on every call; an optimised build removed that copy where the function was inlined, a debug build did not (4.75 s against 3.66 s for three hundred million lookups of a struct of 128 bytes). Cost: the two borrows of a `T?` have different shapes in C, which is not seen from the language |
| <a id="borrows-and-function-values-in-compiled-code"></a>Borrows and function values in compiled code | A field that borrows is a pointer to what someone else owns (for text a pointer and a length); it is never freed with the value that holds it, and `<from source>` leaves no trace in the compiled program. Looking at a field that itself borrows gives the pointer the field holds. A function value is the address of the function, and a call through it is an indirect call. A field of a value that has no name can be read (`longer(a, b).text`): the value is kept for the statement. Decided on 12 November | The checker did the work at compile time; at run time this is the pointer a C programmer writes. Rust's lifetimes and `fn` pointers cost the same: nothing |
| <a id="shared-cycle"></a>`shared` cycle | It cannot be made a compile error: a tree without cycles also contains itself in its type. In test and debug builds, `shared` objects still alive when the program ends are reported: the count, the line where they were created, the field through which they hold each other, and the hint `weak`. No report in release | Rust counts a leak as safe and does not report it, an outside tool is needed. Cost: in release a leak stays silent. Example: [cities and roads](../05-examples.md) |
| <a id="share-and-null"></a>`share` and `null` | `share x` gives `null` if `x` is `null`, whether it is `weak` or not: `share cur.parent`, `share map.get(id)` | So that `if x is null` does not have to be written everywhere. `null` still stays `null`, nothing is hidden |
| <a id="a-borrow-of-a-value-with-no-name"></a>A borrow of a value with no name | It cannot be kept: `var part = make()[..5]`, `var label = make().label()`, `return first(read make())`, and the same put into a field or an item are compile errors whose hint is to give the value a name. Inside one statement it is fine (`print(make()[..5])`). A text constant is exempt | The value a call returns lives until its statement ends, so a borrow kept longer looks at freed memory; compiled code showed it under the address sanitizer. Rust has the same rule ("temporary value dropped while borrowed"). Core principle: caught at compile time, with the fix in the hint. Approved on 13 November 2026 |
| <a id="what-a-loop-moved"></a>What a loop moved | What is moved after a loop is what was moved where a `break` left it, and, unless it is `while true`, before its first round and where each round ended or a `continue` went on: a loop may run no round or end after any. Each `continue` starts a round, so what it leaves moved is checked as the end of the body is. Found in the hundred-and-sixth slice and approved on 18 November 2026 (choice 1157) | Before, a value moved before a `continue` or a `break`, or moved before a loop that gives it back, was taken as there: the interpreter stopped on it and compiled code read an emptied value. Rust's borrow checker follows every way out the same way |
| <a id="a-borrow-read-by-the-right-side"></a>A borrow read by the right side | A borrow that the right side of an assignment reads last ends before the write: `b = Box { n = r.n + 1 }` where `r` borrows `b`, `while s is Circle(r) { s = Shape.Circle(r + 1) }`, `t = part.clone()` where `part` is a range of `t`. Approved on 14 November 2026 | Rust accepts the same. They were refused with "`b` cannot be changed here" |
| <a id="the-place-after-the-right-side"></a>The place after the right side | What the place of an assignment uses counts as used after the right side: a borrow read by the place (`counts[r.length()] = grow(ref xs)`) or written through (`r.x = grow(ref ps)`) cannot have its owner changed by the right side, and the error has a note saying the right side is computed first. Inside the place the parts keep their order from left to right. Approved on 14 November 2026. The same holds for a move: a place reached through a variable or a field that the right side moves (`a.next = a`, `a.next = new Node { next = a }`, `h.node.next = h.node`) is refused, since nothing is left to write into and a value cannot be put inside itself; built on 27 November 2026 (`error_assign_into_what_it_moves` and two others) | Follows from the order: the place is found after the right side, so a borrow it uses must still hold then |
