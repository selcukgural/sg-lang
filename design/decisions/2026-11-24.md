## 166. A `jq` of JSON, and what it asked of the language

The author's word for the trials, given at its start and kept for all of them: they are ruthless, and push
the language to its limits as the world will (a text of 100 MB, ten million members, 10,000 levels, bad
UTF-8, numbers past a `double`, a million calls deep, a closed pipe), and nothing is left out because SG is
weak there. Approved before the slice:

1804. **What is written**: the jq people use. Paths (`.`, `..`, `.a`, `."a"`, `.[n]`, `.[a:b]`, `.[]`, `?`),
     `|`, `,`, `//`, `as $x`, `reduce`, `foreach`, `if`, `def` with filter arguments and recursion, `|=`, `+=`
     and their kin, `"\(...)"`, all of the arithmetic, the functions of `trials/jq/README.md`, and the flags
     `-c -r -n -s -e -S --tab --indent --arg --argjson`.
1805. **Numbers as jq writes them**: a number read and not changed keeps its literal, written as decNumber
     writes it (`1e1000` → `1E+1000`, `2.0` stays, 21 digits stay); a number computed is a `double`, written
     as jq writes one. What a library does not give, each program writes itself.
1806. **The input is a stream** of values one after another, read in pieces of 64 KB, so that `tail -f | jq`
     works. *(The `Json.parseNext` approved here was built, then left out for 1814, which does more.)*
1807. **One algorithm in the three**: the filter read into a tree and evaluated by walking it, with stacks of
     its own on the heap.
1808. **The cases**: speed (records, a record a line, numbers, 1 GB), limits (a text of 100 MB, an object of
     ten million, 10,000 and 10,001 levels, ten million sorted, a `def` a million deep and ten million in tail
     position, a pattern that backtracks, `| head -1`) and what is broken (bad UTF-8 of each kind, a lone high
     surrogate, `\u0000`, a byte order mark, CR LF, 1 GB cut off, an error in the middle, numbers past a
     `double`, jq's quirks).
1809. **jq 1.8.2 is what is right**: each case is held to its output and exit code, on macOS and Linux; a case
     SG fails is a choice and a fix, never taken out.
1810. **jq and jaq measured beside**, as references; where SG loses, it is published.
1811. **Where**: `trials/jq/{sg,rust,zig}`, the results in [Programs](../../benchmarks/programs.md).
1812. **The other trials looked at the same way**, in a slice of their own after this one.

Approved during the slice, from what it found:

1813. **`x.makeUnique()`** on a `shared T`: a `ref T` of what `x` points to when `x` is its only owner and
     nothing looks at it; otherwise a copy (`clone`) that `x` owns alone from then on, the old one let go.
     Rust's `Rc::make_mut`. Found by `reduce range(0; 1000000) as $i ([]; . + [$i])`: a `shared` value is only
     read, so each step copied the whole array: SG did not end in 300 s, jq took 0.26 s. Now 0.11 s.
1814. **`JsonReader`**, a reader of the tokens of JSON (A, of two ways put): the tokens of values one after
     another, a number as it is written, a name given twice and a number past a `double` left to the program,
     which builds values of its own; it keeps where it is and what is open, not the text, so the text may
     grow between calls, and with `more` a token that reaches the end of the text is `UnexpectedEnd` with the
     reader left as it was. Found by the numbers jq keeps (`1.10`, `1E+1000`, 21 digits), the names jq takes
     twice, and the second tree a parse built before the program's own. The other way put (B): three options
     of `Json.parse`.
1815. **A stack that overflows is told**: compiled code ended with a SIGSEGV and no word; now each thread has
     a stack of its own for signals, and a fault at the guard below its stack prints `panic: stack overflow`
     and ends with 1. On Windows, `EXCEPTION_STACK_OVERFLOW` the same way.
1816. **The methods of `string` take a `read shared string`** where they look for a text, as a parameter of a
     function does.
1817. **`try` inside a call's argument in compiled code** (`args.add(try f())`): the interpreter ran it, and
     compiled code asked for a name, since a `try` there leaves the function after the parts before it are
     made. Built the narrow way: the first `try` of a statement, reached through calls, methods and variants
     alone (so it always runs), with nothing before it but literals, constants and reads of variables it does
     not name (a receiver or a borrow by where it lies), is computed before the statement under a name of
     its own; running it first then changes nothing. After an index (which may panic), a call, a field or a
     variable whose value is moved, it is still refused: `lists[3].add(try word(1))` panics before `word`
     runs (`panic_try_after_index`), and running `word` first would print what the program never prints.
1818. **`Clonable` before `makeUnique`** (A, of two ways put): `: Clonable`, decided on 15 November and never
     built, is built: `.clone()` of a struct or an enum written `: Clonable` (or `: Copyable`) copies it field by
     field, calling a `clone` a field's type writes itself; of a `List`, a `HashMap` and a `HashSet`, item by
     item; through a `T*`, the `T`; a `shared` value is one more owner and a `weak` one one more looker. A type
     that writes its own `clone(read this)` is cloned by it. The other way put (B): Rust's `Rc::get_mut`, with
     the copy left to the program.
1819. **Fair: each language its own way, the algorithm the same.** Each version uses what its language has
     and its programmers use; what is a way of working (the single outputs at once of the Zig version, the
     values built from the tokens) goes into all three, or into none.
1820. **What the language walks, it walks with a loop**: `drop`, `clone`, `==`, `compare`, `hash`, the writing
     of a value and the JSON writer, with a list of their own on the heap, so that no value however deep
     overflows a stack. *For slice 167*, as the order approved puts it: 1821 already runs the trial's ten
     million levels.
     *First built after the slice, in the interpreter:* a value is let go there with a list of its own, at
     the end of a scope and where a place is written over, since Rust's drop let go of it by recursion and a
     chain of ten million links ended the interpreter with `fatal runtime error: stack overflow, aborting`,
     no panic. The parts only the value holds are taken apart, each let go in the order the recursion
     had, so a `Writer` inside still writes where it did; a `Disposable` struct is let go as before. A
     chain and a tree ten million deep are let go in 3.5 and 4.0 s; a loop that makes and lets go of a
     struct with a list 200,000 times takes 2% longer (0.195 s to 0.199 s). Compiled code already lets go,
     compares, copies and writes ten million levels on its stack of 1 GB (1821).
1821. **A stack of 1 GB** for `main` and for each task, taken by the system a page at a time as it is used (as
     the interpreter has always run); where the system gives no such thread, 8 MB, as before. With 1815, the
     bound and its word that Go's stacks have.
     *Tried on Windows 11 on Arm:* a million calls deep run, and a recursion that does not end says
     `panic: stack overflow` and ends with 1, in `main` and in a task.
1822. **`(?x)` in `Regex`**: spaces and `#` comments to the end of a line passed over outside a class, as
     Perl and PCRE have it; `\ ` is a space. `(?m)` and `(?s)` were there already, which jq's flags needed
     with it. *Found while it was tested against Rust's `regex`:* Rust passes over spaces and `#` in a class
     too, so `[ ]` is an error there; SG keeps them, as the choice says and as jq's Oniguruma does. Rust reads
     spaces in a count, `a{ 2 }`, and so does SG under `(?x)`; without it `{` that starts no count stays a
     `{` of the text, as in Go.

Approved at the end of the slice, from what its measurements and tests found; none is built in it:

1823. **The interpreter's bound on nested calls follows its stack**: the fixed 5,000 calls gives way to a
     bound measured against the interpreter's stack of 1 GB, as `stack_room` measures a value, so that a
     program compiled code runs a million calls deep runs in the interpreter too (`the_trial_of_jq` runs its
     comparison 10,001 deep compiled only until then). *Next, before slice 167.*
     *Built after the slice:* before each call the interpreter looks at how much of its stack is left, as
     it does before it walks a value, and its panic says what compiled code says, naming the call. A
     million calls did not fit as the choice hoped: a call took the interpreter 36 KB of its stack, and the
     5,000 calls had hidden that. The walk was made smaller (below), and a call now takes about 2.5 KB, so
     about 380,000 calls fit on macOS on Arm; compiled code takes fewer bytes a call and goes past a
     million. The comparison 10,001 deep of `the_trial_of_jq` runs in the interpreter too.
1824. **A number's `double` worked out the first time it is wanted**, as the Zig version of `jq` does, in
     all three (1819): reading 100 MB of numbers takes SG 1.62 s and Zig 0.51 s. *In a slice of its own.*
     *Built in [slice 171](#slice-171)*, the three made one way by 1837.
1825. **A whole number written as an integer first**, as the Rust version of `jq` does, in all three (1819);
     SG's writer of a `double` then makes no text of its own for each number. *With 1824.* *Built in
     [slice 171](#slice-171)*, in SG and Zig.
1826. **`JsonToken` is `Formattable`**: `print(token)` writes `BeginArray`, `Name("id")`, `Number("1.50")`.
     *Next, with 1823.* *Built after the slice*, the text in quotes and escaped as any text a value holds
     is: `String("x\ny")`.

Built without a choice:

- **A fix in compiled code**: a `shared string` lent where a `read string` goes (a variant's text passed to a
  function) gave C a `string*` where it wanted a view; the C compiler refused the program. Found by the first
  build of the trial; the interpreter was right. Test `ok_shared_text_lent`.
- **`sort` merges the runs the items already make**, found by `[range(10000000)] | sort`, which took SG
  1.21 s and 965 MB against Rust's 0.24 s and 310 MB: `sg_sort` merged pairs of one item, then of two, and
  so on, whatever the order the items had. It now finds the runs in order and the runs strictly in the
  reverse order (turned round, which moves no equal items past each other), makes a short run 32 long by
  putting each next item in its place, and merges the runs two by two, copying two that are already in
  order; Rust's and Python's sorts work so. Items in order now take 0.37 s and 325 MB; in no order, as
  before. The interpreter does the same, each `compare` in the same order (choice 1337), so a `compare`
  that gives no single order still leaves the same items in the same places in both. Tests `ok_sort_runs`
  (nine patterns, each size to 200 and three larger, in order and stable; with the reversal of runs that
  are not strict it finds 234 places wrong) and `ok_sort_no_order`, whose items now lie elsewhere, the
  same in both.
- **A stack for signals the thread has already is kept**: the address sanitizer gives each thread one and
  lets it go itself; `sg_guard_thread` put its own in its place and the sanitizer then failed to let go of
  memory it had not made. Found by the tests under the sanitizers. The sizes of the stacks may be given
  when the C is compiled (`-DSG_THREAD_STACK=...`), as `large_frames_touch_their_stack` does to keep its
  stack of 8 MB.
- **The thread `main` runs on lets go of its block for printing** when it ends, as a task's thread does: on
  the first thread the block lived until the process ended, and on a thread of its own (1821) the leak
  checker of Linux found it left behind in every program with tasks. The stack for signals is pages of the
  system (`mmap`), as Rust's runtime takes them, not a block of `malloc` a finder of leaks reports.
- **`_GNU_SOURCE` on Linux for every program with a system**: the guard of 1815 needs `pthread_getattr_np`
  and `sigaltstack`, which strict C11 hides. Found by the tests on Linux.
- **The interpreter's walk takes less of its stack** (after the slice, with 1823): the arms of an expression
  and a statement that a program meets less often are functions of their own, so that the frame every
  call goes through holds only what the common ones need, and an error passed back is boxed, so that
  each result is 64 bytes, not 112. A call of a function went from 36 KB of stack to about 2.5 KB; the
  time of a recursion and of a loop did not grow (0.205 s to 0.199 s, and 0.134 s to 0.130 s). A
  plain call no longer looks at the names of the built-in functions first.
- **The trial**: `trials/jq/sg` (eight files), and the Rust and Zig versions, each held to jq 1.8.2 by its
  own suite of differences (3,571 and 6,013 cases) and by `trials/measure.py jq --check`. What jq 1.8.2 does
  that the first specification did not say is in `trials/jq/README.md`.

Tests: `ok_clonable`, `ok_shared_make_unique`, `ok_shared_text_lent`, `ok_shared_text_methods`, `ok_json_reader`,
`error_clonable_field`, `error_clonable_own_clone`, `error_make_unique_checked`, `error_make_unique_read`,
`error_make_unique_not_clonable`, `ok_regex_extended`, `ok_try_in_argument`, `panic_try_after_index`; in `cli.rs`
`a_stack_that_overflows_is_told` (in `main` and in a task, and a million calls deep that fit) and
`a_try_is_computed_first_only_after_reads`; `ok_sort_runs`; `the_trial_of_jq` in `cli.rs`. After the slice:
`ok_json_token_print` (1826), `panic_stack_overflow` with the new words, `a_stack_that_overflows_is_told`
with the interpreter in `main` and in a task and a hundred thousand calls that fit, and `the_trial_of_jq`
comparing 10,001 deep in the interpreter (1823); `a_deep_value_is_let_go_without_a_deep_stack` in
`interp.rs`, a million levels of each kind on a stack of 256 KB (1820).

## 167. What is walked, walked with a loop

Choice 1820 as the measurements of the night before narrowed it: compiled code already lets go of, compares,
copies and writes a chain of ten million links on its stack of 1 GB (1821), and the interpreter stopped
below a million with a panic, after it had ended without a word in letting go of one (built before the
slice). Approved before the slice:

1827. **Compiled code is not changed**: its stack of 1 GB holds ten million levels and more, and a value
     deeper still ends in the panic of 1815. A walk with a list of its own there would cost every ordinary
     value something, for depths only a value made to be deep reaches; a walk that changes to a list past a
     depth stays for a trial that asks for it.
1828. **The interpreter's other walks with a loop**: writing, `clone`, `==`, `compare` and the keys of
     `HashMap` and `HashSet`, so that the interpreter walks what compiled code walks, as deep.
1829. **The JSON of `std` read and written with a loop**, `Json.parse` and `toJson` both. `maxDepth` stays the
     bound, 128 unless said; it no longer takes stack, so `maxDepth = 1000000` reads and writes a million
     levels.
1830. **The 2% of letting go with a list** (a loop that makes and lets go of a struct with a list 200,000
     times, 0.195 s to 0.199 s) is taken.

Built:

- **Writing** a value keeps a list of what is left to write (text, a value, a part read when its turn
  comes); a type's own `format` is called in the order the recursion called it. A chain of a million links is
  written in 0.11 s by the interpreter's release build; it was a panic.
- **`clone`** keeps a list of the values being made, each with what it is copied from and the copies of its
  parts so far; a type's own `clone` is called where the recursion called it.
- **`==`** keeps a list of the pairs of parts left to compare, the first on top, so a type's own `equals` is
  called in the same order and the first difference ends it as before.
- **A key** of `HashMap`, `HashSet` and of `compare` is one list: the parts of a struct or an enum inside
  another lie between a `Begin` and an `End`, and `End` is below every part and `Begin` above every part that
  is not a struct or an enum, so the order is the one the tree of keys had (a unit test holds it to that). It
  is made with a loop, and hashed, compared and let go of as a list.
- **Letting go**: a map, a set and what is left in a channel are taken apart by the list of the first part
  too. A map or a set holding a chain of ten million links ended the interpreter without a word, and so did
  a channel that held one when it ended.
- **`Json.parse`** reads the items of an array or an object in a loop of its own, as the recursion did,
  until an array or an object that is not empty starts in it; that one goes on a list with the name of its
  member, if it is one, and is given to its own when it ends. An empty `[]` or `{}` is read as an item. The
  errors and where they are found are the ones the recursion found, a name given twice told once its value
  is read. **`toJson`** writes the items of each in a loop of its own, the arrays and objects open on a list
  of borrows.
- **What it costs**, compiled, against the recursion, best of nine, Apple M3 Max: the coordinates read and
  summed 0.348 s to 0.352 s (1%), the records 0.471 s to 0.485 s (3%), read and written back 0.611 s to
  0.634 s (4%), and a document on each line 0.391 s to 0.414 s (6%): each document takes a list for what is
  open, where the recursion took nothing. Variants tried and dropped: the containers on one list with their
  kind on another (records 4%, lines 10%); every value through one loop (7%, 9%); the member's value put in
  the object at once and changed when read (4%, 6%, coordinates 1%); the name on the list of what is open
  (2%, 5%, coordinates 5%).
- **A million levels**: compiled, `Json.parse` and `toJson` read and write an array and an object a million
  deep, and refuse each one level past a `maxDepth`, in 0.8 s all told; the interpreter in 138 s, about
  14 µs a level at its own pace, where the recursion of before had not ended 25,000 levels in five
  minutes.

Approved at the end of the slice:

1831. **`JsonValue.equals` and `JsonValue.clone` stay as they are**: functions of `std` that call themselves,
     so they go as deep as a stack of 1 GB holds and say so when it is full, as every recursion of a program
     does (1815); about 380,000 levels in the interpreter. A loop there waits for a trial that asks for it.
     The cost of reading with a list, above, is taken with 1829.

Tests: `ok_deep_value_walked` (in place of `panic_deep_value_written`: a chain of a million links written,
compared, copied and searched for, in both), `ok_json_deep` (an array and an object 5,001 deep read and
written back, and one level past `maxDepth` refused at the byte it was before), and in `interp.rs`
`a_deep_key_is_made_compared_and_let_go_without_a_deep_stack` (a million levels on a stack of 256 KB) and
`a_key_of_parts_is_in_the_order_of_its_tree`.

## 168. A recursion as deep as the stack holds, then a list

Slice 167 read and wrote the JSON of `std` with a list, at 1% to 6% of the time of the recursion. A
recursion is the fastest way to read and write a tree, and a list is the way that has no bound but memory;
this slice takes the one until the stack runs low and the other after it. Approved before the slice:

1832. **Where the list takes over is where the stack runs low, not a number of levels.** A number cannot be
     right everywhere: a level takes another size of stack in the interpreter and in compiled code, in a debug
     build and a release build, with GCC and with Clang; the program may be deep in a recursion of its own
     when it reads; and a thread of compiled code that cannot have 1 GB has 8 MB. So the recursion goes on
     while more than an eighth of the thread's stack is left, and the part of the value below gives itself to
     the list of 167. Approved with a look every 1,024 levels; built with a look every 16, since a level of
     the interpreter's debug build takes about 16 KB, and 1,024 of them would not fit between an eighth and
     the sixteenth it keeps free. A look is an `&` and a comparison of a number the recursion has already;
     the stack is asked only at the sixteenth level.
1833. **`System.stackLow()`**, for `std` alone: no more than an eighth of this thread's stack is left. In
     compiled code each thread notes where that is when it notes its stack's guard (1815, `sg_stack_mark`,
     from `GetCurrentThreadStackLimits` on Windows), and a thread that did not, such as one of a C program
     that calls SG, is never low. In the interpreter the mark is kept with the stack's size, so a sixteenth
     of a stack of 1 GB is still the 64 MB it keeps free for its own walks.
1834. **JSON first**: `Json.parse` and `toJson` read and write by calling themselves, with `jsonValueDeep`
     and `writeJsonDeep` (the lists of 167) where the stack runs low; the three measured side by side. The
     walks of the interpreter (writing, `clone`, `==`, `compare`, keys, letting go) stay as 167 made them
     until their cost is measured.

Built:

- **Where the list takes over**: compiled in a release build, about 1.7 million levels down in reading,
  and a text 3 million deep written by the recursion alone; in a debug build 1.1 million and 1.8
  million; in the interpreter 150,000 to 240,000. A text 3 million deep is read and written back compiled
  in 1.3 s. The errors are the ones the recursion finds, at the same bytes, with the `maxDepth` that was
  given.
- **What the deep part calls**: a value that is not an array or an object is read by `jsonValue` and written
  by `writeJsonValue` there too, and a member goes into its object through `jsonMember`, so the deep path
  repeats none of them.
- **What it costs**, compiled, best of nine, Apple M3 Max on its battery, a program that also looks a member
  up and adds one: against the recursion of before 167, the records read and summed -0.2%, read and written
  back -1.5%, a document a line -0.5%, the coordinates +0.2%; the list of 167 +1.4%, +1.4%, +4.8%, +3.4%.
  In `trials/std/json`, which never calls `get` or `add`, the recursion was 1.4% to 2.6% faster still: there
  `JsonObject.find` and `append` have one caller, which Clang puts them into, and the deep path gives them a
  second; a program that calls `get` loses that in the recursion as well.
- **The interpreter passes a borrow on as what it looks at.** `ref position` with a `ref nint position`
  made a borrow of the borrow, so a recursion that passed its `ref` on read each step through every one
  before it: 2,500 levels of `Json.parse` took 7 s, 10,000 took 125 s. A borrow of a place that holds a
  borrow is now one of what that looks at, as its type always said (`Ty::strip_borrow`); the 10,000 levels
  take 0.64 s, and a million are read and written back interpreted in 68 s, where 167's list took 138 s.

Tests: `ok_json_stack_low` (arrays and objects 1,000 deep, whole and broken below where a small stack runs
low: one level too deep, cut, more text after, a wrong byte, a wrong closer, a name given twice with a
number and with an object, and arrays written with an indent, each line as far in as it is deep); in
`interp.rs` `json_goes_on_with_a_list_where_the_stack_runs_low`, the same on a stack of 16 MB (debug) or
3 MB (release), its output the same bytes and the list taken at least 18 times; in `cli.rs`
`json_compiled_goes_on_with_a_list_where_the_stack_runs_low`, Linux, the same compiled (debug and release)
under `ulimit -s 1024 -v 800000`, where `main` cannot have its 1 GB and runs on 1 MB, and a recursion a
million deep overflows there to show that it does.

## 172. The three versions of `jq` held to jq 1.8.2 by both suites

The suites of slice 166 were written one with the Rust version (3,681 cases) and one with the Zig version
(6,128), each version run on the suite written with it. Run each on the three, they found what one version
did and another did not: SG failed 3 cases of the Zig suite, Rust 29, and Zig 69 of the Rust suite. Each
was taken back to what jq 1.8.2 does and made the same in the three; probing round them found more, which
the three had alike.

- **jq 1.8.2's grammar** (its `parser.y`): `Expr as $x | Query` binds the whole expression on its left, so
  `1 + .a as $x | $x | . * 2` is 8, and a binding or a `def` may stand after `,` and take the rest (`1, .a
  as $x | $x, 9 | . + 1` is `1 4 10`); `-` before a term makes a term, so `-1 as $x | $x, 2` is `-1 2`;
  `reduce` and `foreach` read from an expression, `try` takes a term. SG read none of these, Rust and Zig
  bound only a term; Zig also read `-a * b` as `-(a * b)` (`-0 * 1` gave `-0`).
- **Paths through what is not a path**: a value made by `reduce`, a variable or `last(f)` stands where its
  input stood when it is that input, as jq's `jv_identical` tells (`path(reduce empty as $x (.; .))` is
  `[]`). Zig had it; Rust had it for `null`, `false` and `true`; SG had it for constants only. `last(f)` of
  no output gives none (jq 1.8.2's `last` is its own, not `reduce`): Zig gave `null`.
- **Constant keys**: jq folds constants when it reads a filter (literals, `[c, ...]`, `{"name": c}`, an
  operator on two constants that gives no error) and refuses a constant key that is not a text then, exit
  3: `{(1 + 1): 2}`. The three folded only a literal.
- **Rust**: a `double` exactly halfway between its two shortest neighbours was written with the upper one
  (Rust's shortest digits round a tie up, jq's `dtoa` to even: `1e15 + 0.3` is `1000000000000000.2`); a
  closed pipe ended it with 0 where jq dies by SIGPIPE (Rust's runtime ignores the signal: it is put back
  and raised); after a file that could not be opened it read on past the value of the next file where jq
  stops (a large value was handed on only once the next file was opened); a space before a part of a byte
  order mark took the part for the start of the input.
- **Zig**: `isempty`, `has` of `null` and of a fraction, `test([re, flags])`, `.[null]`, a slice by an
  object without both `start` and `end`, `..` calling the program's own `def recurse`, a bad byte before
  `\"` in a text, a part of a byte order mark ending the input, `range` with NaN, decNumber's infinity
  (`1E+1000` and `"infinity" | tonumber`) sorted above every double, and comparing `{}` under 10,000 arrays.
- What each version offered that the others did not is taken away: Rust's `while` (it was its prelude's,
  for `range/3`) and SG's `paths(f)`. `isempty(g)`, `infinite` and `nan`, which the three have, are in the
  list of `trials/jq/README.md`.

1839. **The two suites are kept in the repository**, in `trials/jq/tests` (`filters.py` from the Rust
     version, `streams.py` from the Zig version), with what this slice found as cases of `streams.py`
     (jq's grammar, constant keys, paths through what is not a path, ties of doubles, parts of a byte order
     mark). They run by hand against jq 1.8.2 on the `PATH`, as the conformance of HTTP does, not in `cargo
     test`, which does not have jq; `the_trial_of_jq` keeps its own cases. `test("(a+)+$")` on a long run of
     `a`, which jq gives up on and SG's and Rust's expressions answer, is counted as meant in both.

Measured, each version against itself before, best of five (and nine where they differed), Apple M3 Max,
the same output from the six builds at 1, 10 and 100 MB: nothing moved by more than the noise but Rust,
which carried the value a path stood on inside each track and became 4% slower writing ten million
numbers; held behind an `Rc`, the track is two words again and Rust is 3% to 4% faster than before
(`range(10000000)` written 0.398 → 0.388 s, `range(10000000) | . / 2` 0.809 → 0.773 s). SG's `sort_by` of
100 MB of records 1.44 → 1.35 s, its writing of ten million numbers 0.161 → 0.151 s; Zig within 1%.

Tests: each version passes both suites (3,681 and 6,389 cases), `measure.py jq --check` and
`the_trial_of_jq`.

One difference is left, in the three alike: a whole number of up to 15 digits read is held as its value
(1837), never as the same value as another, so `1 | path(. as $v | $v)` is an error where jq gives `[[]]`.

## 173. `Regex` held to Rust's `regex` and to PCRE2, and bytes that are not UTF-8

The other trials looked at as `jq` was (1812): not `wc` and `grep` copied flag for flag from GNU's, which
would teach the language little, but what they lean on held to the engines in SG's lane and pushed with
inputs that break things. Random patterns, each written three ways that mean the same, and texts were
run through SG's `Regex`, Rust's `regex` and PCRE2 (from Zig, which has no regular expressions), and Go's
`regexp`, whose syntax `Regex` follows, before them: two million cases of text, short, long and made
to overflow the DFAs, gave no case where SG differed from Rust and PCRE2 agreeing, and no pattern both
compiled that SG refused. What differs is each engine's own: Rust's `regex` leaves the groups inside a
`{0}` out of `captures` and refuses a program past 10 MB; PCRE2 backtracks to its limit and does not fold
`\p{Lu}` under `(?i)`; SG compiles some large patterns both refuse. Go repeats the atom before a group of
flags alone (`a(?m)+` is `a+`), refuses nested counts past 1000 in all, and takes a name given twice.

The inputs that break things found one gap. A line that is not UTF-8 stopped the three `grep`s at the
first bad byte, exit 2, where GNU's `grep` and `ripgrep` go on: SG had no way to read a line as bytes nor
to search bytes, the second left waiting by 1470 until `grep` asked for it. Rust has `read_until` and
`regex::bytes`, PCRE2 `MATCH_INVALID_UTF`. A closed pipe ends SG's `grep` silently with SIGPIPE, as C's
tools end; Rust's says `Broken pipe` and ends with 2, Zig's with 1. Zig's `grep` stopped at a line past its
buffer of 1 MB, which SG and Rust read whole.

1840. **Bytes that may not be UTF-8, read and searched**: `reader.readLineBytes(ref List<byte> line)` (and
     `readLineBytesAsync`) gives the next line with its bytes as they are, without its `\n` or `\r\n`, no
     byte checked, from a file, the input, a pipe or a connection; `Regex` searches bytes, where a byte that
     starts no character of UTF-8 (a lone continuation, an encoding longer than it needs, a surrogate, a
     code past Unicode, a character cut short) is read alone and matches nothing in a pattern, not `.` and
     not `[^a]`, as in Rust's `regex::bytes`; a word boundary takes it for no letter, and an empty match is
     never inside a character of UTF-8, as with a `string` and as PCRE2 does (Rust's `regex::bytes` gives
     one between the bytes of a character). The three `grep`s read a line as bytes, search it so and write
     it as it is (Rust with `read_until` and `regex::bytes`, Zig with PCRE2's `MATCH_INVALID_UTF` and a line
     past its buffer gathered in memory of its own).
1841. **The differential test is kept** in `interpreter/tests/regex-suite/differ`: the generator, the three
     programs (SG; Rust with `regex`, 1.13.2 in its `Cargo.lock`; Zig with PCRE2), a comparison and
     `run.py`, which builds and runs them on 2,030,000 cases of text and 1,000,000 of bytes, by hand when
     `Regex` changes, as the suites of `jq` are. A case fails when Rust and PCRE2 agree and SG does not, or when both compile a
     pattern SG refuses; in bytes the empty matches are left out, which the three place each its own way.
1842. **The methods of bytes are named for them**, on the same `Regex`, as Go names its methods of text:
     `isMatchBytes`, `findBytes`, `findAllBytes` and `capturesBytes`, which take a `read byte[]` and give
     places in bytes; one compiled pattern serves both. A `ByteRegex` of its own, Rust's way, was the
     other way put.
1843. **Bytes look for a run of bytes**: `indexOf` of a `List<byte>`, an array or a slice of bytes takes a
     `read byte[]` as well as a `byte`, as `indexOf` of a `string` takes a text as well as a character, and
     gives where the run first lies; the compiled code calls the search of text (`sg_find`, sixteen places
     at a time). `Regex` looks for its literal and its inner text in bytes with it; Zig has
     `std.mem.indexOf`, Rust the crate `memchr`.

Built: a search reads a character with `regexDecode`, which checks the bytes it reads past ASCII, and gives
`RegexNotText` (0x110000) for a byte that starts none; read backwards, the character that ends at a place
is the longest of UTF-8 that ends there, else the byte before it. The search functions take a `read
byte[]`, the methods of a `string` give them its bytes. `readLineBytes` is `readLine` without the check, in
the interpreter and in C (`sg_read_line_any`), a connection's too.

Measured, `grep` over 100 MB, best of five (`measure.py grep`), the three reading lines as bytes: `-c ERROR`
0.035 s (Rust 0.041 s, Zig 0.035 s), `-n timeout` 0.043 s (0.045 s, 0.045 s), `-c -i error` 0.065 s (0.063 s,
0.045 s), the address 0.127 s (0.129 s, 0.104 s), `日本` 0.049 s (0.086 s, 0.048 s), `-v -c INFO` 0.036 s
(0.045 s, 0.038 s). Each line is no longer checked to be UTF-8: beside the `grep` of the slice before, built
the same day, best of nine, SG's `-c ERROR` went from 0.044 s to 0.034 s and `-v -c INFO` from 0.048 s to
0.036 s. PCRE2's JIT gained most, so Zig leads `-i` (1.44 times SG, in the list of slow places) and the
address (1.22). The search of a `string`, which now checks the bytes past ASCII it reads, was measured with
the old `grep` built by both compilers: within a millisecond in each case, after the backward DFA, the
character before a place and the one after a match read ASCII without the check (the address had been 3%
slower).

Tests: `ok_regex_bytes` (bad bytes of each kind, `.`, `[^a]`, `\PL`, word boundaries, empty matches, the DFAs
