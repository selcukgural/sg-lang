## 118. Fuzzing the front end, mutants of the rules of safety

Choices made in the hundred-and-eighteenth slice (fuzzing the front end, 1323, and mutants of the rules
of safety, 1325). Approved on 19 November 2026:

1349. **The order**: this slice fuzzes the front end (1323) and then tries mutants (1325); fuzzing for
     differences (1324), with a generator of programs of our own, is the largest piece and is the next slice.
1350. **Two targets** (`fuzz/`): `parse`, the lexer and the parser; and `check`, all `sg build` does before
     the C compiler runs (the parser, the checker, the consts it finds and the C written), on a stack as
     large as the one `sg` gives them. The interpreter does not run there; that is 1324's. An input that is
     not UTF-8 is passed over, as `sg` does not read such a file.
1351. **What counts as a finding**: a panic of Rust, a stack run out, more than 2 GB of memory, or an input
     that takes more than 10 seconds. The targets are built with debug assertions, so an overflow a release
     build of `sg` would wrap without a word is a panic there. A message about the program is the answer
     expected.
1352. **A const takes at most 1 000 000 steps while it is fuzzed** (`cfg(fuzzing)`, which cargo-fuzz sets):
     a hundred million take about 9 seconds, and the fuzzer would count each such input as one that hangs.
     `sg` itself is built as before. The steps stay counted for each const, as Rust counts them for each
     const (`long_running_const_eval`) and Zig for each block run when it compiles (`@setEvalBranchQuota`).
1353. **Where the fuzzer starts**: from the programs of `tests/cases` and `examples`, with the words and
     marks of the language in `fuzz/sg.dict`. The corpus it grows is kept in a volume of the container, not
     in the repository. An input that fails is made smaller (`cargo fuzz tmin`) and becomes a test before
     the fix (1321).
1354. **How it is set up**: `fuzz/` is a crate of its own, not in a workspace with `sg`; its one dependency,
     libfuzzer-sys, has its version pinned and its `Cargo.lock` kept, and Dependabot watches it. The image of
     `fuzz/Containerfile` pins Rust nightly to a day and cargo-fuzz to a version and fetches the crates; only
     building it uses the network, and the fuzzing runs without it (`fuzz/run.sh`). It is not in the CI,
     which runs on Windows and with stable Rust.
1355. **How long**: three hours of `check` and one of `parse`, six at once; a short run again after a fix.
1356. **Which functions mutants are tried on**, named in `.cargo/mutants.toml`: those of the checker that
     follow moves and borrows and what a borrow outlives, all of `src/opening.rs`, all of `src/sums.rs`,
     and the functions of the back end that leave a check of bounds or of overflow out or lend a value; 677
     mutants in all. `Emitter::value` (533 mutants alone) and the rules of types are left out.
     cargo-mutants changes the Rust of `sg`, not the C it writes, so a check written as C is tried through
     the Rust that decides when it is left out.
1357. **Which tests run on each mutant**: on those of the checker and of `opening`, the golden tests in the
     interpreter (`--exact golden`, 34 seconds), where every `error_*` program is; on those of the back end,
     the compiled golden tests without the sanitizers (`--exact compiled`, about two minutes).
1358. **Where**: on macOS, four at once; the fuzzing runs beside it in the container.
1359. **A mutant that lives** is read: a missing test gets written; a mutant that changes nothing a
     program can see is left out in `.cargo/mutants.toml` with the reason; a way of the code that is not
     needed comes as a choice.
1360. **After this slice**, a change to these functions is tried only where it touched them: `git diff |
     cargo mutants --in-diff`. It is not in the CI.

What fuzzing the front end found, from 1377. The first run gave `check` three hours (15 845 031 inputs)
and `parse` one (30 086 188), six at once: no input hung or took more than 2 GB, the parser never panicked,
and `check` found one fault, approved on 19 November 2026 (after the fixes of this slice, half an hour more of
`check`, 2 747 192 inputs, found nothing):

1377. **An end of a channel behind a pointer** (`new jobs.sender()` is a `Sender<int>*`): the checker took
     `tx.send(1)`, `await tx.sendAsync(1)` and `jobs.receive()` through the pointer and the interpreter ran
     them, but `sg build` stopped with a fault of its own (the back end looked at the type without going
     through the pointer, which the address it computes already did). Fixing it showed two more of the same:
     `tx.clone()` counted the copy as an end that receives, so compiled code never let the channel go (a
     leak its debug build reported), and the temporary that holds the end of a send had the C type of one
     pointer too many, which the C compiler took with a warning. The back end now looks through the
     pointers in all four places, as it does for a `List<T>*`; Rust's `Box<Sender<T>>` reaches the methods
     the same way. Tested by `ok_channel_behind_pointer` and `ok_channel_behind_pointer_async`, with which `sg
     emit-c` stopped before the fix; compiled, under the sanitizers, they print what the interpreter prints.

What trying mutants found, from 1378. Approved on 19 November 2026:

1378. **How far the living mutants are followed**: read in four groups, each by a reviewer of its own
     (borrows of the parts of a call, the other borrows, moves and scopes, `opening.rs`), a test written for each
     one a program can tell, and the rest listed as equivalent or out of reach with the reason, once. After this,
     only `--in-diff` (1360). Most of what lives is equivalent, and following each costs more than it finds.

The first runs: in the checker and `opening.rs`, 250 mutants were caught, 108 lived, 3 hung and 161 did not
compile; in the back end, 23 were caught, 62 lived and 70 did not compile. The tests written for them, 75 in
all, are what the slice adds to `tests/cases`:

- **The sums that cannot overflow** (`sums.rs`) had no test of a loop whose sum does overflow, so a mutant that
  took the test out of a loop where it is needed lived: compiled code would have wrapped where the interpreter
  panics. Nine `panic_sum_loop_*` programs overflow at the narrow step that a wrong count would leave without its
  test: a narrower value added or taken twice a round, a number, a negative number, a sum the loop also assigns,
  a step in an arm of a `match`, a sum lent as `ref`, a loop inside the body, and steps whose sum over a round
  does not fit in a `long`. The body holds no call and no formatted text, so the loop is split (a first version printed in the loop, which
  `sums.rs` does not split, and caught nothing). With three more (a negative `sbyte` taken, a sum with a step of no
  small bound, steps below a `long`), 39 of the 61 mutants of `sums.rs` are caught, where none was; the 20 that live
  keep a test that could go, so they make a loop slower and not wrong.
- **A static that would never be closed** was tested only for a writer of its own: `error_static_disposable`,
  `error_static_writer_inside` (a field, a list, `shared`) and `error_static_writer_in_enum`.
- **The checker**: 57 tests from the four groups, among them a field moved out through a `read` or a `ref`
  parameter, a part moved in one branch of a `match` and not the other, a `Copyable` receiver changed by an
  argument, a pointer given to a call that a later part changes, a borrow lent whole and through a field in one
  call, the next round of a loop that changes what a borrow of the round before holds, and the methods of a
  `shared checked` value inside `read ... as` and `ref ... as`. With them, 291 mutants of the checker and
  `opening.rs` are caught, 3 hang and 27 live, from 108.

Four faults of the checker came out of reading them, approved on 19 November 2026:

1379. **`ref a`, `a` a `shared checked` value, lent it to be read only.** Where a `ref T` goes, the checker
     wraps the borrow in the node that reaches what the value holds, and left that node without a type, so
     `opening.rs` took the borrow for a read. Through the same variable, `read a as v { reset(ref a) }` was
     taken; through another owner the change did not stop the program, and compiled code then read a text the
     change had freed (`var head = seen.name[0..9]`, then `rename(ref other)`, then `print(head)`, found with
     the address sanitizer). The node now has the type it stands for, in the three places it is made. Tested
     by `error_checked_ref_whole_in_block` and `panic_checked_ref_whole_through_other`.
1380. **`<`, `<=`, `>` and `>=` on two `shared checked` values** compare what they hold, as `==` and `!=` do,
     so they look through the check too: `a < b` read `a` while another owner changed it. Only the interpreter
     had the fault; compiled code does not take the comparison yet. Tested by `panic_checked_order_while_changed`.
1381. **A borrow of the round before** is named so also where the borrow and the change start at the same place
     (`later(Window { part = buffer.all() }, view)` in a loop), as `error_loop_borrow_same_call_next_round` shows.
1382. **What a part of an index lends lasts until the index runs, also where its value is only looked at**:
     `print(s[cut(ref s)])`, where `cut` gives `s` a new text, was taken (`var c = s[cut(ref s)]` was refused), and
     compiled code read the old text after it was freed. The rule of 1340 and 1347 now holds on that way as well.
     And the note says "the parts of an index". Tested by `error_index_part_changes_text_looked_at`.

And one of the back end, found when the tests above were built under `-Werror`, approved on 19 November 2026:

1391. **A method that takes `this` by value, called on a `shared` or a `shared checked` value**, was given the
     address of the box where C wants the value, which the C compiler refuses: `sg build` could not build a
     program the checker takes. The value is now copied out of its box, as it is out of a `T*`. Tested by
     `panic_checked_value_method_while_changed`, which panics where the interpreter does.

Equivalent or out of reach, read and left: the arms of `held` for `shared` around `shared`, a slice or `void`,
which the parser and the rules of aliases refuse first; the guards whose arm gives what the next one gives
(`part_loans` and `unnamed_owner` on a borrow, `lent_by` on a place); the count of loops in `loop_body`, which only
a `break` outside a loop would see and which is refused before; the order of points of the same `seq`; and in the
back end the mutants that only keep a test that could go (`sums` giving nothing, a step whose bound is not
found), and the indentation of the copies of a loop. `opening.rs`'s guard of a comparison became equivalent with
1380, and the arms of `loans_of` for a formatted value change only a refusal of a safe program
(`s.write($"{r}".toString())` with `r` a borrow of `s`). Not read: the two of `not_lent`, and the arm of `part_loans`
for a number given as the receiver, which lives although `ok_call_parts_copied` was written for it.

## 119. Fuzzing for differences

Choices made in the hundred-and-nineteenth slice (fuzzing for differences, 1324). Approved on 19 November 2026:

1361. **A generator of our own** (`fuzz/difference/`), a crate with no dependencies on stable Rust, as Csmith
     and YARPGen are for C and rustlantis for Rust (which compares Miri with what LLVM makes): a seed gives one
     program, the same on every machine, so a finding is its seed. libFuzzer is not used here: each input is a
     build of C, and what guides it, the coverage of `sg`, does not see the C runtime.
1362. **A program that the checker takes and that ends**: the generator keeps the type of every value it writes;
     a loop runs a number of rounds written in it, a `while` has a counter that no `continue` steps over, a
     function calls only those written before it, and one that calls itself is given its depth; the steps a
     function may take are counted, so a program ends in a fraction of a second. Its only output is `print`: no
     clock, randomness, files, `unsafe` or C. A program the checker refuses is kept apart and read: either the
     generator wrote what it should not, or the checker is stricter than it should be.
1363. **Panics are allowed and compared**: safe SG has no undefined behaviour, and an overflow, an index out of
     range or a division by zero is a panic, whose message and code must be the same both ways. Most operations
     are guarded (`i & 7` as an index, `d | 1` as a divisor, the wrapping methods), about one in ten not, so a
     program does not stop at its first line.
1364. **What is compared**: the interpreter against the debug build under the address and undefined-behaviour
     sanitizers (`-O1`), output, errors and code; and when the program does not panic, the release build
     (`-O2`, under the undefined-behaviour sanitizer) against the debug build, so the way that wraps never
     reaches undefined behaviour of C. A report of a sanitizer, a run that does not end and a fault of `sg` are
     findings too.
1365. **Step by step**: stage 1, the integer types, `bool`, arithmetic, the bit operators, conversions,
     comparisons, `if`, `match`, `for` and `while`, functions, recursion, arrays, consts and `print` with a
     format; stage 2, `Copyable` structs, enums with what they carry and `match` on them, `T?` with `??` and
     narrowing, lists, text and functions that give a `Result` with `??`, `match` and `try`. Borrows and moves
     (stage 3) and tasks with channels (stage 4, compared in any order) come later. Stage 3's borrows came
     with the second review (1593).
1366. **A finding is made smaller** by a reducer of our own: the generator writes a tree of statements, and
     runs of them are taken away, halves first, then blocks replaced by what they hold, while the checker takes
     the program and the finding stays. C-Reduce does not know SG. The program then becomes a test (1321).
1367. **Where**: in the Linux image of the tests, without the network, six at once for two hours; what is found
     and its seed stay in the volume of the fuzzing. On macOS only to see a finding again.
1368. **The interpreter is the `sg` program**, run in a process of its own with a time limit, so a fault or a
     hang of it does not stop the run, and the way a user runs a program is the one tried.

The first run, two hours in the Linux container, six at once: 135 496 programs, of which 14 885 ended in a panic,
gave the same output, message and code interpreted and compiled, and none drew a report of a sanitizer or a
difference between the debug and the release build. The 60 programs the checker refused were all the
generator's: it took a list written through an index that is not cut (`l[5] = x`) for one that was read, and the
checker rightly said the list is given values that are never read; after the fix, 1 703 programs in three minutes
on macOS, none refused. Writing the generator taught it the rules a program must keep, each a rule of the
language as it is meant (`b.max(300)` on a `byte` is an `int`, 163; a `T?` has no text; `x is null` narrows `x`
where it holds, so a `??` there is an error; a program nests at most 1000 deep). The reducer, tried on a difference
made on purpose (the interpreter given one more line when the program has a `while`), took a program of 47 lines
to 10 in 40 tries, nine seconds.

## 120. Support for editors

Choices made in the hundred-and-twentieth slice (support for editors). Approved on 19 November 2026:

1369. **The order**: (1) colours and the settings of the editor (a TextMate grammar, its brackets, comments and
     indentation, and an extension for VS Code in `editors/vscode`), and (2) `sg lsp`, the errors as you write and
     a hint applied with one click, in this slice; (3) the type under the pointer, going to a definition and the
     names of a file, and (4) completion, which needs a parser that goes on after an error, later.
1370. **The language server is in `sg`** (`sg lsp`), with JSON read and written by `sg` itself and no dependency,
     as Deno and Gleam have it: one program, so the server and the compiler are always the same version.
     rust-analyzer, zls and gopls are programs of their own. Publishing the extension is a step outward and is
     asked for with the preview.
1371. **A hint applied with one click** is an edit the error carries beside its text (`Diag::fix`: a place and
     what is written there), given only where the code is certain; rustc marks such suggestions
     `MachineApplicable`. The first four: a conversion (`(int)big`, or `(int)(a + b)`), `.clone()` of a text
     that is only borrowed, `_ = ` before a value dropped on purpose, and the missing `use` line, put before
     the first line of the file that is not a comment. An unused `Result` has none: its two ways are `try`,
     which needs a function that gives a `Result`, and `_ =`, which drops the error, the risky way a hint does
     not take (the first rule of hints in 04). Each fix is applied in `tests/lsp.rs` and the program then checks.
1372. **When and what is checked**: 300 ms after the last change, on a thread of its own with the stack the
     checker needs; the program is the one `sg` would read the file in (the nearest folder above it with a
     `main.sg`, or the file alone with its modules beside it), and an open file is read from the editor, saved
     or not. The program is only checked, never run; `test` blocks are checked too.
1373. **What is shown**: the first error, as the checker stops there, in the file it is in (an error in a module
     is shown in the module's file), with its notes and hint, and the second place it names as a link. An error in
     the language's own module is shown at the start of the file. Several errors at once wait for a parser that
     goes on after one (part 4).
1374. **A fault of the checker does not stop the server**: a panic is caught and shown as one error, *the
     checker stopped: this is a mistake in sg*, and the next change is checked again.
1375. **Tested from outside** (`tests/lsp.rs`): a `sg lsp` process is talked to as an editor talks to it; the
     first error comes, at the column the protocol counts (UTF-16, a character of two units before it), and goes
     once the text is right; what the editor has not saved is read, an error in a module is shown there; each of
     the four fixes is applied and the program then checks; a request it does not serve is answered with an error,
     and the exit codes are as the protocol has them. `json.rs` and the reading of `file:` URIs have tests of
     their own.
1376. **The client for VS Code** is plain JavaScript (`extension.js`), with nothing to build, and one
     dependency, vscode-languageclient 10.1.2, pinned in `package-lock.json` and watched by Dependabot. `sg.path`
     names the `sg` program (`sg` on the `PATH` without it); a workspace that is not trusted cannot set it, so
     a folder cannot choose the program the editor starts. Tried by hand in VS Code 1.146 on macOS: the colours,
     the error under `int small = big` and its fix `(int)big`, after which the error went.

## 121. The web site

Choices made in the hundred-and-twenty-first slice (the web site, `website/`). Approved on 19 November 2026:

1383. **In the repository**: `website/`, built with Docusaurus 3.10.2 on Node 22, its packages pinned and
     locked and watched by Dependabot, so a slice's one commit changes the code and the page that describes it.
1384. **Laid out as Rust's site is**: a front page (what SG promises, three pillars, a program that runs, what was
     built with it, where it stands), then Learn, Reference, Library and Status.
1385. **A thin start**: the front page, how to install, a tour, SG for Rust programmers and the status; the
     reference and the library point into the repository until the preview (942), and pages of the library
     made from its source, as source.dot.net shows .NET's, come with a `sg doc` of their own later. The pages are
     written for the reader, not copied from the record of decisions, in English. `learn/for-rust.md` is the
     exception: `scripts/sync-docs.mjs` makes it from `design/06-rust-to-sg.md` before each build, which keeps it
     as the slice left it.
1386. **Search built into the site** (a plugin, no service outside it); Algolia's DocSearch, which asks for an
     application and runs its own crawler, is for after the preview.
1387. **The look**: the nazar bead (drawn simply for now, `static/img/logo.svg`) and Pasha; cobalt, sky blue,
     white and navy; light or dark as the system is set.
1388. **SG coloured on the site** with the words and marks of the VS Code grammar (`src/theme/prism-include-languages.js`).
1389. **Published by Cloudflare Pages** from the repository on GitHub, no secret in it, with headers of its own
     (`static/_headers`): a CSP that runs no inline script but the colour mode's, by its hash
     (`scripts/check-csp.mjs` fails the build otherwise; Docusaurus's banner about a wrong base URL, another
     inline script, is turned off), HSTS, `nosniff`, no framing. No analytics.
1390. **Publishing is the author's step**: the account, the connection of Pages and the name servers of
     sg-lang.org. Tried before it on macOS with the headers applied: the front page, the tour, and the search,
     with no script refused. Every program on the pages runs (`npm run check`, 9 programs).
1392. **The pages of the library are made from its code**, as Rust's `std` documentation and Go's pkg.go.dev
     are: a page for each type, with its methods, what each does (from comments `///` written in the source),
     examples that run, and a link from each item to its source on GitHub. A browser of the source itself, as
     source.dot.net is for .NET, is for reading how a thing is built rather than how to use it, and is not what
     these pages are; one may come later from what `sg lsp` knows. The pages come with the preview, from a
     `sg doc` of their own and the `///` comments that were put off until then.

## 122. What the web site teaches

Choices made in the hundred-and-twenty-second slice (what the web site teaches). Approved on 19 November 2026:

1393. **The site teaches, as the sites of Rust and Go do**: Learn holds a book of fourteen chapters (the first
     program, values, text, functions, structs and enums, `null` and errors, ownership and borrowing, collections,
     modules, tasks and channels, C, `unsafe`, testing, building), each with programs that run, so that nothing in
     it sends the reader to the repository.
1394. **The reference of the language is written on the site** next, the rules as a reader looks them up; the
     choices in this file and in design/04 stay where they are, the record of why, and the reference links to them.
1395. **The library has a page for each type used most** (text, numbers, collections, files and paths, time,
     tasks, random numbers, other programs), written by hand until `sg doc` makes them from the source (1392).
1396. **Kept in step**: every program on the site is run by `npm run check`, which tells `sg error` (the checker
     refuses it) from `sg panic` (it runs and stops) and checks the message; a page is about one idea, so a change
     touches few. The book and the library hold 213 programs, each also compiled and run the same.

Writing the pages found one fault of compiled code, approved on 19 November 2026:

1397. **A `match` on a borrow of a value that has no name** (`match make().trim()`, `match
     string.fromUtf8(read List<byte> { 72, 105 })`) freed that value before the arms ran in compiled code, which
     then read freed memory (the address sanitizer showed it); the interpreter was right. What the subject is made
     from now lives until the arms are done, as Rust keeps the temporaries of a `match`; before, only a `match` that
     binds names by borrow kept them. Tested by `ok_match_on_borrow_of_temporary`.

And these, approved the same day, for the next slice: a build of a folder whose program would take the folder's
name is a clear error that asks for `-o`, as Go's is (1398); `sg emit-c` and the other outputs of the tool end
quietly when what reads them closes, as programs do (1399); a type of `std` named only inside `$"..."` is found
(1400); fifteen hints and messages that lead to code that does not compile, or are missing, or read wrong, each
with a test, among them the safe way in the panic of an index, `xs.get(i)` (1401); and the documents put right
where they said otherwise than `sg` does (1402).

## 123. What writing the site found in `sg`

Choices made in the hundred-and-twenty-third slice (what writing the site found in `sg`). Approved on 19 November
2026; each change has a test that failed before it:

1398. **An output that is a folder is told before anything is compiled**: `sg build shop` from the folder above
     `shop` would name the program `shop`, the folder itself, and the linker failed with "a mistake in sg". Now
     it is `` error: `shop` is a folder; name the program with -o ``, and `-o` naming a folder is `cannot write X:
     it is a folder`, both with code 2, as Go's `go build` tells it. On Windows the program is `shop.exe`, which
     does not clash. Tested in `tests/cli.rs` (`refuses_an_output_that_is_a_folder`).
1399. **What the tool writes itself ends quietly when what reads it closes**: the C of `sg emit-c`, and the
     `built ...` line of `sg build --library`, `--shared` and `--freestanding`, went through Rust's `print!`, which
     panics on a closed pipe (`sg emit-c x.sg | head`). They end now as a program does (1330): by `SIGPIPE` on Linux
     and macOS, with 0 on Windows (`emits_c_into_an_output_closed_early`).
1400. **A type of `std` named only inside `$"..."` is found**: the files of the language's own module are read
     for the names a program writes, and the code inside a `$"..."` was not looked at, so
     `print($"{Path.extension(name)}")` was "no variable or type named `Path`". `source.rs` now reads the code of
     every `$"..."`, one inside another too (`ok_std_type_named_in_text`, `ok_std_type_named_in_inner_text`).
1401. **Hints and messages**, each with an `error_`, `panic_` or `leak_` test:
     - `try` on a `T?` in a test: the hint was `assert(x is not null)`, which does not narrow, so the code after
       it did not compile; it is `find() ?? panic("...")` now (`tests_error_try_nullable`).
     - `count = 1` on a `read int`: the hint `read 1` borrowed a value gone at the end of the line; it is "change a
       copy of your own: `var own = count`; or take `ref int`" (`error_read_param_assigned`).
     - A `T?` field used without a test: "copy it to a variable" moved a field that is not `Copyable`. The hint

## 125. The library: CRC-32

Choices made in the hundred-and-twenty-fifth slice (the library: CRC-32). 1408 was approved on 19 November
2026, with 1406:

1408. **CRC-32** (`std/checksum.sg`), the one of IEEE 802.3 that zlib, gzip, PNG and ZIP write (reflected,
     the polynomial `0xEDB88320`, starting from all ones and inverted at the end): `Crc32.of(read byte[] data)`
     gives it as a `uint` for all the bytes at once; `var c = Crc32()`, then `c.update(read piece)` for each
     piece and `c.value()`, which may be asked between pieces, the same number for the bytes cut anywhere.
     The table is a const, found when the program is compiled. It is measured against zlib's `crc32`
     (`checksum`, below). Rust's `crc32fast` (`crc32fast::hash`, `Hasher::update` and `finalize`) and Go's
     `crc32.ChecksumIEEE` are the models (`ok_crc32`: the check value `cbf43926`, nothing at all, 32 zeros and 32

     text cut at each of its 79 places into two pieces; `error_crc32_fields`: `Crc32 { state = 0 }` is told how
     one is made).

Approved on 19 November 2026, after the slice was written:

1414. **Sixteen bytes in a step** ("slicing by 16"): sixteen tables of 256 numbers, 16 KB in a program that
     uses `Crc32` and nothing in one that does not, as `crc32fast` does where the processor has no CRC
     instructions. Byte by byte through one table took 2.5 s for a gigabyte, eight in a step 0.45 s, sixteen
     0.27 s; each the time of the same algorithm written in C. The four words of a step are read with
     `uint.fromLittleEndian(data[i..i + 4])`, which C reads as one load (1.10 s for four gigabytes, against
     1.13 s for the bytes joined one index at a time).

     of the processor and multiplication without carries, which SG has no way to call; it goes into "Slower
     than C" below, and the site's page names zlib's `crc32` through C for a program that needs that speed.
     Calling those instructions would be a choice of its own (a built-in that the C compiler maps to them on
     each machine, and the tables where there are none).

## 126. The library: SHA-256 and HMAC

Choices made in the hundred-and-twenty-sixth slice (the library: SHA-256 and HMAC). 1409 was approved on 19
November 2026, with 1406; 1418 the same day, before the slice was written:

1409. **SHA-256 and HMAC** (`std/hash.sg`): `Sha256.of(read byte[] data)` gives the SHA-256 of FIPS 180-4 as a
     `byte[32]`; `var h = Sha256()`, then `h.update(read piece)` for each piece and `h.finish()`.
     `Hmac.sha256(read byte[] key, read byte[] data)` is HMAC-SHA-256 (RFC 2104), a key longer than a block of
     64 bytes hashed first. `Bytes.equalInConstantTime(read byte[] a, read byte[] b)` compares a tag or a token
     in a time that depends on the length only: every byte is gone over and the differences joined with `|`,
     with no branch on what they hold (looked at in the machine code clang 22 makes at `-O2` for arm64 and
     x86-64), and two lengths that differ give `false` at once, as Go's `subtle.ConstantTimeCompare` does. Plain
     SG, no instructions of the processor made for SHA; no other hash and no cipher. Rust's `sha2` and `hmac`
     and Go's `crypto/sha256` and `crypto/hmac` are the models (`ok_sha256`: the examples of FIPS 180-4, one,
     two and no blocks and a million times `a`, the lengths around where the padding takes a second block each
     given byte by byte, a text cut at each of its 93 places, and `finish` asked between pieces; `ok_hmac`: the
     test cases of RFC 4231 but the fifth, whose tag is cut short, a key of exactly a block and of one byte
     more, and a tag with one bit changed; `error_sha256_fields`: `Sha256 { filled = 0 }` is told how one is
     made).
1418. **The order after the log**: once the log (1412) is written, the language is tried on real programs
     before more goes into it: a few programs that people write (a `grep` and a `wc`, a `jq` of JSON, an HTTP/1.1
     file server under load, a key-value store with a write-ahead log, a pool of workers, a GIF tool, an
     interpreter of Lox) are written in SG, in Rust and in Go, the same algorithm each time and written plainly;
     the time, the most memory held, the size of the program and its lines are measured, and each difference is
     a numbered choice, fixed and measured again. XML (1413) and the reference (1394) come after that.

Approved on 19 November 2026, after the slice was written:

1419. **`finish` does not end the hash**: `h.finish()` works on a copy of what the hash holds, so more bytes may
     be taken in after it and `finish` asked again, as Go's `Sum` does and as `Crc32.value()` does; Rust's
     `finalize(self)` takes the hasher. The copy is 104 bytes, against 64 rounds for each block.
1420. **HMAC wipes nothing**: `Hmac.sha256` keeps the key and what is made of it in locals and lets them go
     without writing zeros over them, as Go's `crypto/hmac` and Rust's `hmac` (without its `zeroize` feature)
     do. Copies the C compiler makes of them could not be wiped anyway; a program that must wipe its own key
     calls `Memory.zeroSecurely(ref key)`.
1421. **The interpreter reads the length and an item of an array or a slice where they are**: `data.length()` on
     a slice of a megabyte made a list of a million cells each time, so hashing a megabyte through a loop that
     asks `data.length()` took 46 s in the interpreter and takes 4 s now; `get(i)` is read the same way.
     Compiled code was never touched. `ok_sha256` hashes the megabyte and would take most of a minute again.
1422. **OpenSSL's own speed is not reached**: a gigabyte takes 3.14 s, the time of the same algorithm written in
     C (2.90 s), and OpenSSL 0.35 s with the SHA instructions of the processor, which SG has no way to call;
     into "Slower than C", as CRC-32's (1415), and the site's page names OpenSSL through C for a program that
     hashes gigabytes.

## 127. The library: the command line

Choices made in the hundred-and-twenty-seventh slice (the library: the command line). 1410 was approved on 19
November 2026, with 1406; 1423-1433 the same day, before the slice was written:

1410. **The command line, declared** (`std/command_line.sg`): a program says what it takes, with no generics and
     no reflection, and reads it: `var cl = CommandLine("gifcrop", "Crops GIF images.")`, `cl.flag(...)`,
     `cl.option(...)`, `cl.positional(...)`, then `cl.parse(read args)`. The values are text; a number is read
     by the program (`int.parse`). Rust's `clap` with its builder, Go's `flag` and GNU's `getopt_long` are the
     models.
1423. **The names**: `CommandLine` declares, `Arguments` is what was read, `CommandLineError` why it could not be
     (clap's `Command`, `ArgMatches` and `Error`; Go's `FlagSet`).
1424. **A short letter is a `char?`**: `cl.flag("dry-run", null, "Show what would be done")` has only the long
     name; one function for each kind, not one more for each kind without a letter.
1425. **Words in their places**: `positional(name, help)` must be given, in the order declared;
     `rest(name, help)` takes the words left, none or more, declared once and last. `a.positional(name)` gives a
     `read string`, `a.rest()` a `read List<string>`. No single word that may be left out: `rest` does it.
1426. **An option given twice**: `a.option(name)` gives the last value, as Go's `flag`, Python's `argparse` and
     `getopt` do, and `a.options(name)` every value in order, with nothing more declared. A flag given twice is
     no error. No count of a flag (`-vvv`) yet.
1427. **GNU's way of writing**: an option that takes a value takes the next word whatever it is (`--offset
     -5`); `-ofile` and `-vo file`; a lone `-` is a word (the input, by custom); options may come after the
     words (GNU reorders them, POSIX and Go's `flag` stop at the first word); every word after `--` is a word;
     `--verbose=yes` is an error. A long name is never shortened: `getopt_long` takes `--verb` for
     `--verbose`, and a script that wrote it would read another option once `--verbatim` is declared; clap does
     not shorten either. The nearest name is told instead.
1428. **The nearest name**: an unknown long name is told the declared one at most two edits from it (Levenshtein
     over the bytes; the first declared of those as near), `--help` and `--version` among them. No suggestion for
     a short letter.
1429. **`parseOrExit`**: the help or the version printed to the output with 0; an error to the standard error,
     `gifcrop: unknown option '--verbos' (did you mean '--verbose'?)` and `Try 'gifcrop --help'.`, with 2, as
     Go's `flag.Parse` and clap's `get_matches` end the program. `parse` stays for a program that does its
     own: the same five lines in every program otherwise.
1430. **What is declared wrongly is a panic**: a name declared twice, a short letter twice, `h` or the name
     `help` (and `version` once `cl.version` is called), a name other than lower-case ASCII letters, digits and
     `-` starting with a letter, a short letter other than an ASCII letter or digit, a second `rest` or a
     `positional` after it; asking a name that was not declared (with the declared one nearest to it, when
     there is one) or one declared as something else (`a.option("verbose")` of a flag), or `a.rest()` with no
     `rest`. The names are text, so the checker cannot see them; but the declaring runs on every run, whatever
     the command line holds, so the first run shows the mistake.
1431. **The help**: the line `about`, `Usage: gifcrop [options] <input> [files...]`, the words under
     `Arguments:` and the options under `Options:`, in the order declared, `-h, --help` and `--version` last; one
     column for the texts, four spaces after the longest, counted in characters; no wrapping, no colour.
     `cl.help()` gives the same text.
1432. **`--version` only when asked for**: `cl.version("1.2.0")` adds `--version`, which prints `gifcrop
     1.2.0`, with no short letter (`-v` and `-V` are taken by other things too often). Built in because a
     `--version` the program declared itself would end in `missing <input>` when the program takes a word;
     Go's `flag` has no words that must be given, so it never meets this.
1433. **`CommandLineError`**: `HelpAsked(text)`, `VersionAsked(text)`, `UnknownOption(word, suggestion)`,
     `MissingValue(option)`, `UnexpectedValue(option)`, `MissingArgument(name)`, `TooManyArguments(word)`;
     `{cause}` gives the line `parseOrExit` writes, and the errors compare as values. A short option that is
     not a letter or a digit (`-v-`, `-é`) is named with its whole word.

`ok_command_line` reads 51 command lines of three programs, the help of each among them; eight `panic_command_line_`
programs show each mistake of the declaring and of the asking; `error_command_line_fields` is told how an
`Arguments` is made; `a_command_line_read_or_exit` (in `tests/cli.rs`) runs a program interpreted and compiled
and looks at what goes to the output, what to the standard error, and the codes 0 and 2. With 1410, 461 of the 1823 programs are compiled on macOS and on Linux (102 under the thread
sanitizer), and the 222 programs of the site run as they show; on the Windows Arm VM `ok_command_line` and the

## 128. The library: JSON

Choices made in the hundred-and-twenty-eighth slice (the library: JSON). 1411 was approved on 19 November 2026,
with 1406; 1434-1442 the same day, before the slice was written:

1411. **JSON** (`std/json.sg`): `JsonValue` is `Null`, `Bool(bool)`, `Integer(long)`, `Number(double)`,
     `String(string)`, `Array(List<JsonValue>)` or `Object(JsonObject)`; `Json.parse(read string text)` gives a
     `Result<JsonValue, JsonError>`, `value.toJson()` and `value.toJsonIndented(spaces)` write it. A whole
     number that fits a `long` is an `Integer`, every other a `Number`, so an id above 2^53 survives. A
     `JsonObject` keeps its members in order and finds one by name; a name twice is an error. Strict RFC
     8259, nesting to 128, and a `JsonError` with the line, the column and the kind. Numbers are written in the
     fewest digits that read back the same, and writing NaN or an infinity is a panic. Nothing maps a struct of
     the program: it writes `toJson` and `fromJson` by hand. No reading of a stream yet.
1434. **The names**: `Json.parse`, `JsonValue`, `JsonObject`, `JsonError` and `JsonErrorKind` (serde_json's
     `from_str`, `Value`, `Map` and `Error`).
1435. **An object built and changed**: `JsonObject()`; `o.add(name, value)` panics on a name that is there, as
     `HashMap.add` does (choice 4 of the eighth slice); `o.set(name, value)` puts the value in place of the
     member, where it is, or adds it at the end (serde_json's `insert` with `preserve_order`); `o.remove(name)`
     takes it out and keeps the order of the others; `o.get`, `o.contains`, `o.length()` and `o.names()`, the
     names in order. Without `set` and `remove` a program could not read a file of settings, change one value
     and write it back.
1436. **Looking into a value never panics**, since the data comes from outside and a missing member is an
     ordinary thing: `v.get(name)` is `null` when `v` is not an object or has no such member, `v.at(i)` when it
     is not an array or has no such item; `asString()` (a `read string?`), `asLong()` (an `Integer` only),
     `asDouble()` (an `Integer` or a `Number`), `asBool()`, `asArray()`, `asObject()` and `isNull()`. With `?.`
     a path is one line: `doc.get("user")?.get("name")?.asString() ?? "-"`. serde_json's `get` and `as_*` are
     the same.
1437. **Numbers**: one written with a `.` or an exponent is a `Number` (`1.0`, `1e2`), `-0` too, as `-0.0`,
     which keeps its sign; a whole one beyond a `long` is a `Number`; one beyond a `double` (`1e400`) is
     `NumberOutOfRange`, one below what a `double` holds (`1e-400`) is 0, as serde_json and Go read them. A
     `Number` is always written with a `.` or an exponent (`2.0`), so that reading what was written gives the
     same kind (serde_json does the same; Go writes `2`).
1438. **Writing**: `toJson()` with no spaces, `{"a":1,"b":[true,null]}`; `toJsonIndented(n)` as serde_json's
     `to_string_pretty` writes (`"a": 1`, an empty array or object as `[]` and `{}`), a negative `n` a panic.
     Only what JSON needs is escaped: the quote, the backslash and the control characters (`\n \r \t \b \f`,
     the others as `\u001b`); other characters stay as they are, in UTF-8, and `/` is not escaped; Go's
     escaping of `<`, `>` and `&` for HTML is left out. `JsonValue` is `Formattable`: `$"{v}"` is `toJson()`.
1439. **`JsonError`**: `e.line` and `e.column` from 1, the column counted in characters, as the compiler's own
     messages count it, and `e.kind`: `UnexpectedEnd`, `UnexpectedCharacter(char)`, `InvalidNumber`,
     `NumberOutOfRange`, `InvalidEscape`, `LoneSurrogate`, `ControlCharacter` (in a string, not escaped),
     `DuplicateKey(name)`, `TooDeep`, `TrailingText`. `{e}` is `line 3, column 14: duplicate key "id"`, and the
     errors compare as values.
1440. **The same value**: `JsonValue` is `Equatable`; arrays are compared item by item in order, objects member
     by member in any order, since the RFC gives an object no order (serde_json compares them so too).
     `Integer(1)` is not `Number(1.0)`. `clone()` copies everything in the value.
1441. **Strict in the small things**: a byte order mark before the value is an error (Go and serde_json refuse
     it too); the spaces are the space, the tab, `\n` and `\r`; arrays and objects count together toward the
     128 levels; `\u0000` is read, since a `string` holds a zero byte. The writer has no limit of depth: the
     program built the value. (Since the hundred-and-forty-eighth slice, 1600, it writes 128 levels too, as
     many as are read, and `JsonOptions` gives another depth to both.)
1442. **Tested with JSONTestSuite**: its 318 parsing cases are kept in `tests/json-suite` with their licence
     (MIT); each `y_` file must be read, each `n_` refused, each `i_` as these rules decide, and a file that is

## 129. The library: a log

Choices made in the hundred-and-twenty-ninth slice (the library: a log). 1412, 1416 and 1417 were approved on
19 November 2026, with 1406; 1447-1455 the same day, before the slice was written:

1412. **A log** (`std/log.sg`): `Log.debug`, `info`, `warn` and `error` with a text, `Log.setLevel`, the level
     `Info` unless `SG_LOG` names another. Lines to the standard error, `2026-11-19T20:15:03.123Z INFO message`,
     the time in UTC (RFC 3339); the lines of tasks never mix; a level that is off costs almost nothing. No
     files, rotation or structured fields yet.
1416. **A message is never read for anything in it**: no lookups (`${...}`), no pattern with arguments; `Log`
     takes a finished `string`, and a value put into a `$"..."` is never read again. Written as a rule, so that
     a later "lookup" is refused: Log4Shell (CVE-2021-44228) was a lookup in a message.
1417. **One line is one call**: a line break and every other control character of a message is escaped when
     it is written (`\n`, `\r`, `\t`, `\u001b`), so a text from outside cannot add a line of its own (CWE-117,
     log forging) or drive a terminal. Tested with a forged line.
1447. **A level that is off builds nothing**: the compiler writes `Log.debug(text)` as `if Log.isOn(LogLevel.Debug)
     { Log.debug(text) }`, for `Log` alone; a general lazy argument would be a closure, which the language left
     out. A call inside the text does not run when the level is off, as with the macros of Rust's `log`; C#
     does it with interpolated-string handlers, Swift with `@autoclosure`, and Go's `slog` always builds it.
1448. **The names**: `LogLevel` is `Trace`, `Debug`, `Info`, `Warn`, `Error` and `Off`, in that order
     (`Comparable`, `Formattable`); `Log.trace`, `debug`, `info`, `warn` and `error` take a `read string`;
     `Log.setLevel(level)`, `Log.level()` and `Log.isOn(level)`, for work done only for the log. The level is
     an atomic number: looking at it is one load, and any task may set it. `Trace`, which Go's `slog` does not
     have, was added for nothing at run time.
1449. **`SG_LOG`** is read once, when the first line asks for the level: `trace`, `debug`, `info`, `warn`,
     `error` or `off`, in any case; empty is not set. A later `Log.setLevel` takes its place, so the program's
     own `--verbose` has the last word. A value that names no level does not stop the program: one line says
     `SG_LOG is "verbose", which is not a level (trace, debug, info, warn, error, off); Info is used`, the value
     escaped as any message is.
1450. **The line**: the time with three digits of the second always, the level padded to five letters so that
     the messages line up (`INFO  `, `DEBUG`), then the message; no file or line of the call.
1451. **Written at once**: the line is made whole, then written as one `printError`, under its lock, so it
     never mixes with another task's line or with `printError` and `Stderr`. Each line goes out when it is
     written; a write that fails does what `printError` does.
1452. **What is escaped**: the control characters (C0, DEL and C1) as `\n`, `\r`, `\t` or `\u001b`; the
     characters that cannot be seen or that turn the text around them, as 1445 names them (U+200B-U+200F,
     U+2028-U+202E, U+2060-U+2069, U+FEFF), as `\u202e` (Trojan Source, CVE-2021-42574); the backslash as
     `\\`, so that a `\n` that was in the text is not taken for an escaped line break (a path of Windows shows
     `C:\\Users`). Other characters stay as they are, in UTF-8.
1453. **Tested** with the time at the start of a line of `Log` written `<time>` by `tests/golden.rs` (only a
     time of exactly that form, before a level), a forged line, a `${jndi:...}` written as it is, a call that
     does not run when the level is off, four tasks of 200 lines each (`ok_log_tasks`, under the thread
     sanitizer when compiled), and `SG_LOG` from outside (`tests/cli.rs`). Nothing was added for the tests.
1454. **Measured**: a billion `Log.debug($"...")` calls while the level is `Info` take 1.01 to 1.10 times a C
     loop that tests an atomic global (`bench/log`).
1455. **Colours**: on a terminal the level is coloured, `ERROR` red and bold, `WARN` yellow, `INFO` green,
     `DEBUG` blue, `TRACE` grey (env_logger's); the message never is. None into a file or a pipe, none with
     `NO_COLOR` set or `TERM=dumb`, and on Windows none when the console refuses the escape sequences
     (`ENABLE_VIRTUAL_TERMINAL_PROCESSING`); never the sequences themselves. No way to force them on. Tested
     through a pseudo terminal (`posix_openpt`) and, on Windows, a pseudo console (`tests/sender.c show`).

What writing it found, from 1456. Approved on 19 November 2026:

1456. **A type of a module named with `use` comes before a type of `std`**: the order is the module's own
     names, then those `use` brings, then the language's. `examples/bare` has a module `log` with a `Log` of
     its own, and the new `Log` of `std` was taken in its place; a `Json` of a module was taken for the
     language's the same way since 1411, without a word. Rust's prelude is shadowed by what is imported in
     the same way, and adding a type to `std` no longer changes what a program means. The language's is
     `std.Log`, and `std.Log.debug(...)` is guarded as `Log.debug(...)` is (1447). `tests/modules/stdnames`
     was red before.

Writing it found two mistakes more, fixed in it: a function of `std` that reads a static whose value needs
the system was kept in a program built `--freestanding` while the function that gives the value was left
out, so C was refused (`examples/bare`, which names a `Log` of its own and so brought in `std/log.sg`); a read
of a static now counts as a call of that function. And `Log.isOn` with the first value of the level looked
up inside it was no longer inlined by the C compiler (1.33 times C): the level stays a static found where it
is first read.

compiled, and `log_colours` and `log_level_from_the_environment` pass.
