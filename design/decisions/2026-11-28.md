# Choices of 28 November 2026

Fixes of the open `bug` issues, each with its tests, documents and pages.

## `bool`, conditions, `$"..."`, `a..b` and `xs[^1]` (issues 30 and 47)

The checker let a value move, or be written, while a `$"..."` kept in a variable still looked at it: the
interpreter writes the text out at once, so it printed the old value, and `sg build` refused the type, so no
compiled program showed it (#47). Around them, messages that said the opposite of what was meant (`!n` with the
hint `n != 0`), that spoke of a condition in a declaration (`bool a = 1`), that changed what a format means
(`{(double)cents / 100:F2}`), or that said nothing where the mistake is a common habit of another language:
`bool.parse`, `(int)done`, `done == 1`, `18 <= age < 65`, `True`, `a &= b`, `a &&= b`, `Math.sqrt`, `(bool)n`,
`print("{n} items")`, `$"..." == "..."`, `xs[-1]`, `xs[^1 - 1]`, `0..=int.MaxValue`, `'a'..'e'`, `var r = 0..5`,
`xs[1..].reversed()`, and a word of the language as a function name (#30, #47).

2110. **A `$"..."` kept in a variable borrows each value written in it, as `read` would, until its last use.**
     A place in it (`{name}`, `{p.x}`, `{xs[0]}`) is lent to it: while the variable is still used it is not
     moved or written. A value with no name (`{n + 1}`, `{make()}`, a `$"..."` inside it) is gone when the line
     ends, so it cannot be kept, and the error is the one of `var r = read make()`, with the hint to name the
     value first; a literal or a constant (`{10}`, `{-2}`, `{int.MaxValue}`, `{"!"}`, `{true}`) stays. This is
     what text.md has said since 13 November ("a value that borrows its arguments"), and Rust's
     `format_args!` does the same. `.toString()` still keeps no borrow (162). The interpreter writes the text
     at once, as before; with the borrow followed that cannot be seen. `sg build` still does not compile a
     `$"..."` kept in a variable (not-here-yet.md). Tested by `error_formatted_kept_moved`,
     `error_formatted_kept_written`, `error_formatted_kept_unnamed` and `ok_formatted_kept`.
2111. **A negative number written as an index or an end of a range of a list, an array, a slice or a text is a
     compile error, with the hint `^n`.** `xs[-1]` stopped the program each time it ran, with the hint
     `.get(i)`; it is never an item, and Python's habit is the likely meaning, so the hint is `^1` (1921). An
     index into raw memory, a key of a `HashMap` and `xs.get(-1)` are as before; a negative index known only
     when the program runs still stops it. Tested by `error_negative_index`.
2112. **`(bool)x` is read as a cast, and refused by the checker with a hint.** It was a parse error,
     "expected end of line, found `0`". A number gets `n != 0` (`0` and `1` get `false` and `true`), a text
     `text == "true"`, a `bool` the value itself; `(int)done` gets `done ? 1 : 0`. No cast to or from `bool`
     is added. Tested by `error_cast_to_bool` and `error_bool_cast_to_int`.

The messages, as built:

- A number where a `bool` goes: `0` and `1` get "a `bool` is `true` or `false`: write `false`" (`true`), in a
  declaration and in a condition alike (`bool found = 0`, `while 1`); any other number keeps "compare it: `n !=
  0`". Under `!` the comparison is `n == 0`, "in place of `!n`" (`error_not_number`, `error_bool_from_number`,
  `error_while_one`).
- `bool.parse(text)`: "`bool` has no function `parse`", hint `text == "true"` (`error_bool_parse`).
- `done == 1`: "a `bool` is a test by itself: `done`" (`!done` for `== 0`), `18 <= age < 65`: "compare twice:
  `18 <= age && age < 65`", `answer == true` on a `bool?`: "`null` counts as `false` with `??`: `answer ??
  false`" (`error_bool_equals_number`, `error_comparison_chain`, `error_nullable_bool_equals`).
- `True`, `FALSE`: "a `bool` is written in lower case: `true`" (`error_true_capital`).
- `ready &= ok` on a `bool`: "for two `bool`s write `ready = ready && ok`" (`|=` with `||`, `^=` with `!=`);
  `ready &&= x`: "there is no `&&=`", hint `ready = ready && ...` (`error_bool_and_assign`,
  `error_and_and_assign`).
- `Math.sqrt(x)`: "math is a method of the number: `x.sqrt()`", the cast to `double` put in front of an integer
  (`error_math_type`).
- A word of the language that has a token of its own where a name goes (`void read(...)`, `var in`) gets the note
  "`read` is a word of the language, not a name", as the other words had (`error_word_as_function_name`).
- `{cents / 100:F2}`: the cast wraps the whole value, `{(double)(cents / 100):F2}`, so the hint does not change
  what is written; the same for `e`, `g` and the `(int)` of a `char` (`error_format_letter_sum`).
- `$"..."` where a `read string` goes: hint `read $"...".toString()`; compared with `==`, or given a method:
  "make it a `string` first" (`error_formatted_read_string`, `error_formatted_compare`, `error_formatted_method`).
- A variable never used whose name is in braces in a text without `$`: the note "`"{count} items"` is written as
  it is; a value goes into a text with `$`" (`error_text_without_dollar`).
- `0..=int.MaxValue`: "a range in a pattern ends with a number or a character", with a note that a constant is
  not an end of a range yet (`error_pattern_range_constant`).
- `for c in 'a'..'e'`: hint `for c in (int)'a'..(int)'e'`, and `(char)c` (`error_range_of_chars`).
- `xs[^k + 1]` gives both readings: "`^(k + 1)` counts `k + 1` from the end; 1 after `^k` is `^(k - 1)`"; a
  reading that gives no item is left out: `xs[^1 - 1]` gets "1 before `^1` is `^2`" (`error_from_end_minus`).
- An unexpected `..` (`var r = 0..5`, `print(0..5)`): the note that a range is written at the head of a `for` or
  in an index (`error_range_as_value`).
- `xs.reversed()` on a list, an array or a slice: the hint names `(0..n).reversed()` and `reverse`, which turns
  the items round in place (`error_list_reversed`).
- A count from the end outside the items now has a hint, in the interpreter and in compiled code alike: "from the
  end, `^1` is the last and `^3` the first", "it is empty, so there is nothing to count from the end", and at an
  end of a range "an end of a range goes from `^0`, the end, to `^3`, the start" (`panic_from_end_index`,
  `panic_from_end_empty`, `panic_from_end_bound`).
- The width in `{x,8}` is at most 999, as the letter's number is: the build always did this, and text.md now says
  it.

## Shared values, `lock` and `readonly`

Found while writing the pages of `lock`, `locked`, `weak`, `checked` and `readonly` (#40, #43, #48).

2150. **`Ok()` of a `Result<void, E>` is matched as it is built, as `Ok` is.** A value with nothing in it is
     built `return Ok()`; in a `match` arm or after `is`, `Ok() =>` was refused with "`Ok` carries nothing, so it
     is written without parentheses", while `Ok =>` was taken. Both are taken now and mean the same; a variant
     of an enum that carries nothing is still written without parentheses, as it is built. Tested by
     `ok_result_void_pattern` (#40).
2151. **`readonly` stops every change made through the field, also to what it shares with other owners.**
     `lock h.folder as f { f.name = "b" }` on a `readonly shared locked Folder folder` changed the folder: in such
     a block the name only reads now ("`f` only reads what `h.folder` holds, since `folder` is `readonly`"), and
     `ref h.folder as f` on a `readonly shared checked` field is refused, as `h.folder.name = "b"` already was.
     An owner taken with `share h.folder` is an owner like any other and changes what it holds as every owner
     does: `readonly` is about the field, not about the other owners of the value. Memory was safe either way;
     the row [`readonly` goes all the way down](../rules/modules.md#readonly-goes-all-the-way-down) said
     "nothing behind a `readonly` field can be changed" and the build let a `lock` block do it. Tested by
     `error_readonly_lock_change`, `error_readonly_checked_ref_as` and `ok_readonly_shared_field` (#48).

## Numbers, characters and bytes (issues 29, 31, 42, 46)

Messages about numbers that left out the way out or pointed the wrong way, numbers known when the program is
compiled that still overflowed when it ran, a `float` NaN that the interpreter and compiled code gave different
bits for, and hints about `char` and `byte` that named a fixed `c`. The messages are fixed where they are made;
the choices below are where both answers were reasonable.

2090. **An operation on integers whose numbers are all known when the program is compiled, and that overflows or
     divides by zero, is a compile error.** Known are the numbers written in the program, the constants of the
     number types (`int.MaxValue`) and integer consts, and an operation made only of them. `var month = 30 * 24
     * 60 * 60 * 1000` is "overflow: 2592000 * 1000 does not fit in int" with the hint ``compute in `long`:
     `(long)30 * 24 * 60 * 60 * 1000` ``, and `print(7 / 0)` is "division by zero: 7 / 0". Until now it panicked
     when it ran and wrapped in a release build (#29), while the same in a `const` was already an error, and a
     shift by a known count past the bits too. `nint` and `nuint` are left out, since their size is the
     machine's. Tested by `error_known_overflow`, `error_known_overflow_constant`,
     `error_known_overflow_const_name` and `error_known_divide_by_zero`.
2091. **A conversion between `float` and `double` makes a signalling NaN quiet, in the interpreter and in every
     build; a `float` read from memory or a union keeps its bits.** `double wide = float.fromBits(0x7f800001)`
     is `7ff8000020000000`, and `(float)wide` is `7fc00001`, as the machine converts. The interpreter kept the
     signalling bits when it widened, and a release build gave `7f800001` back, as the C compiler folds
     `(float)(double)x` into `x` (#46); compiled code now makes the result quiet itself (`sg_quiet_f`,
     `sg_quiet_d`, a test that costs nothing unless the value is a NaN). The interpreter read a `float` out of a
     union or raw memory through the machine's conversion and made a signalling NaN quiet there (#42); it now
     moves the bits as `float.fromBits` does, as compiled code always did. Tested by `ok_float_nan_widen` and
     `ok_union_float_nan`, interpreted and compiled.
2092. **A port stays an `int` where the network's library gives one.** `SocketAddress.port()`,
     `TcpListener.port()` and `UdpSocket.port()` give an `int` (#46). A port goes into the library only as text
     (`TcpListener.bind("127.0.0.1:8080")`), where its range is checked, and comes back as the type a number
     has where nothing else is said: every port fits, the 70 places in the examples, tests and pages that use
     `port()` print it, compare it or give it on, and a `ushort` would make `port() + 1` a `ushort` sum that
     can overflow at 65535. C#'s `IPEndPoint.Port` is an `int` too; Rust's `port()` is a `u16`.
     `ushort.parse` stays the way to read a port out of text with its range tested.
2093. **A comparison with `NaN` written out is a compile error.** `x == double.NaN` is always false and `x !=
     double.NaN` always true, so each is an error with the hint `` `x.isNaN()` `` (or `` `!x.isNaN()` ``); `<`,
     `<=`, `>` and `>=` too, without a hint (#29). A `NaN` held in a variable is compared as the hardware does,
     as before. Tested by `error_compare_nan` and `error_compare_nan_not`; `ok_number_tools` compares a
     variable that holds `NaN`.
2094. **A comparison that an unsigned type makes always true or always false is a compile error.** `n >= 0` and
     `0 <= n` are always true on a `byte`, `ushort`, `uint`, `ulong` or `nuint`, `n < 0` and `0 > n` always
     false: "`n >= 0` is always true: a `uint` is never negative". `while n >= 0` never ended, and in a release
     build it went on past 0, while `n > -1` was already refused (#46). Tested by
     `error_unsigned_never_negative`.
2095. **A fractional number beside a small integer takes the fractional type the result goes to.** `float g = k
     * 1.5` with a `byte k` is a `float`, where `1.5` was a `double` and the line was refused: the rule
     "Writing a fractional number" says a number takes the type it is used as, and `f * 2.5` with a `float f`
     was already a `float`. Only an integer type the fractional one holds exactly comes along (`byte`,
     `sbyte`, `short`, `ushort`; `int` only into a `double`) (#46). Tested by `ok_small_int_times_fraction`.
2096. **A panic writes its numbers as plain digits, in the interpreter as in compiled code.** "there is no
     memory for a list of 9223372036854775807 items", where the interpreter wrote `9 223 372 036 854 775 807`
     and compiled code the digits (#46). Every other number of a panic was already plain. Tested by
     `panic_list_capacity_too_large` and `panic_array_no_memory`.

Fixed without a choice, each with a case of its own:

- The hint of a narrowing conversion names the expression and says what a release build does: ``convert with
  `(int)total`; a value that does not fit panics, or is cut to size in a release build`` (`it panics if the
  value does not fit` said it always panics); from a fractional number, "becomes the nearest `int`" (#29).
- An overflow of arithmetic that is then widened names the wider type: `return megabytes * 1024 * 1024` in a
  function that gives a `long` hints ``compute in `long` from the start: `(long)megabytes * 1024 * 1024` ``,
  and `int total = a + b` with two `ushort`s ``(int)a + b`` (`panic_overflow_widened`,
  `panic_overflow_widened_ushort`), in the interpreter and in compiled code (#29, #46). A number that does not
  fit the small type beside it hints the same: ``compute in `int`: `(int)b + 1000` ``, ``compare in `int`:
  `(int)reading < 200` `` (`error_byte_sum_wide_literal`, `error_sbyte_compare_wide`).
- A division by zero names `tryDivide`, as the row "Panics name the way out" says (#29); a shift by a count
  found while running names ``& 31`` and `rotateLeft` (#46); a cast from a fractional number names
  `saturatingToShort()` beside `tryToShort()` (#46).
- A number written in the program that does not fit is shown as written, with its value if it is written in
  hex, binary or octal, and the hint of a declaration names its variable: `` `8_100_000_000` does not fit in
  int ``, hint ``a `long` holds it: `long population = 8_100_000_000` `` (a mask in hex: `uint`); `ulong
  mask = ...`; `float half = 0.5` for `0.5f` (#29, #46). `var x = 1 << 40` hints `long x = 1 << 40`.
  `16_777_217` where a `float` goes hints `16_777_217.0`, which rounds.
- `$"{n:N0}"` hints `{n}` for an integer and `{n:F0}` for a fractional number (#29); `x++`, `x--` and `++x`
  hint `x += 1`; `.5` hints `0.5`; `5.` at the end of a line is an error with the hint `5.0`, where the point
  was taken with the name on the next line.
- `rotateLeft` in place of the rule's own rotation, which panicked for a count of 0 (#46).
- Hints of `char` and `byte` name the program's own expressions: ``compare its code: `text[0] == (int)first` ``;
  `char first = text[0]` says that a byte of a text is a character only below 128 and names `text.chars()`;
  `byte.tryToChar()` is an error, as every byte is the code of a character; `text[3] == 'é'` hints
  `text[3..].startsWith('é')`; `c == "é"` hints `c == 'é'`; `string name = 'P'` hints `"P"`; a code that is no
  character is shown as written, or in hex when it is found while running (`0xD800`) (#31). `an `sbyte``, not
  `a `sbyte``. `sbyte`'s hints of bytes name `wrappingToByte` and `wrappingToSbyte` (#46).
- `ushort.parse("-1")` is `Invalid(0)`, not `OutOfRange`, as the rule says: a sign is not a digit of an
  unsigned type. The row now says it in so many words (#46).
