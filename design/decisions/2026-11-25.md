## 178. What each request costs a server

**Where the time went.** The file server and the HTTP server of the lane, in SG and in C, were run under the
lane's load on Linux (four cores for the server, four for the load, 50 connections), and their processor time
for each answer counted from `/proc`, with `perf` for where it went and `strace -c` for the calls of the system.
For a file of 1 KB SG made 12.3 calls of the system for each answer and C 6.1: `File.infoAsync` looked at the
path through a descriptor of its own (`openat2` with `O_PATH`, `fstat`, `close`, choice 1872), and
`File.openTextAsync` looked at it once more, so as not to open a FIFO, before it opened the file; C asks `stat`
and opens. Three walks of the path and three closes against one and one. The rest, 0.3 to 0.8 µs an answer on
every path, the HTTP server's `/ping` too, is SG's own code: the head of the request read, the tasks, the lock
of the pool. `__wake_up_sync_key`, high in both profiles, is the send waking the load's thread over the loopback,
in C as in SG. The author's word: both, the calls of the system first.

Approved on 25 November 2026:

1873. **A file opened only when it is a regular one, and the info of an open file.**
     (a) `File.openRegular(read string path)` and `File.openRegularAsync(..., token)` give a `StreamReader` as
     `openText` does, but only of a regular file: a folder is `IsDirectory`, and a pipe, a device or a socket
     is refused before it is opened, so a FIFO is never opened and a writer waiting on it is not let go.
     (b) `reader.info()` gives the `FileInfo` of the open file (`fstat`), as Rust's `File::metadata` and Go's
     `f.Stat()` do; it walks no path and waits for nothing, so an async function calls it as it is.
     (c) A new variant, `IoError.NotAFile`, written `not a file`.
     A file server opens the file first and asks the reader for its size and its time. In C, Rust and Zig the
     same order: the file is opened before `If-Modified-Since` and `Range` are looked at, so a file that cannot
     be read is 403 whatever they ask, as nginx answers it.

**As built.** On Linux `openRegular` looks at the path through a descriptor of the path alone (`O_PATH`, from
the cache alone in an async call, 1872), opens the file without waiting (`O_NONBLOCK`, which a regular file
does not heed) and looks at it again, since the path may have been given to a FIFO in between: two walks of
the path and two closes where there were three, and one `fstat` more, which reads what the kernel holds. On
macOS the path is asked with `stat`. On Windows a folder is told by its attributes and a device only by its
handle (`GetFileType`), so a device is opened and closed again. The interpreter does the same through Rust's
`metadata` and `OpenOptions`. `reader.info()` is done by the language's own module, `FileInfo.ofReader(read
reader)`, over a call of the system only it makes (`System.readerStatus`). Linux 7.2 adds `OPENAT2_REGULAR`, which
opens only a regular file in one call; it is not used yet: no machine of the project runs that kernel.

C, Rust and Zig still ask what the path is before they open it (1863: a FIFO is never opened), so they make
as many calls as before; only the order of what they answer changed. `trials/server/files/check.py` was
changed with them: a file that cannot be read is 403 before 304 and 416.

**Measured** in the lane's image (`measure.py --languages sg,c`, one run of each case, 25 November 2026), the
four cases of small files, SG and C only; the whole table is run again at night. Files of 1 KB with 50
connections: SG 452,000 answers a second against C's 637,000 (0.71 times; before, 0.66), 6.6 ms of the processor
for a thousand against 4.5; with 1,000 connections 409,000 against 649,000 (0.63; before, 0.52). A 404 is as it was
(0.70). A 304 opens the file now, in all four, and cost both a seventh: SG 514,000, C 713,000 (0.72), as nginx,
which opens a file before it answers 304 too. An A/B of the server before and after, built by one compiler and run
in turns five times without a profiler: 7.30 µs of the processor for each answer of 1 KB before, 6.21 after
(C 4.39), 417,000 answers a second before and 485,000 after. The calls of the system for each answer of 1 KB, by
`strace -c`: 12.3 before, 11.2 after, C 6.1.

**Tests.** `opens_only_a_regular_file` (in `tests/cli.rs`) runs a program interpreted and compiled, in a plain
call and as a task: a file, a folder, a path not there, a device (`/dev/null`, `NUL` on Windows), a FIFO on
Linux and macOS with a writer waiting on it, which must still be waiting after; `ok_open_regular` holds `info()`
to a file that grows and to a file whose path is given to another, and `error_info_stdin`,
`error_info_connection` and `error_info_args` to what has no `info()`. The four file servers pass
`check.py` on macOS and on Linux.

**After 1873, the cost of SG's own code** (no choice: nothing a program sees changes). A profile of each
function, `/ping` of the HTTP server with `perf` on, showed C's library taking the same time in both servers
(0.30 µs an answer in SG, 0.28 in C) and SG's own code 0.34 µs against C's 0.04, spread over some 25
functions, none above 1.5% of the time: the async functions of `std/http`, the loop of the network, the
parsing of the head. Two things stood out and were taken away.

- `indexOf` and `contains` of one byte (`byte` or `sbyte`) in a list, an array or a slice went through the
  bytes one by one in C; they ask `memchr` now, which looks at many at a time. `httpHeadStop` looks for the end
  of each head so, and it was the hottest line of `/ping`. Alone: 3.2 times as fast over 16 bytes, 6.4 over
  64, 14 over 512 and more. Test: `ok_index_of_byte`.
- A wait for a socket with a token, which every read and send of the HTTP module makes (its time limits),
  took the clock's lock, one for the whole program, twice for each answer: to put the wait on the token's list
  and to take it off when the socket was ready. Every cancellation source now has a lock of its own for its
  list; a cancel takes the clock's lock and then the source's, and the wait for a socket takes only its
  token's. A linked source's lock is taken after its parent's, and the lock of a socket's slot after both.
  An upper bound measured first (the wait not on the list at all): `/ping` 6.3% less of the processor.

**Measured** in the lane's image, an A/B of the servers built by the compiler before and after (the base with
`memchr` already), run in turns five times without a profiler, the middle run: `/ping` 1.22 million answers a
second before and 1.35 million after (C 1.40 million), 2.13 ms of the processor for a thousand before and 1.97
after (C 1.75); 404s 914,000 and 955,000 (C 1.18 million); files of 1 KB 471,000 and 496,000 (C 640,000), whose
runs spread more. What is left is spread thin; the file server's calls of the system (11 an answer against C's
6) are mostly the walk that keeps a FIFO and a path outside the folder from being opened.

**Tests.** The whole suite on macOS and on Linux, the async programs under the thread sanitizer as always;
Windows in CI.

## 179. A GIF tool, held to gifsicle

The trial after the file server in the order of 1418 (1531): a GIF tool, a step towards the program chosen to
show the language, gifsicle. It is written from the GIF89a specification, not from gifsicle's code, so that
nothing of gifsicle's licence comes into the repository; gifsicle is a witness in the tests and is measured
beside the three. Approved before the slice:

1874. **What is written**: `giftool [--info] [--unoptimize] [-O1|-O2] [--crop X,Y+WxH]
     [--flip-horizontal|--flip-vertical] [--rotate-90|-180|-270] [-o OUT] [IN]`. GIF87a and GIF89a, every
     frame, the screen's table and a frame's own, transparency, interlacing, the delays, the loop
     (`NETSCAPE2.0`) and the four disposals; comments kept, other extensions dropped; `-` or no file the
     standard input and output.
1875. **The algorithm, written by hand the same in the three**: the input held whole, each frame decoded,
     changed, encoded and let go, so that one or two screens are held, never every frame; LZW decoded with a
     reader of bits and a table of 4,096 prefixes and bytes, going on when a full table is not cleared (a
     "deferred clear"); encoded with the hash table of 5,003 slots `compress` and giflib use, the table
     cleared when full. The three write the same bytes from the same input.
1876. **What the options mean**: crop, flip and turn work on each frame's indices, its place moved with it,
     its table kept; `--unoptimize` draws the frames on a screen of 32-bit colors by their disposals and
     writes each whole, with the screen's table when it holds every color and a table of its own, the colors
     in the order they come, when not; more than 256 colors in one frame is an error, told as a limit of the
     trial (gifsicle reduces the colors); `-O1` cuts each frame to the rectangle of the pixels that differ
     from the screen before, `-O2` also makes clear those inside it that did not change, which LZW packs
     better.
1877. **`--info`** writes what `gifsicle -I` writes, byte for byte, held to a real tool as `jq` is held to
     jq 1.8.2.
1878. **The inputs**: no large file in the repository; the GIFs are made from a seed: tables of their own,
     interlacing, the four disposals, transparency, comments, tables of 2 to 8 bits, LZW streams whose table
     fills and is cleared and one that is never cleared. The tests also read what ffmpeg and gifsicle write.
1879. **What is measured**: 2,000 frames of 480 by 270 read and written; one frame of 8192 by 8192 (64
     million pixels, the speed of LZW); the first `--unoptimize`d and `-O2`; the second cropped and turned;
     `--info` of 10,000 small GIFs. Time and memory, as every trial; gifsicle 1.99 beside the three where it
     does the same work, its algorithm another, which the table says.
1880. **The tests**: a model in Python, a decoder and a compositor of its own (no Pillow): what each option
     writes, drawn, must show pixel for pixel what the same option makes of the input drawn; gifsicle's
     `--unoptimize` a second witness; what is written read by gifsicle and ffmpeg with no warning; `--info`
     against `gifsicle -I`; broken inputs: cut short, a code past the table, a code size above 11, a frame
     past the screen, no size, sub-blocks that never end, a closed output; interpreted against compiled.
1881. **A limit against a bomb**: a frame or a screen of more than 2^28 pixels (a screen of 1 GB) is an
     error, the same in the three; a frame of 65,535 by 65,535 alone asks 16 GB. gifsicle has no such limit,
     which the table says.

What was built. `trials/giftool/` holds the three versions, the page that says what each does
(`trials/giftool/README.md`, the specification they were written from), and the tests: `model.py`, a reader and
a compositor in Python and the text of `gifsicle -I`; `inputs.py`, which makes the GIFs from a seed with an
encoder of its own; `check.py`, which holds every build to the model; and `sample.gif`, eight frames of 830 bytes
for `the_trial_of_giftool` in `tests/cli.rs`. The inputs are made by Python, as those of `hashsum` and `kv` are,
in place of a program of `trials/inputs` (1878): an encoder written apart from the three's tests them better.
What the specification had to settle on the way, each as gifsicle or GIF has it: a code between 256 and the
clear code, which a code size of 9 to 11 allows, is a pixel past 255 and an error; `--info` reads no frame's
data, as gifsicle does not, so a GIF whose data is broken is told as it is; a GIF with no frames is told as
nothing, as gifsicle tells it, and is not written; the local tables of the animations measured hold colors of
the screen's, as an encoder that made one palette for the whole writes them, and the screen's table has 255,
so that `-O` has an index for its clear pixels. gifsicle is 1.99, which is what Homebrew gives; Debian's 1.96
writes the comments of the end before the loop, and the tests say so and do not hold `--info` to it.

The model was held to gifsicle before anything was measured: on every GIF that is not broken its `--info` is
`gifsicle -I`'s text, and what gifsicle's `--unoptimize` writes draws as the model draws the input. On macOS SG
compiled and interpreted, Rust, and Zig in both builds: 1,653 runs of three builds and 1,102 of two, none
differed and every build wrote the same bytes; on Linux SG, Rust and the interpreter, the same. The Zig version
also ran 4,000 GIFs with random bytes changed, against SG, in its safe build: the same bytes, no trap.

Measured on 25 November 2026 ([Programs against Rust and Zig](../../benchmarks/programs.md#giftool)): reading,
writing, cropping, flipping and turning, the three within 4%, SG's program the smallest (148 KB against 401 and
474); `--info` of 10,000 small GIFs 0.144 s against gifsicle's 0.318. Two differences, in
[Slower than C](../../benchmarks/slower-than-c.md): a lookup in `HashMap<uint, nint>` takes 9.4 ns against
Rust's 3.8, which makes `--unoptimize` 24% slower and `-O2` of whole frames 14%; and `-O2` of 2,000 frames is
faster checked than not (0.716 s against 0.852), clang having put a loop into a large function in the build
without checks.

## 180. The lookup of a `HashMap`, as hashbrown's

The GIF tool of slice 179 gives each color of a screen its index through a `HashMap<uint, nint>`, and there SG
took 24% more than Rust. Alone, a hundred million lookups of 255 keys took SG 0.97 s and Rust 0.38. Measured on
the C SG writes: one round of SipHash fewer for a key of four bytes, as Rust hashes a `u32`, 0.86 s; the key kept
in the slot, no faster; no SipHash at all, 0.54 s, still slower than Rust with it. The search itself was the
cost: one slot after another, a branch at each that the processor guesses wrong as often as right. The author's
word, after the proposal: both. Approved on 25 November 2026:

1882. **The lookup of a `HashMap` and a `HashSet` in compiled code, as Rust's.** (a) A key of four bytes or
     fewer (`byte`, `sbyte`, `short`, `ushort`, `int`, `uint`, `char`, `bool`) is hashed in one block of SipHash-1-3
     with its length, as Rust hashes a `u32`: one round fewer. (b) The slots are found as hashbrown finds them: a
     byte for each slot, the top seven bits of its key's hash or a mark for a slot free, read eight at a time and
     compared at once, the key looked at only where the seven bits agree. Nothing a program sees changes: the
     entries keep their order, and the hash keeps its secret key.

What was built. `TABLE` in `emit_c.rs` keeps the entries one after the other as before, and beside them `ctrl`,
a byte for each slot and a copy of the first eight at the end, so that eight can be read from any slot, and
`index`, the entry's place. A search reads eight bytes and finds those equal to the seven bits without a branch
for each (an exact test of each byte: a byte matched by mistake would send the search to a slot that holds no
entry), going from group to group by steps of 8, 16, 24 and on, which reach every group of a table whose size is
a power of two; a group with a slot never used ends it. A slot whose entry is removed is marked as never used
when no search can have passed it on the way to another, and as taken out when one may have, as hashbrown does.
The table is at most seven eighths full; when no slot never used is left, the slots are made anew from the
entries, twice as many when the entries fill more than half of them. The search is put where it is called,
as hashbrown's is: as a call it kept the next search from starting while one waited on its hash (0.60 s
against 0.48). The interpreter's tables are Rust's and do not change.

Measured, SG before and after (choice 1882 is held to Rust and Zig no further: from this slice on, SG is
measured against what it was, and a program against the C program it mirrors, by the author's word): a
hundred million lookups 0.97 s and 0.48 (Rust 0.39, Zig's `AutoHashMap`, whose hash has no secret key, 0.44);
`giftool --unoptimize` of 2,000 frames 2.22 s and 2.08, `-O2` of 300 whole frames 0.288 and 0.275; `kv`, whose keys
are lists of 16 bytes, a log of 1 GB read back 2.60 s and 2.45 in 194 MB and 177, ten million keys compacted
3.89 s and 3.74, a million sets 0.20 s and 0.18 in 197 MB and 184.

**Tests.** `ok_hash_churn`: maps with keys of four bytes, of eight and texts and a set, 180,000 adds and removes
over 3,000 keys, grown, emptied a key at a time and at once, each checked every 5,000 steps against lists of what
must be there; interpreted and compiled the same. Two changes made to the C by hand, every slot of an entry
removed marked as never used and the moved entry's place not written, are both found. The whole suite on macOS
and on Linux.

## 181. An interpreter of Lox, held to clox

The last trial of the order of 1418 (1531): an interpreter of Lox written after clox, the bytecode interpreter of
*Crafting Interpreters*, and measured against clox alone, as the rule of slice 180 has it. Approved before the
slice:

1883. **What is written**: clox whole, the chapters 14 to 30 of the book: the scanner, the compiler in one pass,
     the machine of bytecode, closures and upvalues, a collector that marks and sweeps, classes, inheritance,
     `super`, `clock()`. `lox [path]`, and the REPL without one. What it writes on the output and the standard
     error, and the codes it ends with (65 for compiling, 70 at run time, 74 for a file), are clox's byte for
     byte; the limits are clox's (256 constants, locals and upvalues, 255 arguments, 64 frames, "Stack overflow.").
1884. **The heap**: Lox's objects refer to each other in cycles. They are the items of one list and a value holds
     an item's place, a handle; clox's collector, marking and sweeping, works on the handles, and a freed place
     goes to a list of free places. No `unsafe`. (`shared`, whose count is always atomic and which leaks a cycle,
     and `raw` with `unsafe`, which would give up what the trial is for, were left.)
1885. **A value**: NaN boxing, in SG and in clox, as clox builds by default: a value is a `ulong`, a number its
     bits, an object a quiet NaN with the handle in it; only bits are moved.
1886. **The tables** are the language's `HashMap`: strings interned by their bytes, looked up through a window
     without copying them; the globals, the fields and the methods by the handle of the interned name; the
     collector takes out of the table of strings those no longer reached.
1887. **`%g`**: clox writes its numbers with `printf("%g")`, and SG has no such format; it comes into the library
     as a choice of its own (1892), not by hand in the trial.
1888. **The tests**: the book's tests (about 240 programs with `// expect:`, MIT) and clox, fetched at a commit by a
     script and not kept in the repository; a runner in Python; SG interpreted and compiled; the whole suite with the
     collector at every allocation; programs made from a seed held to clox byte for byte; the limits pushed (deep
     recursion, texts of a million characters, millions of objects, a string never ended, bytes that are not UTF-8,
     a pipe closed, one past each limit); `the_trial_of_lox` in `tests/cli.rs`.
1889. **What is measured**: the book's eleven benchmarks, time and memory, with fib, binary_trees and a program of
     texts at a small, a medium and a large size; clox built by its own Makefile in release with the same Clang. The
     table goes into `benchmarks/programs.md`.
1890. **A gap found is built**: each lack of the language or the library the trial finds is a choice of its own,
     approved, built into the language in the slice, and measured as SG before and after.

Found on the way and approved on 25 November 2026:

1891. **The bits of a `float` and a `double`**: `ulong d.toBits()`, `double.fromBits(ulong)`, and for a `float`
     `uint toBits()`, `float.fromBits(uint)`, as Rust's `to_bits` and `from_bits`; no cost (a `memcpy`) and no
     `unsafe`, every pattern of bits being a number.
1892. **`%e` and `%g` in `$"..."`**: `{x:e3}` is `3.142e+00`, `{x:g6}` is C's `%g` (`3.14159`, `1e+21`, `100000`,
     `1e+06`, `-0`); `E` and `G` write a capital `E`, as `x` and `X` do; C's rules, the exact value rounded.
1893. **The hash of a key of a fixed size** (an integer, a `bool`, a `char`, an enum whose variants carry nothing):
     a folded multiplication by the secret key, as hashbrown's foldhash and wyhash, in place of SipHash-1-3; text and
     lists keep SipHash. The lookups of fields and methods took 40% of the Lox machine's time in SipHash.
1894. **Two columns**: SG and clox as the book writes clox, the place in the code read through the frame at each
     byte, and both with that place kept in a local variable, the first challenge of the book's chapter "Calls and
     Functions", made to clox's `vm.c` by the same change: an idea of design is measured in both.

What was built. `trials/lox/sg/`: `scanner.sg`, `compiler.sg`, `vm.sg`, `heap.sg`, `value.sg`, `main.sg`, and
`local.sg`, the loop of 1894 (`--ip-local`). The program is kept apart from the heap: every function's code lies in
one list, put there when the compiler ends it, so that the machine reads the program while the heap changes. The
functions live as long as the program, and their constants are roots; the collector does not run while the
compiler does. The first sweep went over every place the heap ever had, and `instantiation` took 7.07 s against
clox's 0.39: the handles in use are now a list of their own, which the sweep goes over as clox goes over its
objects (0.41 s). `tests/clox.py` fetches the book's repository at its last commit (4a840f70, 1 August 2024) into
`trials/target/lox` and builds clox and `clox-ip-local`; `tests/check.py` holds each build to the book's tests and
to clox, `tests/fuzz.py` to clox on programs from a seed; `measure.py lox` measures SG, SG with its arithmetic
checked, SG `--ip-local`, clox and clox `--ip-local`.

In the language: `toBits` and `fromBits` (1891) in the checker, the interpreter (a `float` is an `f64` there, and its
`NaN` is widened and narrowed by hand so that its payload stays) and compiled code (`memcpy`); `&` on a `double` hints
at `toBits`. `e`, `E`, `g` and `G` (1892): compiled code calls `snprintf`, the interpreter writes from Rust's `{:e}`,
a program with `--freestanding` gets a compile error at the letter; held to Python's `%e` and `%g` on 5,729 values at
0 to 25 digits, interpreted and compiled, with no difference. `sg_hash_fixed` (1893) for the keys of a fixed size.

What the trial found besides. clox's compiler takes a nested expression on the C stack and ends on `SIGSEGV` at
200,000 levels; SG, whose main thread has 1 GB of stack, prints the answer at a million and ends with its panic,
`stack overflow`, at five million. Compiling one function with a thousand formatted `print`s at `-O2` takes clang
10 to 12 s and half a gigabyte, more than twice the time of five hundred: each formatted value is a buffer of its
own on the stack. Not this slice's work; it is in Slower than C.

Measured, SG before and after 1893: the Lox machine, `properties` 0.75 s and 0.38, `method_call` 0.33 and 0.19,
`invocation` 0.42 and 0.25, `zoo` 0.55 and 0.31, `trees` 2.78 and 1.80 (clox 0.22, 0.12, 0.15, 0.15, 1.21); a hundred
million lookups of 255 keys in a `HashMap<uint, nint>` 0.49 s and 0.16 (Rust's std, SipHash, 0.39); `giftool
--unoptimize` of 2,000 frames 2.08 s and 1.94 (Rust 1.79), `-O2` of 300 whole frames 0.275 and 0.262 (Rust 0.252);
`counts` of `bench/run.py`, a `HashMap` of 50,000 numbers, 0.322 s and 0.106 against its C's 0.305. The table of the
trial is in [Programs](../../benchmarks/programs.md#lox).

**Tests.** `ok_float_bits` (a thousand patterns of bits kept, a signaling NaN in both builds, a tag in a NaN),
`ok_format_exponent`, `error_format_general_integer`, `error_format_exponent_text`, `error_float_bits_hint`,
`error_float_from_bits_int`, `error_float_from_bits_wrong`, and `tests/freestanding/error_format_general`. The book's
246 tests and 19 programs of `tests/programs`, by the release build as it is, with the collector at every allocation,
with `--ip-local` and with both, and by the interpreter in the same ways, and by `clox-ip-local`: 2,114 runs, none
different from clox. 5,000 programs from a seed (250 ended well, 1,125 with errors of compiling, 3,575 with an error
at run time, 50 left out as clox took more than ten seconds): none different. `the_trial_of_lox`.

## The showcase: gifsicle in SG

The showcase chosen on 13 November is gifsicle, a tool in C that is used everywhere and has no Rust rewrite of note.
It is written in SG file by file in a repository of its own, [sg-gifsicle](https://github.com/selcukgural/sg-gifsicle),
under gifsicle's license. Approved on 25 November 2026:

1895. **Where.** A public repository of its own, under GPL-2.0 as gifsicle is, from gifsicle 1.99, with gifsicle's
     copyright and license at its head. The language's repository stays MIT OR Apache-2.0.
1896. **How.** Translated from gifsicle 1.99 file by file, keeping the names of the files and the order of the
     functions. Counted references become owners and indexes; a reader through function pointers becomes the whole
     file in memory; `goto` becomes loops; the macros that make one copy of the optimizer for each width of index
     become one copy.
1897. **Held to what.** Byte for byte to gifsicle 1.99 by default. Where floating point or heuristics decide (color
     reduction and dithering, the filters of resizing, the candidates of `-O3`), a valid GIF of the same size and
     frames, within the palette, with few pixels different; its README says which options are equal and which near.
1898. **Built how.** A fixed commit of the language, named in a file of the repository, built with `cargo build
     --release`, then `sg build`; its CI does the same on Linux and macOS.
1899. **Tested how.** gifsicle's own tests, every output compared with the C gifsicle built on the same machine
     (sample GIFs and GIFs from a seed), and fuzzing; measured against the C gifsicle only.
1900. **In what order.** The core first (read, `-I`, `-O1` to `-O3`, write, the options, merging, choosing frames),
     then resizing, color, lossy compression, `-j` and `--exec`, and a last check. A gap of the language is a slice
     of the language's own, with its numbered choice, and is not worked around in the port.

The first stage is done: every option of the core gives what gifsicle 1.99 gives, output, standard error, exit code
and files, on the icons of a system and 178 animated GIFs from a seed under 34 sets of options, and 10 of gifsicle's
23 tests pass; the other 13 need the later stages.

## 182. Whether a stream is a terminal

gifsicle will not write a GIF to a terminal, and tells why; to know, it asks `isatty`. SG could not ask: only
`System.colourTerminal()`, which `Log` uses, looked, and only at the standard error. Approved on 25 November 2026:

1901. **`isTerminal()` of every `StreamReader` and `StreamWriter`.** It gives a `bool`: whether the stream is a
     terminal (`isatty`; on Windows a console, `GetConsoleMode`). `Stdin`, `Stdout`, `Stderr` and a file opened on
     `/dev/tty` can be; a connection and the pipes of another program never are. It takes a `read` borrow and does
     not wait, so it has no async form.

What was built. The checker knows `isTerminal` on both kinds of stream, after `buffered` and before the check that a
stream is lent with `ref`; `isTerminalAsync` is an error that names `isTerminal`. Compiled code calls
`sg_reader_terminal` and `sg_writer_terminal` of `IO_RUNTIME`: a reader of a connection or a pipe answers `false`
without asking, the rest asks `sg_sys_terminal` of its descriptor; on Windows the output and the standard error are
asked through `GetStdHandle`, since their descriptors are not handles. The interpreter asks Rust's `IsTerminal` of a
file, and for its own streams `World` now says whether the output and the standard error are terminals, as it said of
the input.

**Tests.** `ok_is_terminal_process`: the three streams, a file written and read, a connection and both pipes of
another program, each asked through a `read` borrow, none a terminal, and what is read and written around the
questions all there; interpreted (in a process of its own, as the program is run) and compiled the same.
`error_is_terminal_async` and `error_is_terminal_argument`. `streams_on_a_terminal` in `tests/cli.rs` runs the
program on a terminal of its own with `script`, interpreted and compiled: the three streams and `/dev/tty` opened
to read and to append are terminals; with the input, the output and the standard error sent into files those three
are not, and `/dev/tty` still is.

## 183. The conditional operator `?:`

A value picked by a condition took a `match` on `true` and `false`, or a variable assigned in an `if`: `if` is a
statement, and there was no `?:`. Approved on 25 November 2026:

1910. **`c ? a : b`.** `a` where `c` holds, otherwise `b`; only the arm chosen runs. The condition is a `bool`: a
     number or a `T?` is an error, with the hint an `if` gives. As in C#; Rust writes `if c { a } else { b }`, and
     `if` stays a statement here.
1911. **Order and grouping.** It binds more loosely than any other operator, `??` too: `a ?? b ? c : d` is
     `(a ?? b) ? c : d`. It groups to the right, `a ? 1 : b ? 2 : 3` is `a ? 1 : (b ? 2 : 3)`, and a nested one
     needs no parentheses. C#'s order and grouping.
1912. **The type.** The rule of the arms of a `match`: both arms have one type; an arm that is only a number takes
     the type of the other one, and `null` with a `T` gives a `T?`.
1913. **Names and narrowing as in an `if`.** The first arm sees the names of an `is` in the condition and what it
     narrows (`p is not null ? p.x : 0`, `r is Ok(v) ? v : 0`); the second sees the names of an `is not` and what
     a failed test narrows (`r is not Ok(v) ? 0 : v`). C# does the same.
1914. **Not a statement.** `ready ? start() : stop()` alone is an error whose hint is the `if`, and an arm that gives
     nothing is an error. C#'s rule.
1915. **No `return` in an arm.** Leaving the function stays with `if` and with `?? return`.
1916. **In parentheses inside `$"{...}"`.** A `:` there starts the format (`{x:X}`), so `{(c ? a : b)}`, as in C#;
     without them the error says so.

What was built. The parser reads `?:` above `??`, so the right side of `??` now stops before a `?`. A statement that
starts `flag ? x ...` is not taken for a declaration of a `flag?` named `x`: a name after a type ending in `?` is
declared only when `=` or the end of the line follows it. A line may end with `?` or `:` and go on; one that starts
with either is an error whose hint moves it. The lexer stops at the `:` of a `?:` inside `{ }` of a formatted text and
asks for the parentheses; a `?` that ends a type there (`{List<int?>().length():X}`) is not taken for one. The checker checks `c ? a : b` as `if c { a } else { b }`: the condition has a scope that
the first arm shares, the second arm gets the names of an `is not` and the narrowing of a failed test, the moves of the
two arms are joined, and an arm that never gives a value (`panic(...)`) does not reach what comes after. An arm that
is only `null`, or a number before one with a point, is checked after the other arm, whose type it takes. An arm that
is a borrow of a `Copyable` value (the `v` of `r is Ok(v)`) gives the value, as `??` does, unless it lends on purpose
(`read x`) or the place wants a borrow. The value of a `?:` that borrows carries the borrows of the names of its
condition, as a `match` carries those of its subject: `var t = r is Ok(s) ? s : "x"` keeps `r` lent while `t` is used
(found while the slice was built, before anything was committed: without it `r` could be moved and `t` left pointing
into it). The interpreter computes the condition in a scope of its own and then the arm chosen. Compiled code writes
the `if` it is before the statement, as a `match` inside an expression is, and gives the value through a name; in a
declaration, an assignment, a `return` or the last line of an arm it writes into the place, so a chain becomes nested
`if`s. clang -O2 makes the same instructions of that `if` as of C's `?:` (a `csinc`, no branch, on arm64).

**Tests.** `ok_cond` (the type rules, literals taking the other arm's type, `T?` from `null`, narrowing, `is` and
`is not` names, in a formatted text, in an operator, over lines), `ok_cond_arms` (only the arm chosen runs, owned
texts moved and made in the arms, in a struct literal, nested, in a `while` condition, on the right of `&&`, a `try`
in an arm, `?:` on the right of `??`, a `panic` arm, inside a `match` arm, in a loop), `ok_cond_names` (`is` names
along `&&` and `||`, `read` arms returned from a function, `char` and `long` arms), `ok_cond_borrows` (lent arms,
borrows of `Copyable` values copied, a borrowed text from an `is` name), `ok_cond_chain` (200 arms in one chain),
`ok_cond_null_chain` (`p?.age ?? 2` beside `?:`), `ok_cond_order` (a `ref` in an arm and the parts around it computed
from left to right), `panic_cond_arm`, and sixteen `error_cond_*` cases: a number and a `T?` as the condition, a statement, an arm with
no value, `return` in an arm, no parentheses inside `{ }`, two types, `null` alone, a line that starts with `?`, an
`is` name in the wrong arm, a `T?` not narrowed, no `:`, `??` taking the condition, a move in an arm, a borrow kept
from an `is` name and from an arm, and `a ?? 0 > 18 ? ...`, which reads `a ?? (0 > 18)`: the note says so and the
hint writes `(a ?? 0) > 18`. Every `ok_` case runs interpreted and compiled, with the address sanitizer and the
leak check. By hand: chains of 300 and 990 arms run both ways, one of 5,000 is the error for nesting deeper than
1,000.

The generator of `fuzz/difference` writes `?:` now: `(c ? a : b)` among the integer expressions, outside a const,
and `(x is not null ? x : n)` beside `x ?? n`. Its first run, 2,128 programs in five minutes, found no difference
but seven programs the back end refused: a `?:` after a text in a formatted text (`$"{t}{(c ? 1 : 2)}"`). The back
end had taken a `?:` for something that may change what the parts beside it read, as a `match` may, and a text
before such a part is not in the back end yet; a `?:` does what its parts do, and its lines before the statement are
put in order as any part's are. The seven compile and print what the interpreter prints, and a second run in the container, 10,893 programs in ten
minutes, found nothing and had none refused. libFuzzer ran the lexer and parser for eight minutes (3.6 million inputs)
and the checker and the C writer for ten (666,000), with the tests of the slice in the corpus and ` ? ` and ` : ` in
the dictionary: no panic, no hang, no stack or memory run out. A `?:` is not yet a const
(`const int n = big ? 8 : 4`): the error says a const is made of operators and casts.

Also in this slice: `b != null` is refused with a message that names `!=` (it named `==` for both) and a hint that
names the value (`b is not null`, not `x is not null`); `error_null_compared_equal` and
`error_null_compared_not_equal`. `fuzz/run.sh` and `fuzz/difference/run.sh` leave `trials/target` out of what they
copy: a file there that only its owner reads stopped the copy, and with it every run.
