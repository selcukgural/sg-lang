# Async, the direction

*Decided on 14 November 2026, to be built after threads.* Async takes C#'s behaviour, compiled the way Rust compiles it:
`async` functions, `await`, the same `Task<R>` that `Task.run` gives, and cancellation tokens. The rows of threads in the
decisions table (["Starting a task"](../rules/concurrency.md#starting-a-task) to ["Tasks in the interpreter"](../rules/concurrency.md#tasks-in-the-interpreter)) were chosen so that nothing in them changes when async
comes.

```
async Result<int, IoError> countLines(string path, CancellationToken token) {
    var text = try await File.readTextAsync(read path, read token)
    int lines = 0
    for line in text.lines() { lines += 1 }
    return Ok(lines)
}

async Result<void, IoError> main() {
    var source = CancellationSource.after(5000)          // cancelled after five seconds
    var first = countLines("a.txt", source.token())      // Task<Result<int, IoError>>, already running
    var second = countLines("b.txt", source.token())
    print(try await first + try await second)
    return Ok()
}
```

| Topic | Direction | Reason |
|---|---|---|
| <a id="how-it-is-compiled"></a>How it is compiled | Each `async` function becomes a state machine; the machines of the functions it awaits are put inside its own. A task takes one allocation when it starts and none for each `await`; there is no garbage collector | Rust's cost. C# allocates a `Task` for each async call and collects it later |
| <a id="starting"></a>Starting | An async function called without `await` gives a `Task<R>` that has started, and runs on the caller until its first `await` that has to wait, as in C#. `await f()` takes no allocation. `f()` alone on a line is an error, as `Task.run(...)` is (["Every task is waited for"](../rules/concurrency.md#every-task-is-waited-for)) | In Rust a future does nothing until it is polled, so a forgotten `.await` runs nothing and only a warning says so |
| <a id="one-runtime"></a>One runtime | A pool of threads, a clock for delays and threads for input and output that has to block come with the language, and only programs that use tasks carry them. *Changed on 15 November 2026, before the sixty-first slice:* a file cannot be waited for with epoll or kqueue, since it is always ready, so a read or a write of a file runs on a thread of its own and wakes the task when it is done, as Tokio does it; the loop that waits for the network (epoll, kqueue, IOCP) comes with the network. *Built on 15 November 2026, in the sixty-fifth slice:* one thread waits with epoll or kqueue for every socket a task waits for (["The loop of the network"](#the-loop-of-the-network)). *Changed on 16 November 2026, in the eighty-first slice:* that thread is one of the pool, the one with nothing to do, as Tokio's driver. *Changed on 16 November 2026, in the eighty-third slice:* each thread of the pool has a queue of its own, which the others steal half of when they have nothing, and a slot for the task that the task it runs woke; a task woken outside the pool goes on a queue they share, as in Tokio | Rust has several runtimes (tokio, async-std, smol) whose libraries do not fit each other |
| <a id="cancellation"></a>Cancellation | `CancellationSource` (`source.token()`, `source.cancel()`, `CancellationSource.after(ms)`); a token is passed as a parameter, and a task stops only where it looks at its token, as in C#. Dropping a handle cancels nothing, and a handle cannot be dropped anyway | No task stops at a place it did not choose |
| <a id="waiting-the-wrong-way"></a>Waiting the wrong way | `t.wait()` in an async function is an error whose hint is `await t`; a call that blocks (input and output that is not async, or a function that does it) in an async function is an error whose hint is its async version or `Task.run`. `Task.run` of a function that blocks runs it on threads of its own; the compiler knows which functions block, so the program does not choose | C#'s best known deadlock is waiting for async code from code that is not async (`.Result`, `.Wait()`), and a call that blocks inside async code starves the pool in C# and Rust alike. Tokio makes the program choose between `spawn` and `spawn_blocking` |
| <a id="locks"></a>Locks | `await` inside a `lock` block is an error (["A `lock` block does not wait"](../rules/concurrency.md#a-lock-block-does-not-wait)); there is one kind of lock. An ordinary `lock` can be used in async code, since nothing inside it waits | Rust needs a second, async lock to hold across `await`, and holding the first one there deadlocks or does not compile |
| <a id="no-pin"></a>No `Pin` | A state machine is never a value the program holds; a `Task` lies on the heap and does not move | Rust needs `Pin` because a future is a value that could move while something points into it |
| <a id="calling-itself"></a>Calling itself | An async function that calls itself, directly or around, is an error whose hint is to keep the call's `Task` in a variable, which puts it on the heap | A state machine that holds itself would have no end; Rust writes `Box::pin` |
| <a id="not-taken-from-c"></a>Not taken from C# | `async void`, `ConfigureAwait` and the synchronization context, `ValueTask`, `.Result`, exceptions (an error is a `Result`, `try await f()`) | Each is a second way, or a known trap |
| <a id="waiting-for-several"></a>Waiting for several | `Task.whenAll`, `Task.whenAny`; `whenAny` cancels nothing, and the tasks that lost are still waited for. *Built on 15 November 2026* (["A list of tasks and its end"](#a-list-of-tasks-and-its-end), ["What `Task.whenAny` gives"](#what-task-whenany-gives)) | The rule ["Every task is waited for"](../rules/concurrency.md#every-task-is-waited-for) holds |
| <a id="a-list-of-tasks-and-its-end"></a>A list of tasks and its end | *Decided on 15 November 2026, before the sixty-third slice.* A `List<Task<R>>` is given to `Task.whenAll`, or emptied by a loop `while tasks.length() > 0` with no `break`, after which the compiler counts its tasks as waited for; anything else is a compile error. A way out with an error waits for what is left in it (["An exit with an error waits for a task"](../rules/concurrency.md#an-exit-with-an-error-waits-for-a-task)) | The loop that takes tasks one by one ends only when none is left, which the compiler can see as it sees `while x is null`. Swift's task group waits for what is left when it ends and drops what they give, which would let an error go unseen |
| <a id="what-task-whenany-gives"></a>What `Task.whenAny` gives | *Decided on 15 November 2026, before the sixty-third slice.* `await Task.whenAny(ref tasks)` gives what the first task to end gave and takes that task out of the list, as Rust's `JoinSet::join_next` | C# gives the task that ended, so that its state can be looked at; an SG task has no state beside what it gives, so the value comes in one step |
| <a id="no-iscompleted"></a>No `isCompleted` | *Decided on 15 November 2026, before the sixty-third slice.* A task cannot be asked whether it has ended without waiting for it. What C# keeps on a task (`IsFaulted`, `IsCanceled`, `Exception`) is in what an SG task gives: an `Error(...)`, a `Cancelled` | A loop that asks without waiting holds its thread: in the interpreter, where tasks change hands only where one waits, it would never end. `Task.whenAny` answers which task has ended |
| <a id="a-writer-dropped-in-async-code"></a>A writer dropped in async code | *Decided on 15 November 2026, before the sixty-fourth slice.* A writer an async function drops without `closeAsync` (on a way out with an error, at the end of a block, as a field, an item or a `shared` value that ends, or given another value) has its block written and its file closed on a thread of input and output, and the function awaits that where the writer is dropped; the error is lost, as when a writer ends without `close` in code that is not async. The writers and the tasks left behind on a way out end together, in the reverse order of their names, one after the other. A cancelled token does not stop the closing | C#'s `await using` and Python's `async with` await the closing on the way out of an exception; Rust has no async drop, and Tokio's `BufWriter` loses what it holds. Before, the writer was closed on a thread of the pool, which held it while it wrote |
| <a id="the-async-methods-of-a-writer"></a>The async methods of a writer | *Decided on 15 November 2026, before the sixty-fourth slice.* What the block of 64 KB can take is written into it in place, without waiting, as a read the block can answer (["A read the block can answer, in place"](../rules/concurrency.md#a-read-the-block-can-answer-in-place)); a full block goes out on a thread of input and output while the task waits, `flushAsync` waits only when the block holds something, and `closeAsync` always goes to a thread. `Stdout` and `Stderr` have the async methods too, done in place and in order with `print`; `closeAsync` on them is an error | A function given a `ref StreamWriter` works when it is given `Stdout`, and writing a line costs no wait unless a block is full |
| <a id="channels"></a>Channels | When tasks send each other messages, two can wait for each other, which no compiler can see. If every task waits and no input, output or timer is pending, it is a panic that says so, as Go does; in the interpreter this is exact, and since the hundred-and-ninety-third slice compiled code gives the same panic, counting the threads that are awake and the waits for what is outside the tasks (2002-2010). *Decided on 18 November 2026, before the hundred-and-thirteenth slice (choices 1276 to 1289).* `var jobs = Channel<int>(16)` is the end that receives, with room for 16 items, always at least one, taken once (no channel without a limit, none with no room); `jobs.sender()` gives a `Sender<int>`, `.clone()` one more end of either kind, and several receivers share the items, each to one of them in order. `tx.send(x)` waits while the channel is full and gives `false` when no end receives any more, the item dropped; `jobs.receive()` waits while it is empty and gives `null` once every sender has ended and nothing is left: there is no `close`. `for job in jobs` receives until then. `sendAsync` and `receiveAsync` in async code; a token may come last on the four, which then give a `Result` whose error is `Cancelled`. No `tryReceive` or `length`; `select` came in the 192nd slice (["Waiting on several channels"](../rules/concurrency.md#waiting-on-several-channels)). An item follows the thread rule and is never a `T?`; a send or a receive is not in a `lock` block; a `for` over a channel while a sender this function made of it lives is a compile error. What is left ends with the last end | Never a program that hangs without a word. Rust's `mpsc` ends the same way, by `drop`, but has one receiver and needs a tuple; Go's `close` twice is a panic and its unbuffered channel and `select` are a second way; C#'s `Writer.Complete()` can be forgotten |
| <a id="channels-as-built"></a>Channels, as built | *Built on 18 November 2026, in the hundred-and-thirteenth slice.* The async versions are awaited where they are written; a `for` over a channel in a variable does not take it; a wait the channel lets go on is not cancelled, and a cancelled send drops its item; a channel of a `StreamWriter` is not here yet; an item not taken is dropped inside the call. In compiled code one block holds the header and the ring, a thread sleeps on a condition of its own and an async task is woken through the pool; an item wakes the first receiver that waits, and the last end of a kind all of the other kind. The interpreter looks at those that wait at each change of turn, and stops on tasks that wait for each other (399). Choices 1290 to 1299, approved on 18 November 2026 | In compiled code tasks that wait on channels for each other wait for ever until the count of waiting tasks of the hardening (the 193rd slice) |
| <a id="time-zones-and-dates-in-text"></a>Time zones and dates in text | *Decided on 18 November 2026, before the hundred-and-fourteenth slice (choices 1300 to 1310).* The offset of the system's time zone at a moment comes from the system, through one more call that only `std` makes (`localtime_r` on Linux and macOS, which reads `TZ`; on Windows the rules Windows keeps for each year). `DateTimeOffset` is a moment with its offset from UTC: `d.toLocal()`, `d.withOffset(offset)` (`InvalidOffset` for a day or more), `DateTimeOffset.local(y, m, d, h, mi, s)` from what the clocks of the place show (`SkippedLocalTime` in the hour summer time skips, the earlier moment in the hour it repeats), `t.toUtc()` back, no `now()`. Its parts are those of the place; `offset()` is a `Duration`; `plus` keeps the offset; equal by moment and offset, in order by moment then offset. Printed `2026-11-18T12:30:05+03:00` (`+00:00` for 0, `:ss` for the old local mean times). `DateTime.parse` and `DateTimeOffset.parse` read RFC 3339 strictly, the first taking the moment to UTC; `DateError` gains `InvalidText(position)`, `InvalidOffset` and `SkippedLocalTime`. No pattern of your own: the parts and `{n:D2}` write any form. No zones by name yet | `DateTime` stays in UTC and in 8 bytes, so a local time is never taken for UTC; Go's one `time.Time` compares the place with `==`. A format written with the parts is checked when the program is compiled, where a pattern is read when it runs |
| <a id="time-zones-and-dates-in-text-as-built"></a>Time zones and dates in text, as built | *Built on 18 November 2026, in the hundred-and-fourteenth slice.* A `DateTime` where a `DateTimeOffset` goes, or the other way, is an error whose hint is `toUtc()`, or `toLocal()` and `withOffset`. An offset with a part of a second is `InvalidOffset`. `parse` checks the whole form first, then the parts as `DateTime.utc` does, then the offset, then the range with the fraction. `local` reads the offsets a day before, at and a day after, and keeps each moment at which its offset is in force. Choices 1311 to 1317, approved on 18 November 2026. *Since the hundred-and-fifty-third slice (22 November 2026, choice 1675):* a million moments seen in a zone take 3.9 times `chrono`'s time, which reads the TZif file of the zone once and finds each offset itself; SG asks `localtime_r` each time, as Zig's program does. A reader of TZif of SG's own, on Linux and macOS, is the way ahead; Windows keeps the rules of its system | macOS takes the rules of a `TZ` written out only from 1970 on; the offset is read again at each call |
| <a id="a-cancellation-in-a-result"></a>A cancellation in a `Result` | *Decided on 15 November 2026.* An error of its own type, the built-in `Cancelled`: `token.check()` gives a `Result<void, Cancelled>`, `Task.delay(ms, read token)` a `Task<Result<void, Cancelled>>`. `IoError` has the variant `Cancelled(Cancelled cancelled)`, so async input and output still gives an `IoError`, and `try token.check()` turns one into the other by ["Error conversion"](../rules/errors.md#error-conversion) | A cancellation is told apart from a failure without a second error type in every signature. The cost: a `match` that names every variant of `IoError` needs one more arm |
| <a id="the-names-of-async-input-and-output"></a>The names of async input and output | *Decided on 15 November 2026.* C#'s: the name of the function that holds the thread with `Async` at the end (`File.readTextAsync`, `reader.readLineAsync`), and a token that may come last, lent with `read` | One name to learn for each piece of work, and the token is not written where nothing is to be cancelled |
| <a id="the-network-as-written"></a>The network, as written | *Decided on 15 November 2026, before the sixty-fifth slice.* TCP first: `TcpListener.bind("host:port")`, `listener.port()`, `listener.accept()`, `TcpStream.connect("host:port")`, `stream.receive(ref buffer)` (what has come, how many, 0 at the end) and `stream.send(bytes)` (all of them), each without async and with it (`acceptAsync`, ...), with a token that may come last. An address is one text, `[::1]:80` for v6; `bind` looks no name up and never waits. Four new variants of `IoError`: `ConnectionRefused`, `ConnectionReset`, `AddressInUse`, `HostNotFound`. A socket has no buffer and closes where it ends. `receive` and `send` are C#'s names for a socket: `read` is a word of the language. *Changed on 15 November 2026, before the sixty-sixth slice:* `send` goes through a `read` borrow, and a connection is read through a buffer by a reader of its own (["Lines over a connection"](#lines-over-a-connection)) | Rust and Go write the address as one text; C# has both kinds of call. An async version beside each call is the rule of the files (["The names of async input and output"](#the-names-of-async-input-and-output)) |
| <a id="a-cancel-ends-a-wait"></a>A cancel ends a wait | *Decided on 15 November 2026, before the sixty-fifth slice.* A cancel ends a wait for a socket at once, and nothing that came is lost. A wait for a line of an input that can make the program wait (a pipe, a terminal) ends too: the read goes on on a thread, and what it reads stays in the reader's block for the next read | macOS cannot wait for a terminal with kqueue or `poll`, so the input is not waited for on the loop; a thread that reads on is what C# and Tokio do too |
| <a id="lines-over-a-connection"></a>Lines over a connection | *Decided on 15 November 2026, before the sixty-sixth slice.* `conn.reader()` gives a `StreamReader` that borrows the connection and reads it through a block of its own: `readLine`, `lines()`, `readText`, `readBytes`, `readSome` and their async versions work on it, and a function that takes a `ref StreamReader` reads a file, the input and a connection alike. `send` goes through a `read` borrow, so the connection sends while the reader holds it; `receive` still needs a `ref`, so a `receive` while the reader is used again is a compile error, and bytes are never taken from under its block. Neither goes through a `shared` connection, which tasks on several threads may own. The reader lives no longer than the connection: it is kept in a variable and lent | Rust, Go and Zig read a socket through a separate buffered reader too; Rust's trick is `Write for &TcpStream`. No copy of the socket (`dup`), so the other side sees the end when the connection ends |
| <a id="the-longest-line-over-a-connection"></a>The longest line over a connection | *Decided on 15 November 2026, before the sixty-sixth slice.* The reader of a connection gives no line, and no text, longer than 64 KB (`conn.reader(limit)` for another limit): a longer one is `IoError.LineTooLong`, and so is every read after it. A reader of a file or of the input has no limit | The other side of a connection could make the memory grow without end; Go's `bufio.Scanner` has the same 64 KB. Safe by default, as everywhere in SG |
| <a id="a-read-that-gives-what-is-there"></a>A read that gives what is there | *Decided on 15 November 2026, before the sixty-sixth slice.* `reader.readSome(ref buffer)` on every `StreamReader`: what the block holds, or what one read of the system gives when it is empty, at most what the buffer holds; 0 at the end. `readBytes` still fills the buffer unless the end comes first | Rust's `BufReader::read` and C#'s `Stream.Read`. A message whose length is not known is read without waiting for a full buffer |
| <a id="the-loop-of-the-network"></a>The loop of the network | *Decided on 15 November 2026, before the sixty-fifth slice.* In compiled code one thread waits for the sockets with epoll (Linux) or kqueue (macOS) and wakes the task through the pool (*changed on 16 November 2026, in the eighty-first slice:* a thread of the pool with nothing to do waits on the loop itself, one at a time, and runs the tasks it wakes; at most one idle thread at a time is woken to look for work, Tokio's rule; *changed on 16 November 2026, in the eighty-third slice:* a queue for each thread, from which the others steal); a socket is waited for once each time it is not ready (*changed on 16 November 2026, in the eighty-second slice:* a socket goes on the loop once and stays until it is closed; the loop writes what is ready into the socket's slot, where its tasks wait; *changed on 22 November 2026, in the hundred-and-fifty-fourth slice:* on Linux and macOS a send that the socket took only part of, and a receive that gave fewer bytes than there was room for, mark the socket not ready, as Tokio does, so the next call waits for the loop rather than try the socket and be told so (1687), unless the loop has seen the other side close, which stays in the slot (1696)). In the interpreter the scheduler waits for the sockets with `poll` when no task can run | One runtime, carried only by a program that uses the network the async way |
