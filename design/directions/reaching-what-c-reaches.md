# Reaching what C reaches, the direction

*Decided on 16 November 2026, after the eighty-third slice.* No preview of the language comes out while there is work
that C can do and SG cannot. The rows below were decided together (choices 703-718); each slice decides the details of
its own part before it is written. *Reached on 17 November 2026, with the ninety-fourth slice: each of the seven
programs of the threshold runs and is tested. The slices came out one later than planned (the ninety-second became a
rule of names, ["A name that hides another"](../rules/statements.md#a-name-that-hides-another)), so the kernel is the ninety-fourth. Windows is talked through next.*

| Topic | Direction | Reason |
|---|---|---|
| <a id="the-threshold"></a>The threshold | It is reached when each of these runs and is tested: a program that keeps its data in sqlite; a client that fetches a page over HTTPS with libcurl; a server that ends cleanly on Ctrl-C; a library written in SG and called from C; a small kernel that boots in QEMU, writes to its serial port and takes a timer interrupt; a queue without locks, built on atomics; a reader of a binary header with a union and bit fields | A list of programs can be checked; "everything C can do" cannot |
| <a id="the-order"></a>The order | 84: a C file beside the program, the variables of C, `errno`, a pointer as an integer and back, the difference and the order of two pointers. 85: functions of SG that C calls (`export`), pointers to functions of C both ways (`CFunc`), the state a callback reaches. 86: calls of C with a varying count of arguments, and sqlite wrapped. 87: libcurl wrapped. 88: signals. 89: unions, bit fields, `packed` and alignment. 90: atomics and `volatile`. 91: a library built from SG. 92: building without an operating system. 93: the kernel in QEMU *(17 November 2026: the ninety-seventh slice written, 980 to 998. Decided the same day: the tests on Windows are run whole when a release is near, not after every slice, since a run on the machine of Windows takes most of an hour; the CI still runs on every push and nobody waits for it, what it finds being made right before the release; while a slice of Windows is written, a few programs are tried there)* | The C file comes first: it opens macros, inline functions, assembly and intrinsics at once. sqlite needs callbacks, libcurl a varying count of arguments |
| <a id="a-c-file-beside-the-program"></a>A C file beside the program | `extern "./native.c" { ... }` names a C file of the module's folder instead of a library; it is compiled into the same unit as the program, so a `static inline` function of it is inlined and costs nothing. The interpreter builds it into the library of its wrappers | One door for what a header gives and a library does not: macros, inline functions, assembly, intrinsics, `setjmp`. Rust takes it through the `cc` crate and a second build script |
| <a id="the-variables-of-c"></a>The variables of C | `extern { int opterr }`: a variable of C, read and written only inside `unsafe`. SG has no variable of its own that is assigned freely; what lives for the whole program is a `static` (["Globals, as decided"](../rules/concurrency.md#globals-as-decided)) | Some C libraries keep their state in variables; a kernel's interrupt keeps its state where the handler finds it |
| <a id="errno"></a>`errno` | Read right after the call of C it belongs to; the interpreter keeps it as each call of C ends, so that its own work does not change it; an `IoError` is made from its number | Rust's `last_os_error`; a C library answers most failures this way |
| <a id="functions-of-sg-that-c-calls"></a>Functions of SG that C calls | `export int compareInts(raw void a, raw void b) { ... }`: a signature of C types only, the name C sees as written. A panic inside ends the process with its message; nothing unwinds through C | Callbacks, and the functions of a library built from SG, are the same thing |
| <a id="pointers-to-functions-of-c"></a>Pointers to functions of C | A type of its own, `CFunc<raw void, raw void, int>`, apart from `Func`; the name of an `export` function is a value of it, and one that comes from C (`dlsym`, a field of a struct) is called only inside `unsafe`. A `Func` does not go to C | A pointer from C may be wrong, and a `Func` may take types C does not know |
| <a id="the-state-a-callback-reaches"></a>The state a callback reaches | There are no lambdas and no globals that are assigned freely (a `static` is read only, atomic or locked), so the state of one call goes through C's `void* userdata`: `unsafe Memory.addressOf(ref state)` gives a `raw void`, and `unsafe (ref State)data` lends it again inside the callback. That the value lives long enough is the program's promise; the interpreter keeps the addresses it gave in a table and panics on a wrong type or a value that has ended | Rust's way; the interpreter checks it as it checks raw memory |
| <a id="signals"></a>Signals | Not handlers written by the program: `Signals.listen(...)` and a wait for the next one (`next()`, `nextAsync(token)`), as in Go and Tokio; while a listener lives, those signals do not end the program. A handler of C is still possible inside `unsafe`, through `export` and `CFunc`. Built in the eighty-eighth slice (["Signals, as built"](../rules/input-output.md#signals-as-built)) | A handler runs between any two steps of any thread; almost nothing is safe inside it |
| <a id="a-varying-count-of-arguments"></a>A varying count of arguments | `int curl_easy_setopt(raw CURL handle, int option, ...)`: what comes after is of C types, a number constant an `int` unless cast *(16 November, before the eighty-sixth slice, choice 752: a number written without a type is an error there, so the cast is always written)* | `printf`, `ioctl`, `fcntl` and libcurl's options need it |
| <a id="a-pointer-as-a-number"></a>A pointer as a number | `(nuint)p`, `(raw void)n`, `p - q` (a count of items) and `p < q`; none of them reads memory | `SQLITE_TRANSIENT` is `(void*)-1`; allocators and kernels compute addresses |
| <a id="the-layout-of-c"></a>The layout of C | Unions, bit fields, `packed` and alignment; a field of a union is read inside `unsafe`. The notation is decided in their slice *(16 November 2026, after the eighty-seventh slice: two more will be done, their slice not chosen yet. A `raw T` that is not aligned for `T` is a panic where it is read or written, in the interpreter and in checked compiled code; and a window that writes, a `ref T[]` over raw memory beside `Memory.view`, for a buffer C wants filled)*. Built in the eighty-ninth slice, with both (["The layout of C, as built"](../rules/c-and-the-machine.md#the-layout-of-c-as-built)) | C structs as C lays them out, binary formats, the registers of devices |
| <a id="three-systems"></a>Three systems | SG runs on Linux, macOS and Windows. Linux and macOS come first and Windows later, but nothing is built in a way Windows cannot take: what the language says holds on all three, what the runtime asks of the system goes through a function of its own, and the C the back end writes is read by the compilers of all three (on Windows Clang, since the C uses statement expressions). The parts already built on what only Linux and macOS have (the loop of the network on `epoll` and `kqueue`, threads and locks of `pthread`, signals, starting a program, `dlopen` in the interpreter, blocks aligned beyond 16 bytes given back with `free`) are looked over before the slice of Windows. *Decided on 16 November 2026, during the eighty-ninth slice* *(17 November 2026, the ninety-first slice: so is a library on Windows, a `.dll` with its `.lib`, pinned so that it is not unloaded, choice 874)* *(17 November 2026: looked over, ["Windows, the direction"](windows.md); the import library of a `.dll` is `x.dll.lib`, choice 929)* | Three systems are where programs run; going back later is dearer than keeping the way open |
| <a id="atomics-and-volatile"></a>Atomics and `volatile` | Built-in atomic types, sequentially consistent by default, with forms that take an order; `volatile` as calls (`unsafe Memory.readVolatile(p)`, `writeVolatile(p, v)`), not as a qualifier of a type *(16 November 2026, before the ninetieth slice, choice 843: the call takes a place in raw memory, `Memory.readVolatile(p[0].status)`, so that a field of a block of registers is reached)*. Built in the ninetieth slice (["Atomics and `volatile`, as built"](../rules/concurrency.md#atomics-and-volatile-as-built)) | Queues without locks; the registers of devices. Rust's form for `volatile` |
| <a id="a-library-built-from-sg"></a>A library built from SG | `sg build --library` gives a `.a` or a `.so` and a header made from the `export` functions *(built in the ninety-first slice: ["A library built from SG, as built"](../rules/c-and-the-machine.md#a-library-built-from-sg-as-built))* | C calls SG |
| <a id="without-an-operating-system"></a>Without an operating system | `sg build --freestanding` with a cross compiler, compiled code only: what needs the system (`print`, `File`, tasks) is a compile error with a hint, `string` and `List` work when the program gives an allocator, a panic goes to a function of the program, and `main` is not needed *(built in the ninety-third slice: ["Without an operating system, as built"](../rules/c-and-the-machine.md#without-an-operating-system-as-built))* | Kernels, boot loaders, small devices |
| <a id="the-kernel-shown"></a>The kernel shown | A RISC-V kernel on QEMU's `virt` machine *(built in the ninety-fourth slice: ["The kernel shown, as built"](../rules/c-and-the-machine.md#the-kernel-shown-as-built))* | Its start is the simplest, and its serial port and timer are plain |
| <a id="windows"></a>Windows | Not part of the threshold; talked through once the threshold is reached *(17 November 2026: talked through, ["Windows, the direction"](windows.md))* | A platform of its own: IOCP, its processes, its paths |
