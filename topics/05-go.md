# Go: its philosophy and its place among these languages

*Source: the conversation of 4 November 2026. The questions and answers are given as they were in the conversation; for correction notes see [decisions and open questions](../design/04-decisions-and-open-questions.md).*

## Question

> I noticed we never talked about Go :) Where is Go among these languages and what is its philosophy

## Answer

Go sits right in the middle of this conversation as a counter-argument: "Let us solve the memory safety problem with a GC, not with the type system, but make the GC fast enough for systems programming and keep the language as small as possible."

**The origin story explains the design.** In 2007 at Google, Rob Pike, Ken Thompson and Robert Griesemer started designing the language while waiting for a C++ build that took 45 minutes. Thompson is one of the creators of C and Unix, Pike comes from Plan 9. So Go is the answer of the people who wrote C to "what would we do if we wrote C today". The goal, though, was not academic but corporate: a language that thousands of new graduates at Google could work in at the same time, that compiles fast, is easy to read and can be maintained at large scale.

**The three pillars of the philosophy:**

1. **Fewer features, more language.** Rob Pike's famous essay "Less is exponentially more". Go had no generics until 2022, and it has no exceptions, no inheritance, no operator overloading, no macros, no implicit conversions, not even a ternary operator. There is one way to write everything, and `gofmt` ends that debate too. It is the exact opposite of Rust's choice that "every concept should be expressed in the type".

2. **A GC can be acceptable in systems programming.** Go's GC was optimised for low pauses: concurrent, tri-colour mark-sweep, with pauses at the microsecond level. It is not generational and it does not compact; throughput was sacrificed for simplicity and low latency. Add to this value types, placement on the stack through escape analysis, and pointers: part of C's control over memory layout stays in your hands, together with the GC. While in Java every object is on the heap, in Go structs are values.

3. **Concurrency is part of the language.** Goroutines and channels come from Hoare's CSP model (1978); Pike had already tried this three times, in Newsqueak, Alef and Limbo. Go is the fourth and the successful attempt. Millions of lightweight threads, with a scheduler managed by the runtime. This is not Go's real "new idea", but it is its best implementation.

**Comparison with the languages in this conversation:**

| Topic | C | Zig | Rust | Go |
|---|---|---|---|---|
| Memory management | Manual | Manual, explicit allocator | Ownership | GC |
| Memory safety | None | Partly runtime | Compile time | Runtime (GC + bounds check) |
| Data race | None | None | Compile time | None, there is a runtime race detector |
| Language size | Small | Small | Large | Small |
| Compile speed | Fast | Fast | Slow | Very fast |
| Runtime | None | None | None | Yes (scheduler, GC) |
| Target | Kernel, embedded | Kernel, embedded, tools | Everything | Server, network, CLI, infrastructure |

**Where it stands:** Although Go calls itself a "systems language", in practice it did not enter C's territory. There is no kernel, driver or embedded Go, because it has a runtime. The place it really took is the server side of Java and Python: Docker, Kubernetes, Terraform, Prometheus, CockroachDB. It became the language of cloud infrastructure. So while Rust is replacing C++, Go replaced Java and part of Python.

**Its weak sides, which the Go community admits too:**

- The `if err != nil` repetition. Errors are returned as values, but the language gives nothing to shorten this. Dozens of proposals on this were rejected; in 2025 the Go team said "we are no longer trying".
- The nil pointer is still there. There is no equivalent of Rust's `Option` or Zig's `?T`. Nil having two meanings in interfaces is a classic trap.
- Generics came late and are limited. There are type parameters, but methods cannot be generic and there are no higher-kinded types.
- Data races are not prevented at compile time. Goroutines are easy, but making shared memory mistakes is easy too. There is the `-race` flag, but it finds only what you can find during testing.
- Zig's "no hidden control flow" principle is broken here as well: `defer`, `panic`/`recover`, GC pauses.

**From your point of view:** If you find C#'s syntax clean and Rust's noisy, Go may appeal to you; its syntax is even leaner than C#'s. But the question at the start of the conversation was "as fast as C and free of C's bugs". Go answers this question with "give up 20 to 50 percent of being as fast as C, accept the GC, and in return skip all of Rust's complexity". It is an honest trade-off, and the right one for most server software. Rust's reason to exist is the 10 percent that cannot make this trade-off: browser engines, kernels, game engines, embedded, real time.

For the question of designing your own language, Go's lesson matters: Go's success did not come from language features but from **the discipline of not adding features** and from the toolchain (gofmt, go build, go mod, go test, each a single command). Language designers mostly think "what should I add"; Go won by thinking "what should I not add".
